# 多内核壳：pi 和 dsh 是同级的两个内核

> ⚠ **思路稿/部分已被取代**：「切内核=开新会话」「补面在适配器」已被 kernel-design-spec.md §17/§18 与 session-neutral-layer.md §16/§19（切内核=换投影，同会话来回切）取代。本文保留作历史参考。

- my-harness-desktop 不是「pi 的壳」。它是一个内核无关的壳：壳只认一份中立契约，契约背后可以是 pi、dsh，或任意个自洽的 agent 运行时。pi 和 dsh 是同级的两个内核，谁也不比谁更「内建」。

- 本文把这层抽象拆成四个并列的概念，各自讲清细节：**内核**（它是什么、不是什么）、**中立契约**（壳需要内核提供什么）、**适配器**（内核专属与中立之间的翻译）、**壳**（它拥有什么、不拥有什么）。四个概念合起来，就是「多内核壳」的全部。

- 名词先一次性交代：**内核**（kernel）指一个自洽的 agent 运行时，自带插件树、会话模型、能力集——pi 和 dsh 各是一个；**壳**（shell）指 my-harness-desktop 的薄壳，拥有槽位/渲染/布局/事件总线等机制；**中立契约**（contract）指壳需要内核提供的「最小意图」集合；**适配器**（adapter）指内核专属形状与中立契约之间的翻译层，每个内核一个；**壳插件**指挂在壳槽位上的 UI 插件，只 import `@my-harness-desktop/contract`。**lineage** 指一条会话里的「一条线性历史」——根 lineage 是最早那条，fork 出来的分支各是一条 lineage，`fork(parent, boundary)` 里的 parent 和 boundary 都是 lineage 坐标系里的东西。**capability seam**（能力缝）是 dsh 的能力组织方式：一个能力 = 定义（接口）/ 提供（实现）/ 消费（调用）三个角色，provider 可换、consumer 无感知。**Cordis 插件树**是 dsh 的扩展机制：一切（工具、模型、连 agent-loop 本身）都是插件，挂在同一棵树上。**会话头**是会话自带的元数据（谁建的、哪个内核、哪个项目），内核归属就记在这里。**多路并发**是 pi 的 `steer`/`followUp` 所指：同一会话里同时开多条消息线、各自推进。本文刻意不用「底座」这个词——它在 my-harness-desktop 里既指「被管理资源」、又暗含「pi 那一套」，两个意思混在一起，讲不清「同级」。

## 1. 问题：底座抽象只有 pi 一个实例，壳长成了 pi 的壳

### 1.1 「底座是被管理资源」是一句没被第二实例验证的宣言

- my-harness-desktop 的设计宣言里有一句：底座不是插件，是被管理资源，和 git、文件系统同一层抽象。这句话如果成立，换底座就该像换 git 实现一样，壳一行不改。但到今天为止，这句话只被一个实例——pi——验证过，而且是「恰好」验证过：pi 的协议、会话文件、事件形状从一开始就是壳的圆心契约参照系，从来不需要「换」，也就从没暴露过这句话哪一部分是假的。

- 为什么拿 dsh 当第二个实例？因为它是「和 pi 几乎处处相反」的那个内核，是最锋利的探针。pi 的会话是文件、dsh 是日志；pi 的 fork 在文件内分叉、dsh 的 fork 出子会话；pi 的事件是 `message_start/update/end` 三态、dsh 是 `assistant/chunk` token 增量；pi 的扩展是装进进程的 TypeScript 扩展、dsh 是 Cordis 插件树、连 agent-loop 都是插件。如果壳能吞下这个处处相反的实例而不改一行，那句宣言就真的成立；吞不下，泄漏点会在第一次接入时当场现形——这正是这次实验要抓的东西。

### 1.2 壳插件已经内核无关，但圆心契约仍漏 pi 的形状

- 壳插件这一层是干净的：它们只 import `@my-harness-desktop/contract`，看到的是会话意图（prompt/abort/steer），不是 pi 的命令字面量。但壳插件之下、底座之上的「圆心契约」，还在三个地方漏着 pi 的形状。

- **会话标识是文件路径**。`SessionsApi.list/openSession/copySession/forkFromSession` 全吃 `~/.pi/agent/sessions/` 下的 JSONL 文件路径，连 bookmarks 都自己在项目目录下管一份副本。dsh 的会话是 append-only 日志，没有文件可指。

- **事件形状是从 pi 翻来的**。中性 `SessionEvent`（`messageStart/messageUpdate/messageEnd`、`toolCallStart/End`）是从 pi 的 `message_start/tool_execution_start` 翻译来的。dsh 的事件是 `turn/start`、`assistant/chunk`、`tool/call`，粒度不同，翻译不是一一对应。

- **fork 语义是文件内分叉**。pi 的 fork 在文件内挂 `parentId` 开分支、分支跟着原文件走；dsh 的 fork 是 `ctx.sessions.fork` 新建一个自洽子会话、前缀被拷贝。两者同名，语义不同。

- 这三个泄漏不是抽象问题，是「把 dsh 塞进来当天就会崩」的具体问题。如果现在直接让 dsh 当底座：壳去 `~/.pi/agent/sessions/` 找 dsh 的会话文件，找不到——dsh 没有文件；壳等 pi 的 `message_end` 事件来闭合消息，dsh 推的是 `assistant/chunk`，时间线永远不闭合；壳调 `fork(entryId, "at")`，dsh 的 fork 既没有 entryId 也没有 position，直接报错。三处泄漏，一处崩一个功能。

### 1.3 目标：壳同时托管 N 个同级内核，换内核 = 换适配器

- 目标不是「把 pi 换成 dsh」，是「让壳同时托管任意个同级内核」。pi 和 dsh 谁也不比谁更内建，都是注册进壳的内核；换内核 = 换一个适配器，壳和壳插件不动。这篇文章要立住的，是这个目标背后的四个抽象，以及它们各自的精确边界。

### 1.4 为什么不是别的做法

- 要「接第二个内核」，有三条看着更省力的路，都不对。**继续 pi-only**：把 dsh 的 DeepSeek 适配器搬进 pi，壳一行不改——但那是把内核的插件树拆了、只搬一个 adapter，dsh 的价值（Cordis 插件树、能力缝）没进来，等于「为了省架构，丢掉内核本身」。

- **给 dsh fork 一份壳**：把 my-harness-desktop 复制一份、改掉 client 层给 dsh 用——短期能跑，长期两份壳各自维护，槽位/渲染/布局这些本该共用一层的东西，全要双份。这正是「多内核壳」要消灭的重复。

- **翻译层让 dsh 装 pi**：写一个适配器让 dsh 学说 pi 的 31 命令协议，壳一行不改——这是最省事的假象，但 dsh 要重新实现 pi 的会话文件、parentId 树、fork 语义，等于「让 dsh 假装自己是 pi」，永远追着 pi 的表面走，且 dsh 的 append-only 日志、子会话这些真长处全被埋掉。

- 三条路的共同病根：它们都把「内核」当成「pi 的形状」，而不是「一个抽象」。多内核壳和它们的区别，不在工作量，在于「内核」这个词从「pi」变成了「一类东西」。

## 2. 抽象一：内核

### 2.1 内核的判据

- 内核是一个自洽的 agent 运行时。判据有三条：它有一棵自己的插件树（扩展机制）、它有一个自己的会话模型（怎么存、怎么分叉、怎么回放）、它有一个自己的能力集（工具/模型/子代理）。三条齐了，它就是一个能被壳托管的内核。

- 内核的价值在于它的插件树。把 dsh 接进壳，价值不是「多一个能发消息的进程」，是它的整个插件树跟着一起进来——模型适配器、工具、子代理，全是内核侧插件，接内核 = 连树一起进。pi 同理：它的价值是它的扩展（会话总线、工具门控、子代理）加技能生态。

### 2.2 pi 作为内核

- pi 的会话模型是磁盘上的 JSONL 文件，条目靠 `parentId` 连成树，fork 在文件内开分支；能力集是 31 个 RPC 命令（`prompt`/`steer`/`fork`/`compact`/`exportHtml` 等）；扩展机制是装进 pi 进程的 TypeScript 扩展。

### 2.3 dsh 作为内核

- dsh 的会话模型是 append-only 的 `SessionEvent` 日志，fork 是 `ctx.sessions.fork` 新建一个自洽子会话（前缀被 `events.slice(0, boundary+1)` 拷贝）；能力集是 capability seam（Service Definition / Provider / Consumer）；扩展机制是 Cordis 插件树——连 agent-loop 本身都是插件。

### 2.4 三个「不是」

- 内核不是壳插件。壳插件挂槽位、出 UI；内核出能力、不出 UI。一个东西如果主要产出是 React 组件，它是壳插件；如果主要产出是会话/工具/模型，它是内核。

- 内核不是适配器。适配器在内核之外，是内核专属形状到中立契约的翻译；内核本身不知道、也不需要知道自己正被一个壳托管。

- 内核不是「底座」。「底座」既暗示「被管理资源」、又暗示「pi 那一套」，两个意思混在一个词里，才让「把 dsh 也接进来」这件事显得别扭。用「内核」替代它之后，pi 和 dsh 都能无争议地填进去，谁也不抢占「内建」的位置。

### 2.5 内核的契约义务

- 内核对壳只有一项义务：兑现中立契约。它内部怎么存会话、怎么分叉、怎么跑插件，是它自己的事，壳不过问。这条义务是双向的——壳也只能向内核索要契约里的东西，不能伸手进内核内部。

- 两个内核在五个维度上的差异，一张表钉死：

| 维度 | pi | dsh |
|---|---|---|
| 会话模型 | JSONL 文件 + `parentId` 树 | append-only `SessionEvent` 日志 |
| fork | 文件内开分支（不拷贝，跟随原文件） | fork 出子会话（前缀拷贝） |
| 事件 | `message_start/update/end` 三态 | `turn/start`、`assistant/chunk` 增量 |
| 扩展 | 装进 pi 进程的 TS 扩展 | Cordis 插件树（连 agent-loop 都是插件） |
| 能力 | 31 个 RPC 命令 | capability seam（定义/提供/消费） |

- 一个内核要「接入」壳，交三样东西：一个 **spawn 命令**（怎么起这个内核进程、起几个、怎么杀）、一个 **适配器**（把它的专属形状投成中立契约）、以及一份 **会话模型映射**（把它的会话落到 lineage 坐标系上——`fork` 的 parent/boundary 分别对应它内部的什么）。三样齐了，它是一个「可托管内核」；缺任何一样，它只是「一个能跑的程序」，不是壳能托管的内核。

### 2.6 内核的生命周期

- 壳和内核的关系是「一个内核 = 一个子进程」。壳 spawn 它、探测它就绪、给它发意图、收它的事件流、最后 kill 它。生命周期四个阶段：**spawn**（按内核的 spawn 命令起进程）、**就绪**（内核回一个就绪信号，壳才开始发意图，否则意图会落空）、**运行**（意图往返 + 事件流）、**退出**（用户关会话或内核崩了，壳收尾、pending 的意图全部报错）。这套生命周期对 pi 和 dsh 一模一样，区别只在 spawn 命令和就绪信号的形状——那两个归各自的适配器，不进契约。

### 2.7 同级的代价

- 「同级」不是免费的。它要付出三个代价：**pi 失去默认特权**——今天 pi 是唯一底座，很多东西「默认就是 pi」；同级之后，默认也要显式化（「默认 pi」是一个配置，不是「pi 内建」）。**迁移有成本**——三处泄漏要中性化，这是真工作量。**测试翻倍**——壳的集成测试要跑 pi 和 dsh 两遍，任何一个内核的行为差异都要解释。代价换回来的是「换内核不用改壳」这个能力——值不值，取决于你预期未来有几个内核。

### 2.8 内核接入的验收

- 一个内核「可托管」的验收，是它能把 §3 的六条意图每条都兑现或显式「不支持」，外加 §2.6 的生命周期跑通。验收不看你「读了多少它的源码」，只看三件事：起得来、六条意图逐条有响应、崩了壳能收尾。三件过了，它就是一个合格的内核——至于它内部多复杂、插件树多深，壳不在乎。

### 2.9 能力与意图的分野

- 内核的「能力」和契约的「意图」是两个词，别混。能力是内核**有什么**——pi 有 31 命令、dsh 有工具和能力缝；意图是壳**要什么**——六条。能力是内核的内部事实，意图是壳的必要需求，两者靠适配器对上。内核有一堆能力，壳只关心其中六条能对上；对不上的（pi 的 `steer` 之外的、dsh 的 lsp/terminal 之外的）是内核自己的事，壳不用也不碰。这个分野解释了为什么「内核很强大」不等于「契约要很大」——内核再强，壳要的始终是那六条。

### 2.10 为什么每个内核要有自己的插件树

- 为什么不让壳统一管所有插件、把 pi/dsh 的插件都挂壳上？因为插件树是内核的**能力来源**，不是壳的 UI 扩展。dsh 的工具、模型适配器、capability seam 全是 Cordis 插件，它们直接操作 dsh 的 session/agent 内部，离开 dsh 的运行时毫无意义；pi 的扩展（工具门控、会话总线）同理，直接 patch pi 的 RPC。把这些插件挂到壳上，等于让壳去实现每个内核的运行时细节，壳就再也不是薄壳了。所以插件树必须留在内核各自，壳只托管「壳插件」这一套 UI 扩展——这就是三套插件系统各自独立的根因。

## 3. 抽象二：中立契约

### 3.1 最小意图集

- 中立契约是壳需要内核提供的「最小意图」，一共六条。每条钉死签名、边界、以及它刻意不包含的东西。多了，就是把某个内核的专属概念塞进契约；少了，壳就缺一项能力。

- 这六条是从「壳的 UI 到底要做什么」倒推出来的。timeline 要显示消息、要流式滚（→ 消息、流式事件）；停止按钮要打断生成（→ 中断）；分支树要分叉（→ 分支）；会话列表和书签要定位「哪个会话哪个分支」（→ 会话标识）；模型下拉框要切模型（→ 模型）。壳的 UI 只需要这六件事，所以契约只需要这六条——多一条，就是为某个内核的专属能力开的特权口。

- **消息 `sendMessage(text, images?)`**：发一条用户消息。边界是「文本 + 可选图片」，到此为止。它不包含 `steer`/`followUp`——那是 pi 的多路并发叫法，dsh 没有对应，进契约就会把 pi 的形状带进去。

- **中断 `abort()`**：取消当前回合。边界是「取消」，到此为止。它不包含 `abort_bash`——那是 pi 内部「先中断 bash 再中断 agent」的编排，是 pi 专属。

- **分支 `fork(parent, boundary?)`**：从某条 lineage 的某点切出一条新 lineage。边界是「父 lineage + 一个分叉点」。它不包含 `position`（before/at）——那是 pi 的 fork 参数，dsh 的 fork 没有。

- **会话标识 `sessionId`**：一个不透明字符串。边界是「壳拿它定位一条 lineage，不解析内容」。它不包含文件路径——文件是 pi 的存储，dsh 没有文件。

- **流式事件**：一条中性事件流。边界是「消息开始/增量/结束、工具调用开始/结束」这五种事件。它不包含内核自己的事件形状——pi 的 `message_start/update/end` 和 dsh 的 `assistant/chunk` 由各自的适配器投成同一条中性流。

- **模型 `setModel(provider, model)`**：切 provider/model。边界是「provider + model 二元组」。它不包含 `thinkingLevel`——那是 pi 的推理强度档位，dsh 用 `reasoningEffort`，是两个不同的概念。

- 六条意图在 pi 和 dsh 两边各落到什么，一张表对照：

| 意图 | pi | dsh |
|---|---|---|
| 消息 | `prompt` 命令 | `session/prompt` |
| 中断 | `abort` 命令 | `session/abort` |
| 分支 | `fork(entryId, position)` | `session/fork(parentSessionId, boundarySeq)` |
| 会话标识 | 文件路径 | session id |
| 流式事件 | `message_start/update/end` | `assistant/chunk` 组装 |
| 模型 | `set_model` | `session/setModel`（dispose+resume 补面） |

- 注一：六条意图落到接口层不是六个方法——「会话标识」一条对应 `getTree`/`getEntries`/`bookmark`/`resume` 四个操作（都是「壳定位/保存一条 lineage」的机械展开），外加 `deleteBookmark`（书签清理补面，不单独列意图）。所以接口面是「四意图一方法 + 会话标识四操作 + 流式事件一订阅」。
- 注二：代码层至今仍用「底座」指代本文的「内核」（`BaseBackend`/`PiBackend`/`DshBackend`），文档用「内核/契约/适配器」。这是术语断层，不是两套概念，统一重命名留待独立收尾。

- 这张表就是「中立契约 → 两个适配器」的骨架：每一行，左边是契约签名，右边两列是各自适配器要做的事。适配器写得好不好，就看它能不能把右列的每一行，干净地投成左列那一行。

- 六条意图各自「用一次」是什么样：

- **消息**：用户点发送 → 壳调 `sendMessage("帮我看看这段代码")` → 内核生成 → 壳收中性事件流 → timeline 流式滚出回复。这是唯一会「起内核进程」的意图。

- **中断**：用户点停止 → 壳调 `abort()` → 内核停止当前生成 → 壳把「已收部分」标成「已停止」。重复点停止，第二次是 no-op。

- **分支**：用户在分支树里某条消息上点「从这里分叉」→ 壳调 `fork(这条消息所在的 lineage, 这个消息的 boundary)` → 内核切出一条新 lineage → 壳在分支树上多一个分支。

- **会话标识**：壳要定位「哪个会话的哪个分支」，手里只有一串 id——`fork` 返回新 lineage 的 id，`getTree` 返回整棵树的 id 结构。id 对壳是不透明的，壳不解析它里面是什么。

- **流式事件**：内核边生成边推「开始→增量→增量→…→结束」，壳边收边渲染，直到「结束」或「断开」。断开时壳把已收部分标成「已停止」，不假装消息完整。

- **模型**：用户在模型下拉框选「DeepSeek V4 Pro」→ 壳调 `setModel("deepseek-official", "deepseek-v4-pro")` → 内核切到该模型 → 下一条消息用新模型。

### 3.2 契约的地板

- 中立契约有个地板：不是所有东西都能中性化。会话是「文件」还是「日志」、消息是「内容块」还是「树」、fork 是「文件内分叉」还是「fork 出子会话」——这些是内核之间真实的存在差异，不是翻译层能抹平的。

- 地板的画法：壳**必须**中立的（否则换内核要改壳），和壳**必须留给内核各自的**（否则削平两边、哪个都用不爽），要精确分界。六条意图里，「消息/中断/分支/模型」的地板在签名层——签名中立，实现归内核；「会话标识」和「流式事件」的地板在形状层——壳只认不透明 id 和中性事件，内核的存储和事件形状留在适配器里。

- 为什么分这两层？因为「签名」和「形状」是两种不同性质的中立化。签名层的中立，是「函数长什么样」——`fork(parent, boundary)` 这个名字和参数，pi/dsh 都能填，所以签名可以中立。形状层的中立，是「数据长什么样」——会话是「文件」还是「日志」、事件是「三态」还是「增量」，这是内核的存储和协议本身，壳不碰、也碰不了，只能要求「壳看到的那一层」中立。分层的意义：签名层中立，换内核不改接口；形状层中立，换内核不改壳的渲染。

- 中性化不足，换内核要改壳（现在的三处泄漏）；中性化过头，丢掉 pi 的文件树和 dsh 的 append-only 日志。地板就是两者之间那条线，也是这份契约唯一需要精雕的地方。

### 3.3 契约的纪律

- 契约是「最小公共分母」：多一分是内核专属、少一分壳缺能力。判断一个东西该不该进契约，只问一句——「壳是不是必须向**每一个**内核索要它？」如果 dsh 没有、且壳不非得要，它就不进契约。

- 拿这个判据过一遍被排除的候选，就能看出为什么是这六条、不是别的。**compaction** 不进契约：它是内核自管上下文的内部事务，壳只观察（`compactionStart/End` 事件）、不驱动——壳不必向每个内核索要「压缩」。**列工具**（tool-list）不进契约：壳渲染的是「工具调用/结果」的中性事件，不渲染「内核有哪些工具」这个清单，后者是内核自己的配置面。**搜索/文件树/终端**同理：它们是「能力」，不是「意图」——壳要的是「怎么发、怎么停、怎么分叉、怎么定位、怎么收事件、怎么切模型」，其余能力由工具在「消息」这一条里承载。

- 中立契约是**下限**，不是上限。壳插件除了六条，还能调到某个内核专属的意图（比如 pi 的 `steer`）——它们经那个内核的适配器暴露，在别的内核上降级为「不支持」。壳的核心机制（渲染、布局）只依赖下限；内核专属意图是「有则用、无则降级」的扩展面，不决定内核的地位。

### 3.4 意图的失败与幂等

- 六条意图各自有失败语义和幂等语义，钉死之后，适配器和壳插件才知道「坏了怎么办、重试行不行」。

- **消息**：失败 = 内核拒绝（消息格式不对）或超时，壳收到错误、不静默；幂等 = 不可重入，一条消息发两次是两条消息，「已发去重」由壳的上层（发送按钮）保证，契约不承诺去重。

- **中断**：失败 = 内核无响应，壳超时放弃、不阻塞；幂等 = 可重入，重复 `abort` 无害。

- **分支**：失败 = 边界无效（非连续、或落在回合中间）报错，壳把入口降级成「从末尾分叉」；幂等 = 不可重入，每次 `fork` 都产生一条新 lineage。

- **会话标识**：失败 = 无（纯值）；幂等 = 无状态，同一个 id 永远指向同一条 lineage。

- **流式事件**：失败 = 流断开，「已收部分」保留、标记「已停止」；幂等 = 增量按序消费，重复/乱序的增量由壳端去重。

- **模型**：失败 = 内核无此 provider/model，报错；幂等 = 可重入，同值 `setModel` 无副作用。

### 3.5 契约的版本化

- 契约会变——下一个内核漏出新形状，壳的「必要面」可能扩大。但变法是「只往壳的必要面扩」，不是「追着内核的专属形状跑」：每加一条意图，都要回答「壳是不是必须向每一个内核索要它」，答不上就不加。

- 兼容策略分两层：**加意图**是向后兼容的（旧内核不实现新意图，降级为「不支持」，壳照跑）；**改意图**（比如 `fork` 的 boundary 从 string 变成别的）是破坏性的，要显式版本号，壳和适配器按版本对齐。契约没有「悄悄改」——每次改动要么是加、要么是带版本号的破坏性变更，不存在第三种。

### 3.6 一个完整会话把六条串起来

- 一个完整会话，六条意图各出场一次：用户开新会话（内核归属记进会话头）→ 发消息 `sendMessage`（起内核）→ 内核边生成边推流式事件（壳滚出回复）→ 用户不满意，点「从这里分叉」`fork`（分支树多一个分支）→ 在新分支里试了试，觉得值得留，点书签（`bookmark` 记下这个 `sessionId` + 分叉点）→ 换了个模型 `setModel` 继续 → 聊完了，中途点过几次停止 `abort`。六条意图，一个会话里全用到了，而壳从头到尾没碰过内核的存储、没消费过内核的原始事件——这就是六条够用的证明。

### 3.7 契约的边界情况

- 六条意图各自的边界情况，钉死几个最会踩的：**空会话上 fork**——没有内容可分叉，`fork(parent, 空 boundary)` 就是「开一条新 lineage」，不报错；**setModel 到不存在的模型**——内核报错，壳在模型下拉框标红、不静默切到上一个；**流断开在消息中间**——壳把已收部分标「已停止」，不假装消息完整，下次重连从「重试」开始；**两个内核同名模型**——模型名是内核各自的，壳不跨内核比对，选了哪个内核就用哪个内核的模型表。

## 4. 抽象三：适配器

### 4.1 三个角色

- 适配器是内核专属形状与中立契约之间的翻译层，每个内核一个。它做的事分三种：直接映射、需翻译、缺面。

### 4.2 直接映射

- 直接映射 = 语义完全一样，适配器只把参数按各自的线格式摆好，不改变任何结构。判据是「一对一、无拆合」：中性签名的每个字段，内核签名里都有唯一对应。例子：消息这条意图，pi 叫 `prompt`、dsh 叫 `session/prompt`，名字不同、线格式不同，但两边做的都是「发一条用户消息」这件事——适配器把文本搬过去，没翻译任何语义。中断同理：pi 的 `abort`、dsh 的 `session/abort`，同名同义，适配器只换线。

### 4.3 需翻译

- 需翻译 = 语义一样，但**形状**变了：不是换名字，是「一条拆多条」「粒度变了」「结构重排」。判据是「不是一对一」：中性签名和内核形状对不上，适配器要拆、合、或折叠。

- 流式事件是「拆」：pi 把「一条消息」拆成 `message_start/update/end` 三条，dsh 拆成 `assistant/chunk` 若干 token 增量，适配器把两边的拆分方式都投成中性事件的「开始/增量/结束」。

- 会话标识是「折叠」：pi 的会话本质是「文件路径」，壳的 `sessionId` 是纯不透明 id，适配器把「路径」折叠成「id」，中间丢掉了「会话是文件」这个信息——壳从此不再知道会话是不是文件。这正是折叠和搬运的区别：搬运不动信息，折叠丢掉信息。

### 4.4 缺面

- 缺面 = 内核根本没有这个能力，找不到可翻译的对应物。判据是「找不到对应」：壳要的意图在内核里不存在，翻译无从谈起。两种处置：**降级**——壳收到「不支持」，照常跑其余能力，pi 的 `steer` 对 dsh 就是缺面（dsh 没有多路并发，steer 按钮在 dsh 下降级）；**补面**——在适配器里补一个实现，凑出这个能力，「运行中热切模型」对 pi 是现成的 `set_model`，对 dsh 是缺面，适配器用「dispose 旧 agent + resume 同 session」补出「热切」。

- 补面发生在**适配器里**，不伸手进内核——内核始终不知道自己在被补。这跟「翻译」的区别是：翻译是形状之间的换算，补面是凭空造一个内核没有的东西。

### 4.5 适配器的位置

- 适配器夹在壳和内核之间，每个内核一个。壳不感知适配器这个「翻译层」的存在——它只看到中立契约的六条意图，外加各内核经适配器暴露的扩展面（`steer` 之类）；内核也不感知自己被托管，它只兑现自己的协议。换内核，就是换一个适配器——这是「多内核壳」能立住的全部机制。

### 4.6 端到端：一条消息在 pi 和 dsh 两条路径上怎么走

- 发一条消息，壳调 `sendMessage("帮我看看")`。pi 路径：适配器把 `sendMessage` 直接映射成 pi 的 `prompt` 命令（只换线格式），pi 进程推 `message_start → message_update* → message_end`，适配器把三态投成中性事件的「开始/增量/结束」，壳渲染。dsh 路径：适配器把 `sendMessage` 映射成 `session/prompt`，dsh 推 `assistant/chunk` 若干 token 增量，适配器把增量组装成中性事件的「开始/增量/结束」，壳渲染。两条路径，壳看到的是同一条中性事件流——这就是「换内核 = 换适配器」的全部含义。

### 4.7 适配器的错误语义

- 适配器自己也会坏，坏了要有明确语义。**内核崩了**（进程退出）：适配器把「已收部分」投成「已停止」，pending 的请求全部报错，壳进入「内核离线」态、可重启。**RPC 超时**：单条请求超时报错，不影响内核进程本身。**缺面降级**：壳调了内核没有的意图，适配器返回「不支持」，不抛异常、不崩溃。三种错误的共同纪律：适配器不吞错、不伪造成功——内核没做的事，适配器绝不假装做了。

### 4.8 适配器的具体形态

- 适配器在代码里是一个接口的 N 个实现：接口就是中立契约的六条意图 + 生命周期，pi 适配器一个类、dsh 适配器一个类。直接映射、需翻译、缺面三种事，在代码里就是三个形状：直接映射是一行「把参数换个字段名发出去」，需翻译是一段「把内核事件逐条组装/折叠成中性事件」，缺面是一段「要么返回不支持、要么调用内核别的能力凑出来」。三者合起来，就是一个适配器类的全部内容——适配器没有第四种事可做。

### 4.9 翻译的边界

- 适配器的「翻译」有边界，边界就是契约的地板（§3.2）。翻译能做的是「形状之间的换算」：三态 ↔ 增量、文件路径 ↔ 不透明 id、before/at ↔ 分叉点。翻译不能做的是「凭空造一个内核没有的东西」——那已经跨到「缺面」了，不再是翻译。区分「这是翻译还是缺面」，就看一件事：内核有没有「同一个语义、只是形状不同」的对应物。有，是翻译；没有，是缺面。

### 4.10 适配器怎么算写对

- 一个适配器写对的标准，是「壳插件在它上面跑，和在另一个适配器上跑，行为一致」。可检验的三条：**意图覆盖**——六条意图每条都有实现或显式「不支持」，没有「忘了实现」的静默空转；**事件等价**——同一条内核事件，投成的中性事件和另一个适配器投的一致；**错误诚实**——内核崩/超时/缺面，壳收到的错误和另一个适配器一致。三条全过，适配器就算写对。

### 4.11 适配器的生命周期

- 适配器没有独立的生命周期，它跟着内核走：内核 spawn，适配器就建连接；内核就绪，适配器就标记可发意图；内核退出，适配器就断开、pending 全报错。适配器是内核的「影子」，内核活着它就在，内核死了它不留。这让「换内核」变成一件干净的事：杀掉旧内核进程，旧适配器随之消失；起新内核进程，新适配器随之建立——中间没有需要手动收拾的残留状态。

## 5. 抽象四：壳

### 5.1 壳拥有什么

- 壳拥有机制：槽位/贡献（sidebar/sidePanel/mainView/settings 等）、会话意图（对内核发 prompt/abort/fork 的接口）、渲染（timeline/会话列表/分支树）、布局、文件与主题、事件总线。这些是「所有内核共用」的东西，收进壳。

### 5.2 壳不拥有什么

- 壳不拥有任何内核的存储格式、事件形状、插件树、fork 语义。pi 的 JSONL 文件、dsh 的 session log，都不出现在壳的契约里；壳只认不透明 id 和中性事件。

### 5.3 壳插件与内核之间没有直接通道

- 壳插件只 import 一份契约（`@my-harness-desktop/contract`），它对内核的一切访问都走契约 + 适配器。壳插件不感知自己是挂在 pi 上还是 dsh 上——这是「壳插件内核无关」的精确含义。

### 5.4 壳的不变量

- 壳有几条「任意内核下都成立」的不变量，它们是「内核无关」的可检验标准：**壳不读任何内核的存储**（pi 的文件、dsh 的日志，壳都不碰，只认不透明 id）；**壳只认中性事件**（内核事件由适配器投喂，壳不直接消费内核事件）；**壳的渲染是纯函数**（给定同一条中性事件流，timeline 怎么画，与内核无关）。这三条不变量是「多内核壳」成立的判据——违反任何一条，壳就偷偷依赖了某个内核。

### 5.5 会话意图的完整链路

- 壳插件点「发送」→ 壳的会话意图层收到 `sendMessage` → 按当前会话的内核归属路由到对应适配器 → 适配器把 `sendMessage` 变成内核的命令 → 内核推事件流 → 适配器投成中性事件 → 壳渲染。这条链路里，壳插件、壳的意图层、壳的渲染，三处都不感知内核身份；感知内核身份的只有「路由」这一跳，而它只认一个不透明标记。判断壳有没有漏内核身份，就看这条链路上有没有出现「if 内核 === pi」这种分支——出现一处，就是一处泄漏。

### 5.6 机制与内容：多内核壳是「机制与内容分离」的延伸

- my-harness-desktop 自己的第一条铁律是「机制与内容分离」：内核（core）只放机制，文案/配色/管理页这些内容全推给插件。多内核壳是这条铁律在「底座」这一层的延伸：壳只放「所有内核共用的机制」（槽位/渲染/意图/事件总线），内核只放「它自己的内容」（会话模型/插件树/能力集）。「机制与内容分离」在 UI 层叫「壳 vs 壳插件」，在底座层就叫「壳 vs 内核」——同一句铁律，两层各应用一次。

### 5.7 壳漏内核的反例

- 「壳偷偷依赖了内核」长什么样，举两个具体反例：壳代码里写 `if (sessionPath.endsWith(".jsonl"))`——它知道会话是 JSONL 文件，这是 pi 的形状；壳直接读 `~/.pi/agent/sessions` 目录做会话列表——它知道会话存在哪，这也是 pi 的形状。凡出现「壳知道会话是文件还是日志、壳知道内核的目录、壳直接消费内核的原始事件」，都是泄漏。多内核壳的纪律，就是把这些「知道」一个个从壳里赶出去，赶进适配器。

## 6. 同级别落地：把 pi 从「唯一底座」降成「一个内核」

### 6.1 底座注册表

- 一个内核 = 一个「怎么 spawn、怎么翻译」的实现，注册进一份注册表，配置选当前会话用哪个。pi 和 dsh 平级注册，谁也不默认、谁也不内建；旧会话按头里记的内核归属打开，归属缺失的默认 pi（迁移期兼容），但这是「默认值」不是「特权」。

### 6.2 迁移顺序

- 先把 pi 降级成「一个内核」：把 pi 的协议、会话文件、31 命令全部收进 pi 适配器内部，验证壳在 pi 上语义等价。再让 dsh 入列：写 dsh 适配器，壳一行不改。顺序不能反——先降级 pi，再入列 dsh，每一步都有一条已知正确的参照线，不会出现「新契约 + 新内核一起炸、分不清是谁的错」。

### 6.3 现有缝隙逐个中性化

- 三处泄漏（会话标识、事件形状、fork 语义）逐个收进适配器：会话标识从文件路径换成不透明 id、事件形状从「pi 翻来的中性流」换成「适配器各自投喂的中性流」、fork 语义从「文件内分叉」换成「lineage + 分叉点」。这是「多内核壳」从宣言变成事实的最后一步。

### 6.4 三个缝隙各自的收口步骤

- **会话标识**：先把 `SessionsApi` 的接口从「吃文件路径」换成「吃不透明 id」，内部再映射回文件（pi 侧）；bookmarks 不再自己管副本目录，改调 `bookmark`/`resume`。这是三处里牵动最广的，因为它从圆心契约一直漏到插件的取数层。

- **事件形状**：把中性 `SessionEvent` 从「pi 翻来的三态」重定义成「适配器各自投喂的中性流」，pi 和 dsh 各写一条投喂线；`assistant/chunk` 的 token 级流式补上，否则 dsh 下时间线只能等消息完成才跳出来。

- **fork 语义**：把 `fork(parent, boundary)` 的 boundary 定义成「lineage 上的一个分叉点」，pi 映射成它的 user 锚点、dsh 映射成它的 boundary seq；position（before/at）收进 pi 适配器内部。

### 6.5 「完成」的定义

- 多内核壳完成的标准不是「dsh 能跑」，是「壳在 pi 和 dsh 上行为一致」：同一个壳插件、同一份中性事件流，在 pi 和 dsh 下渲染出同样的 timeline、同样的分支树、同样的书签行为。可检验的形式是：一套壳插件的集成测试，参数化地跑在 pi 和 dsh 两个后端上，全绿且壳插件代码零改动——那一天，壳才真正内核无关。

### 6.6 迁移期的并存与回滚

- pi 和 dsh 并存期间，一份会话数据只属于一个内核，不存在「同一会话在两个内核下打开」。选内核 = 开新会话时选一次，记进会话头；旧会话按头里的归属打开，不跨内核读。回滚 = 把默认内核改回 pi，dsh 会话留在原地、不迁移、不丢失。迁移本身是无损的——它从不搬数据，只搬「哪个内核负责哪个会话」这个归属，所以随时可回滚，不存在「迁到一半回不去」。

### 6.7 完成之后的一天

- 多内核壳完成之后，用户的一天是这样：开新会话时选一个内核（默认 pi），在这个会话里聊天、fork、书签、重试，行为和今天一模一样；哪天想试试 dsh 的 DeepSeek，开一个新会话选 dsh，timeline、分支树、书签还是那套，只是底座换成了 dsh；不想用了，把默认改回 pi。全程，壳和壳插件一行没改。这就是「多内核壳」的日常形态——不是一个「迁移项目」，是一个「内核可替换」的常态。

### 6.8 迁移验收表

- 迁移完成，按这张表验收：**会话标识**——壳插件代码里不再出现文件路径，只剩不透明 id；**事件形状**——pi 和 dsh 各自投喂同一条中性流，timeline 在两边渲染一致；**fork**——分支树在两边画出一致的 lineage 树；**bookmarks**——书签在两边都能建、能重启；**回归**——pi 上跑旧集成测试全绿，dsh 上跑同一套全绿，壳插件零改动。五条全过，多内核壳落成。

### 6.9 迁移的完整故事

- 迁移是一段降级 + 一段入列。**降级**：pi 的 31 命令、会话文件、事件形状全部收进 pi 适配器，壳从此只看到六条意图和中性事件——这一步 pi 上的用户无感，但「pi 是唯一底座」的特权没了。**入列**：dsh 适配器写好，dsh 作为一个新内核注册进壳，开新会话能选 dsh——这一步壳一行不改。两段走完，pi 和 dsh 平级，换内核 = 换适配器。故事的核心不是「dsh 终于能用了」，是「pi 终于成了一个普通内核」。

### 6.10 一句话收束

- 这篇文章从头到尾只立了一件事：pi 和 dsh 是同级的两个内核，壳对它们一视同仁，中立契约是唯一的地基。四个抽象、六条意图、三处泄漏、一张迁移表，都是这件事的展开。

- 立住这件事，靠的不是「说了几遍」，是每一处都问同一个问题：这个东西是「壳必须向每个内核索要的」吗？答得上，进契约；答不上，就是某个内核的专属，留在适配器里。这一问贯穿全文——它是「多内核壳」和「pi 的壳」之间那条真正的分界线。读完之后，如果「换内核 = 换适配器」从一句口号变成了一句有细节支撑的工程判断，这篇文章就写成了。

## 7. QA

- **Q：pi 有 `steer`、dsh 没有；dsh 的热切模型要补面、pi 现成——两边各有对方没有的东西，还算「同级」吗？**
  答：算。同级指的是「地位」（谁都不是内建、谁都能被换掉），不是「能力完全重合」。两边各有专属能力是正常的，契约只保证「壳需要的最小意图」两边都兑现；超出最小意图的能力，谁有谁用，没有的一方降级，这不影响地位。

- **Q：加了 dsh 之后，下一个内核（比如一个只有 LSP 的本地 agent）又会漏新形状，契约会不会永远补？**
  答：契约补不补，取决于「壳是不是必须向每一个内核索要它」。新内核漏出的如果是壳非必须的能力，就留在适配器里降级，不进契约；只有「壳真的需要、且每个内核都该有」的，才进契约。契约会变，但只往「壳的必要面」扩，不追着内核的专属形状跑。

- **Q：「地板」到底画在哪，谁说了算？**
  答：地板画在「壳必须中立」和「内核各自专属」的分界上，判据是 §3.3 那一问——「壳是不是必须向每一个内核索要它」。说它必须中立，是因为壳插件/渲染/布局这些机制层不能为某个内核改；说它留给内核，是因为文件树、append-only 日志这些是内核的价值本身，削平了就没内核可换。

- **Q：壳插件现在真的内核无关，还是「只遇到过 pi 所以看起来无关」？**
  答：是「看起来无关」。§1.2 已经点名：会话标识、事件形状、fork 语义三处还漏着 pi。真正的内核无关，要等这三处收进适配器、且 dsh 挂上来壳插件一个不改地跑，才成立。在此之前，它是「半解耦」。

- **Q：迁移期 pi 和 dsh 并存，一个会话能不能在两个内核间切？**
  答：不能。会话的数据边界是内核私有的（pi 是文件、dsh 是日志），一个会话永远只在一个内核下打开，内核归属记在会话头。切内核 = 开一个新会话，不是「把同一个会话搬过去」。

- **Q：适配器「缺面降级」时，壳插件会不会感知到差异（比如 dsh 下 `steer` 没了）？**
  答：会，但差异只体现在「那个能力不可用」，不是「内核身份泄露」。壳插件调 `steer` 得到「不支持」，它知道的是「当前内核没有多路并发」，不是「当前是 pi 还是 dsh」。如果某个壳插件非 `steer` 不可，那是它把自己的工作假设写死了，不是壳的问题。

- **Q：这份「架构层」文档和已有的 `base-interface-lineage.md`（实现层）是什么关系？**
  答：本文是「为什么」，`base-interface-lineage.md` 是「怎么做」。本文立住「内核/契约/适配器/壳」四个抽象和它们的地板；那份文档落的是具体机制（`BaseBackend` 五操作、`LineageTree`、`PiBackend`/`DshBackend` 两个适配器）。改实现层之前，先回来对齐本文的抽象，避免把内核专属的东西又写进契约。

- **Q：契约为什么不是「一条消息 + 一条事件流」两条，而是六条？**
  答：因为「消息」承载不了「中断」（中断要打断一条正在跑的消息，不是再发一条消息）、「分支」（fork 是会话结构，不是消息内容）、「模型」（切模型是配置，不是消息）。六条里，「消息/中断/分支/会话标识/流式事件/模型」各回答一个壳必须独立控制的问题，合不成更少；再多一条（比如 compaction），就有一条不是壳「必须向每个内核索要」的，该砍。

- **Q：适配器是「每个内核一个」，壳和适配器是一对多，壳怎么知道当前该用哪个适配器？**
  答：壳不「知道」是哪个适配器——壳只持有「当前会话的内核归属」这个不透明标记，发意图时按标记路由到对应适配器。壳的代码里没有「if pi / if dsh」的分支，只有「路由到当前内核的适配器」这一句。判断壳有没有漏内核身份，就看它有没有出现 `if 内核 === pi` 这种分支。

- **Q：如果 dsh 的 fork 有个约束 pi 也有（比如 boundary 必须是完整回合之后），这个约束进不进契约？**
  答：进，因为它对**两个**内核都成立——pi 只接受 user 锚点（一个回合的结束），dsh 拒绝落在回合中间，两者是同一个约束的两种表达。所以它是契约语义，不是内核细节。反过来，pi 的 before/at 两个 position 只有 pi 有，就是 pi 的扩展面，不进契约。判据还是那一问：这个约束是「每个内核都成立的通用语义」，还是「某个内核的实现细节」。

- **Q：多内核会不会让壳变复杂？壳插件会不会因此写得更难？**
  答：壳会多一层「路由」，但这一层只有一个职责（按内核归属路由到适配器），不会蔓延。壳插件不会更难——它们看到的还是那份契约，多内核不增加它们的 API 面，反而逼它们把「写死 pi」的假设改掉，写得更干净。真正变难的是适配器的作者：他要同时懂一个内核的专属形状和一份中立契约，两边都得精确。

- **Q：这份文档和「多后端」「多 provider」是一回事吗？**
  答：不是。「多 provider」是「同一个内核里换模型供应商」（pi 里换 Anthropic/OpenAI），那是内核内部的事，壳无感。「多内核」是「换整个 agent 运行时」（pi ↔ dsh），连会话怎么存、fork 怎么分叉、扩展怎么装都变了。前者是内核的一个配置项，后者是壳之下的一层替换。别把「换模型」和「换内核」混成一个概念——前者是 `setModel`，后者是换适配器。

- **Q：内核的「能力」和契约的「意图」是一回事吗？**
  答：不是。「能力」是内核**有什么**（pi 有 31 命令、dsh 有工具和能力缝），「意图」是壳**要什么**（六条）。能力是内核的内部事实，意图是壳的必要需求。两者靠适配器对上：意图能直接映射的能力，就是「直接映射」；意图在内核里找不到对应能力的，就是「缺面」。内核有一堆能力，壳只关心其中六条能对上。

- **Q：这份文档落地后，`base-interface-lineage.md` 要改吗？**
  答：不用改内容，只需对齐术语。那份文档里的 `BaseBackend` 就是本文的「中立契约」，`PiBackend`/`DshBackend` 就是「适配器」，`lineage` 就是本文定义的那个概念。它落的是「怎么做」，本文落的是「为什么和边界」——两份文档不冲突，是同一件事的两层。

- **Q：壳插件怎么知道当前内核支持哪些「扩展面」意图（比如有没有 `steer`）？**
  答：壳插件调它、内核不支持就收到「不支持」，这是「运行时探测」，不是「事前查询」。契约不承诺一个「能力清单」接口——因为那样壳又得知道「内核有几种能力」这种内核内部事实。壳插件的正确姿势是「有则用、无则降级」，而不是「先问再决定」。
