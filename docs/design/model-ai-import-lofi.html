v2 → v3 的纠偏

v2 把「收藏」理解成"把 AI 产出存成草稿卡片"——理解错了。 v3 对齐收藏插件（session-bookmarks）的机制：收藏 = 自包含快照（BookmarkSnapshot.lineage.entries = NeutralEntry[]）， 发起 = resume(snapshotId) → deriveSession（复制出新会话）→ materializeSession（seed 投影进内核）→ 跳转激活。 AI 导入就是同一串动作换内容来源：快照不是用户收藏的，是内核插件预制的分发资产（教程 + 开场白已经躺在 entries 里）。

「预制上下文」为什么用快照 entries 而不是 system prompt 注入

  • 教程作为快照里的真实 entry（user 角色）随 seed 物化进内核会话——AI 看到的上下文与用户看到的时间线完全一致（开场白就是 entry[1]，不是壳另画的气泡）。
  • 不碰内核 spawn 参数、不发明新的提示注入通道；「不入正常上下文」天然成立：模板只被 AI 导入的派生会话读取，任何正常会话的 seed 内容与它无关。
  • 教程按内核各一份（pi/dsh 的落盘差异、字段拼写、追问清单都写在自己的模板里）——内容归内核插件（内容层），派生/物化机制归壳（机制层），加第四个内核 = 加一份快照资产。

无联动（已拍板）

  • 产出 json 块只有「复制」（代码块复制是既有能力，可能零新增）；应用按钮/自动跳转/自动合并/草稿收藏卡片全部取消。
  • 取用路径完全手动且全部走既有功能：复制 → 设置 → 模型 → 导入（既有弹窗、既有合并语义）→ dirty → 保存浮层 → saveConfig。AI 导入功能自身不新增任何落盘通道。
  • apiKey：不做过滤（v2 的过滤决定随草稿卡片一起作废）——JSON 里带 key、贴进导入弹窗、随保存落盘，与手动导入的既有语义完全一致（pi 内联 / dsh 转凭证库）。

ephemeral（"只读模式"）的落点

  • 需要给 deriveSession/中立 header 加一个 ephemeral 标：列表过滤掉它；「✕ 结束导入」或切走时销毁（stop proc + 删 ~/.my-harness-desktop/sessions/<ns>.json + 内核侧投影按各内核临时会话语义处理——session-store 已有 test: 前缀 ephemeral 先例可参照）。
  • 对话照常（多轮粘贴/追问/修改）；「只读」指不持久、不进历史，与 v1 读法①一致。
