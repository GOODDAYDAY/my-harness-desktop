# 设计原则与坑点总纲

> 本文是 my-harness-desktop 的「设计原则 + 高频坑点」总纲，从三处真相源交叉提炼：
> **① 用户全部历史输入（176 个 session 逐条分析）② 真实代码与目录结构 ③ 1300+ 条 commit 历史**。
>
> 本文不是新造一套原则，是把散落在 CLAUDE.md、kernel-design-spec.md、008-thin-shell.md、
> plugin-isolation-principles.md 里的纪律，按「用户反复点名的坑点」重新组织成一张可对照执行的总表。
> 每条原则都回答三件事：**原则是什么 → 为什么（用户/架构依据）→ 违反时的坑点长什么样**。
>
> 术语口径以 `kernel-design-spec.md §4` 为准：**内核** = pi/dsh 运行时（同级），**壳** = 薄壳，
> **中立契约** = 壳向内核索要的最小意图，**适配器** = 内核形状 ↔ 契约的翻译层。旧文档里的「底座」「pi 底座」
> 一律读作「内核」，不再使用「底座」一词。

---

## 一、设计目标（这个项目要做成什么）

一句话：**内核无关的薄壳 + 壳插件生态**。

1. **内核无关的壳**：壳同时托管任意个同级内核（现在是 pi 和 dsh，将来可加第三个），
   **换内核 = 换适配器，壳和壳插件一行不改**。pi 和 dsh 谁也不比谁更「内建」。
   三条看着省力的路都是错的：继续 pi-only（拆了 dsh 的插件树只搬一个 adapter）、给 dsh fork 一份壳（槽位/渲染双份维护）、
   翻译层让 dsh 装 pi（让 dsh 重写 pi 的 31 命令/parentId 树，真长处全埋掉）。
   —— `kernel-design-spec.md §2`。

2. **薄壳**：壳的功能含量趋近于零，只有机制（加载器、槽位契约、权限沙箱、进程隔离、生命周期、事件总线），
   内容（文案/配色/管理页/渲染逻辑/业务分支）全部外挂给壳插件。极薄的功能含量 + 极强的机制保障（「薄不等于弱」）。
   —— `008-thin-shell.md`。

3. **洋葱架构**：依赖只向内。圆心（`packages/shared/src/domain` + `contract`）零依赖，只放类型和纯函数；
   外层逐层是会变的细节（协议、进程、内核实现、UI）。换 Electron/React/内核/存储，圆心一行不动。

4. **插件生态**：内置壳插件与第三方壳插件无特权差异，走同一套加载器/契约/权限，优先级最低、可被覆盖。
   （VSCode 是这套模型最成功的工业级样本。）

5. **高内聚 + 低耦合 + 开闭原则**：一个功能收进一个壳插件（及其内核侧扩展）整体交付，插件之间只走事件总线，
   新逻辑通过扩展（新插件/新槽位/新内核适配器）实现，不修改已有稳定代码。

## 二、设计理念（反复强调的价值观）

1. **机制与内容分离**：让功能能挂上来的机制留在壳，挂在上面的功能推给插件。拿掉它系统能不能启动 + 一年后会不会换——两条判据。
2. **依赖只向内（洋葱的根）**：外层可依赖内层，内层绝不依赖外层。不解释、不通融、没有例外。
3. **高内聚**：同一件事只在一处。一个功能的 UI、i18n、pi 内核扩展、dsh 内核扩展收进**同一个 plugin 目录**。
4. **低耦合**：插件之间不共享 store 互读写、不直读对方文件，唯一通道是事件总线。
5. **开闭原则**：对扩展开放（加插件/加槽位/加适配器），对修改关闭（不碰稳定内核与已有插件）。
6. **契约单源**：一个概念只有一份定义，外层 re-export，永不复制一份「本地版」。
7. **消费而非翻译**：主动消费内核吐出的结构化数据自己画 UI，不造「内核 UI 翻译层」。
8. **构造与执行分开**：怎么拼（Assembler）和怎么发（Gateway）两件事，一个函数既构造又执行就是坏味道。
9. **框架管通用，特化归外层**：多调用方共用的逻辑收进框架（壳），差异只在参数；行为级差异才各自保留。
10. **完整设计一次落地**：先设计终态，再一步做完；拒绝「方案菜单里混补丁」「步骤切片交半成品」。
11. **根因修复不打补丁**：改完能说清根因是什么、为什么之前会触发、为什么改完不再触发。
12. **设计先行 + 提交即文档**：文档驱动代码；每个 commit 自解释（改了什么/为什么/架构依据/运行时验证）。

## 三、二十条原则（编号，可对照执行）

### 原则 1 · 依赖只向内（洋葱架构）

外层可以依赖内层，内层绝不依赖外层。`domain`/`contract` 里出现 `electron`/`better-sqlite3`/`react`/内核实现 import 即红线。

**坑点**：内层 import 了外层包 → 依赖方向反了，换外层要动内层，冲击波从外向内炸。业务函数里直接出现 spawn/fetch/ORM → 业务核心被基础设施污染。
**用户原话**：「看下 ../git-project/deepseek-harness 里的 fork 之类的功能，这个写的太好了，为啥 desktop 这边，写的就是一个垃圾呢」。

### 原则 2 · 圆心零依赖 + 契约单源

圆心只放类型定义和纯函数，零依赖。类型（`KernelId`/`BaseBackend`/中性事件/模型/配置）在圆心定义一次，外层 re-export。
内核身份 `"pi" | "dsh"` 只允许 `domain/kernel.ts` 一处定义。

**坑点**：两个文件出现同一概念的两份定义 → 从第一天开始漂移。`"pi" | "dsh"` 散落全仓 60+ 处 → 在圆心之外复制联合类型。
**反模式**：`if (provider.includes("deepseek")) kernel = "dsh"`——内核身份由 provider 名反推，而不是由「从哪个内核的配置扫出来」赋值。

### 原则 3 · 机制与内容分离（薄壳）

壳零功能含量：不出现写死的颜色 hex、写死的用户可见文案、针对具体内核/业务类型的 if-else 分支。
token key 合规（`t("shell.settings")`），token 值违规（`"#89b4fa"`、`"设置"`）。

**坑点**：把文案/配色焊死进壳 → 每次改配色/文案都要动壳、发版、全量回归。
**检验**：打开壳任何文件，找到一处写死颜色/文案/业务分支即违规。删掉 i18n 插件，界面文案退化成 key 原文——这是设计，证明壳没内嵌文案。

### 原则 4 · 无特权差异

内置壳插件与第三方壳插件同一套加载器/契约/权限，优先级最低、可被覆盖。pi 与 dsh 同级，谁也不比谁更内建。

**坑点**：壳出现「识别内置件并特殊对待」「识别 pi 并特殊对待」的代码路径 → 多一套加载逻辑、多一条特权分支，每条都是 bug 温床。
**检验**：删掉任一内置插件壳照常启动；复制到用户目录以更高优先级覆盖；禁掉 dsh 壳照常启动只是少了 dsh 的能力。

### 原则 5 · 多内核默认：内核先抽象、后实现

任何涉及内核的开发，第一步先问「壳要的是一个什么抽象」，把抽象落进中立契约（`BaseBackend`/`SessionCatalog`/`KernelModelSource`），
第二步才想 pi/dsh 怎么实现。内核永远是抽象的一个实现，不是抽象本身。

**坑点**：把某个内核的实现细节写进壳或圆心 → 违反「内核可替换」根。换掉任一内核、加第三个内核，壳和圆心必须一行不改。
**判别气味**：会话意图链路上出现 `if (kernel === "pi")` 或 `asPi()` 类型守卫 → 壳在漏内核身份。理想是 `backend.capabilities.pi` 能力探测。

### 原则 6 · 壳的三条内核无关不变量

1. 壳不读任何内核的存储（pi 的 JSONL、dsh 的 log 都不碰，只认不透明 `sessionId`）。
2. 壳只认中性事件（内核事件由适配器投喂成中性事件）。
3. 壳的渲染是纯函数（给定同一条中性事件流，timeline 怎么画与内核无关）。

**坑点**：违反任何一条，壳就偷偷依赖了某个内核。会话意图链路上出现 `if (kernel === "pi")` 即一处泄漏。
**用户原话**：「统一扫一下全局，看下哪些是泄漏，直接从其他的 domain 请求到了 pi 或者 dsh 内核？而没有经过 kernal 层抽象」。

### 原则 7 · 能力拉平三分法：适配器翻译 → 内核补面 → 显式降级

壳看到 pi/dsh 的差异，三条出路按优先级：① 有「同一个语义、只是形状不同」→ 适配器翻译；② 形状翻译不了的能力缺失 → 内核插件补面
（pi 侧 TS 扩展，dsh 侧 Cordis 插件）；③ 补不了 → 显式降级（入口隐藏/置灰 + tooltip），不静默、不伪造成功。

**坑点（唯一不允许的状态）**：静默缺面——壳调了内核没有的能力，既不翻译、不补面、不降级，静默吞掉或假装成功。
**高频实例**：dsh 缺 `setModel`/`fork`/`setSessionName` 时曾反复「缺面抛错打断发送」，正确做法是缺面 no-op/降级，且**重装内核后缺面补丁不再丢**（桌面随附补丁持久化）。

### 原则 8 · 高内聚：一个功能 = 一个 plugin，内部四件套

一个功能收进**同一个壳插件目录**，内部按需分四件：
- `locales/`——i18n 文案（desktop UI 文案）
- `renderer/`——desktop 壳插件（UI 组件 + 槽位贡献 + 事件）
- `pi-extension/`——pi 内核插件（给 pi 内核补能力的 TS 扩展）
- `dsh-extension/`——dsh 内核插件（给 dsh 内核补能力的 Cordis 插件）

**这是用户反复强调的「尽可能集中」**：一个功能的所有内核侧适配都内聚在这一功能自己的 plugin 下，而不是散落到壳的内核层。
参考实现：`src/plugins/sessions/goal/`（`renderer/` + `pi-extension/` + `dsh-extension/` 三件齐全）、
`src/plugins/insight/llm-recorder/`（`core/` + `renderer/` + `pi-extension/` + `locales/`）。

**坑点（用户点名「非常愚蠢」）**：新写插件时去改动 desktop 的内核（壳）来容纳这个插件——这是把会变的内容焊进壳，破坏薄壳。
正确方向是「尽可能集中」到插件自身；有细节出入可以，但方向是这个。

### 原则 9 · 非必要不修改薄壳内核；要改动，首选改对方插件

**默认不改壳的内核**。确需改别人功能时，首选「改对方插件」，而不是动壳：比如要扩展会话流 UI，
是「会话流插件（timeline）提供槽位，本插件去填槽」——动的是对方插件和本插件，动不到壳的核心内核。
文件列表（file-tree）、会话列表（sessions-list）同理：它们本身就是薄壳插件，别的插件往里填槽，而不是改壳。

**坑点（用户原话）**：「薄壳架构，那新写插件的时候，那就不能去改动 desktop 的内核啊，这个思路就非常愚蠢……
我承认，有时候要改动别的，那应该首选改动其他插件，比如会话流插件的 UI，对方插件提供槽位。本插件去填槽，那也动不到核心内核啊。
非必要不修改薄壳内核。还比如别的文件列表啥的，也是一样，是人家也是薄壳插件，然后别的插件去往里填。」

### 原则 10 · 低耦合：插件间只走事件，不共享 store 互读写

插件之间唯一合法通道是 `ctx.events.emit/on`。不通过共享 store 互读写、不直读对方配置文件、不经 `window.kernel` 直调对方能力。
共享 store 允许插件「读」框架状态，禁止调 setter——setter 只归框架。要改变框架状态走 ctx API。

**坑点**：timeline 写 `useUiStore().requestBookmark()`、session-bookmarks 读它——隐式握手，无依赖声明、payload 形状两处手写、改一边漂移。
**反模式**：`dependsOn` 声明缺失时，删掉被依赖插件，依赖方静默读到空对象而不是报错「缺依赖」。

### 原则 11 · 零硬编码

插件代码不允许出现 plugin ID、component 注册名、slot contribution ID、配置文件路径、**内核身份**的字符串字面量。
pluginId 由 `PluginIdContext` 自动注入，component 名由框架从 manifest 自动匹配，slot 可见性由框架传 `isActive` prop，
配置路径由框架按 pluginId 推导，内核身份由适配器/框架抹平。唯一的例外是事件 channel 名——它是发布方的对外契约（类比 API 签名）。

**坑点**：`const PLUGIN_ID = "blind-review"` 和 manifest `"id"` 手写两遍，改一处忘一处 → 运行时静默失败。

### 原则 12 · API 单入口（usePluginContext，不直访 window.kernel）

插件只经 `usePluginContext()` 拿受控 API（pluginId 绑定层 / 系统级 API 层 / 事件层），不直访 `window.kernel`，不 `usePiApi()` 拿裸对象。

**坑点**：直访 `window.kernel.sessions.copySession()` 绕过 pluginId 绑定和权限校验——IPC 边界拿到裸调用，不知道调用方是谁，权限校验形同虚设。
**反模式**：6 个插件 26 处直访 `window.kernel.*`——全是这条原则的违反现场。

### 原则 13 · 构造与执行分开

一个函数既构造又执行（既拼命令又 spawn、既拼请求又 fetch）就是坏味道。拆成：一个返回构造结果，一个接收构造结果并执行。

**坑点**：`sendCommand` 里既拼 JSON 又写 stdin 又等响应又解析 JSONL——改格式/改写入/改超时/改解析都要动同一个函数。

### 原则 14 · 框架管通用，特化归外层

多调用方共用的逻辑（save/dirty/reset、组件注册、pluginId 注入、事件 channel 注册、样式、语言、配置通道）收进框架统一承担，
调用方只传参数。差异是「参数级」就收敛，是「行为级」才各自保留。

**坑点**：几十个设置页插件各写一份 save/dirty/拦截逻辑——同一逻辑几十份复制。pi/dsh 的会话模型/事件形状/fork 语义处处相反，
这些行为级差异硬塞进基类共享 = 错误收敛。

### 原则 15 · 依赖倒置连通内外

接口定义在内层，实现在外层，启动期注入。`session-store` 持 `BackendFactory` 接口而非 `new PiBackend()`；
`KernelManager` 持 `KernelRuntime` 接口而非直接 `spawn("npm")`。内层不直读 `process.cwd()`/`process.env.HOME`，路径由外层注入。

**坑点**：`session-store` 直接依赖 `ModelsStore`（core→client 依赖）——已作为专项修复「core→client 归零」。
**用户原话**：「统一扫一下全局，看下哪些是泄漏，直接从其他的 domain 请求到了 pi 或者 dsh 内核」。

### 原则 16 · 继承 + 实现：接口 → 抽象基类 → 具体实现

「接口 + 两个平行实现」的重复代码（缺面抛错、装/查机制）用「接口 → 抽象基类 → 具体实现」三段式收敛：
`BaseBackend`（契约）→ `AbstractBackend`（骨架 + 缺面默认）→ `PiBackend`/`DshBackend`（override 差异）。
基类只 import `core/domain`，绝不 import 具体内核；子类只填差异；组装归 bootstrap。

**坑点**：pi/dsh 各写一份「缺面抛错」「装/查机制」——重复代码两份漂移。不预支：等真有第二个内核共享的编排才往基类加模板方法。

### 原则 17 · 手写收敛到成熟包

版本比较（semver）、类型解析（TS Compiler API）、拖拽、右键菜单、深合并（deepmerge）、UUID——成熟包千锤百炼，收敛掉。
自己写的每一行都是背的债。

**坑点**：字符串字典序比较版本会误判 `0.10.0 < "0.9.0"`；正则解析 `.d.ts` 在嵌套/extends/联合面前脆弱不堪。

### 原则 18 · 事件驱动，不轮询不 sleep

用事件驱动替代轮询和固定延迟。组件只读 store、零拉取，基线 + 事件增量应用。冷启动不 sleep 猜就绪，而是向内核发探测命令以结果为准。

**坑点**：固定 sleep 是对时序竞争的赌注，赌输就是偶发 bug 永远复现不了；组件各自 useEffect 拉数据 = 同一数据拉三遍。

### 原则 19 · 根因修复，不打补丁

定位真因再修，每个 fix 标注根因（哪个闭包旧值/时序竞态/useEffect 没重跑/IPC 监听器没返回清理）。
治标 = 改完能跑但说不清为什么；治本 = 说清根因 + 为什么之前会触发 + 为什么改完不再触发。

**坑点（用户点名反复犯）**：「为啥我修改了模型后，点击表情包发送，是修改模型前呢？这个发起，难道是自己写的？
我说了一万遍了。要等效点击发送按钮才行，怎么总是不等效呢？」——表情包/附件发起绕过了统一发送路径，属于「自写发起」而非「等效点击发送」。

### 原则 20 · 会话列表是壳的唯一源数据，同步给内核

壳拥有自己的会话列表作为**唯一源数据**，通过同步方法同步给内核（pi/dsh），而不是反过来让内核持有会话列表、壳去读内核。
这是「壳不读内核存储」在会话列表上的具体形态。

**坑点（用户点名）**：「我不理解啊，session list，不是壳子上的吗？你到底是否理解，壳子有要有自己的 session 列表作为唯一源数据，
然后通过同步方法，同步给内核这个核心设计？」——把 session list 做成内核的投影/读内核，是 pi-only 惯性 + 泄漏。

### 原则 21 · 等效点击发送（统一发起路径）

表情包、附件、任何 UI 入口发起会话，必须走**与点击发送按钮完全等效**的统一发起路径，
不能「自写一套发起逻辑」。自写发起必然与发送按钮的模型/参数/时序不同步，出现「发的是修改模型之前」。

**坑点**：见原则 19 的用户原话（「我说了一万遍了」）。这是「构造与执行分开 + 统一入口」在 UI 发起层的具体表达。

### 原则 22 · 不兜底、立即报错；内核身份跟随模型

「兜底」是被用户点名「兜底你妈呢」的反模式——把兜底模型、默认内核、默认模型**全删掉**，缺了就**立即报错**，绝不静默回落。
内核身份是**模型的派生量**：用户选哪个模型，就进哪个内核，选择时内核即已知——不存在「默认内核」，也不需要「反查」。
`ModelInfo.kernel` 由「模型从哪个内核的配置扫出来」决定，不由 provider 名反推。
`refreshThinkingLevels`/`abortRetry` 等 pi 专属能力在非 pi 内核下要门控（非 pi 不拉取/回落中性实现）。

**坑点（用户原话）**：「为啥要有默认内核？……为啥要兜底，兜底你妈呢？把兜底啥的，全删了，要立即报错，怎么能兜底呢？」
「我他妈说了一万遍，要根据选择模型去判断用啥内核，用啥模型」「我在选择的时候，难道还不知道内核？为啥要反查？」
「你告诉我，deepseek 模型，就一定是 dsh 吗？你告诉我，你他妈告诉我！！！」——deepseek 模型 ≠ 一定走 dsh 内核。
**反模式**：`if (provider.includes("deepseek")) kernel = "dsh"` 是错的；「兜底永远回落 pi」是 pi-only 惯性。

### 原则 23 · 多内核会话/模型切换全对称

模型切换要支持 pi↔dsh **来回切换**，模型选择经 `ModelCatalog` 反查内核（不是「在 pi 上切 dsh 的模型」），
会话页在切换内核时带过渡动画、图标跟随内核切换。会话启动、模型握手、事件流在两种内核下行为一致。

**坑点（用户点名反复犯）**：「模型切换失败：Model not found……就是会话流这里，我必须得支持各种来回切换呀，
比如之前是 pi，然后切到 dsh，你会在 pi 上切换」——切换目标是旧内核而非目标内核。
「我很伤心，这么久了，我就没有在会话页，成功发起 dsh 的请求一次」——dsh 会话发不出去。

### 原则 24 · 开闭原则（对扩展开放、对修改关闭）

新逻辑通过「加一个壳插件 / 加一个内核适配器 / 给缺面内核加一个内核插件」实现，不修改已有稳定代码。
这是薄壳 + 多内核 + 插件化的合流：扩展的载体是插件和适配器，不是给壳打补丁。

**坑点**：每加一个功能就改一次壳 → 壳从薄变胖，特权分支累积。正确做法是「对方插件提供槽位，本插件填槽」（原则 9）。

### 原则 25 · 设计先行 + 设计文档盲审（终态一致、无自相矛盾）

先写设计文档再搭骨架再填代码；设计文档是真相源。写完后做**盲审**（clean-room reviewer）：
以真实代码为真相源核对「文档说了但代码不是那样」「文档自相矛盾/术语漂移/读者定位不到唯一判据」。

**坑点（用户点名）**：「看下所有的设计文档，整体扫一遍，再盲审几遍，所有的……结合起来扫，看下有没有什么矛盾冲突，不对的地方」——
设计文档之间/与代码之间漂移（术语「底座 vs 内核」、判据「空会话/无内容/有历史」多套说法）是反复被点名的坑。
机械清扫有固定术语规则：「底座」→「内核」；「内核」当指壳机制 → 「壳」。

### 原则 26 · 内核身份不进配置文件；能力探测而非身份硬分支

`ModelInfo.kernel` 由「从哪个内核的配置扫出来」赋值，不由 provider 名反推；会话意图链路上用 `capabilities` 探测（有则用、无则降级），
不用 `if (kernel === "pi")` 硬分支。内核身份、模型类型、事件类型、配置类型、lineage 类型全部从圆心发出。

**坑点**：`if (provider.includes("deepseek")) kernel = "dsh"` 是错的；会话链路上 `asPi()` 类型守卫是泄漏。

### 原则 27 · 进程不泄漏（每次调用不泄漏内核进程）

`getTree`/`bookmark`/`deleteBookmark` 这类读操作要走 catalog（会话目录），不能每次调用都 spawn 一个 pi 进程（进程泄漏）。
内核子进程的生命周期由壳统一持有/回收，读操作是纯目录查询，不拉起进程。

**坑点**：「getTree/bookmark/deleteBookmark 改走 catalog，杜绝每次调用泄漏 pi 进程」——曾经每次调用都泄漏一个 pi 进程。

### 原则 28 · 安装/升级诚实：不「假安装成功」

内核/插件安装要么真失败、要么真成功，不允许「假安装成功」。覆盖式安装要清旧 `node_modules`+lock（堵 ERESOLVE），
版本走正确的 dist-tag（next 而非 latest 陈旧依赖），安装后验证连通性（模型测试）。

**坑点（用户点名）**：「为啥 dsh 的安装，每次都要重新安装？这里问题很大啊，要么一直安装不上，要么安装成功，
怎么能一直假安装成功呢？」「dsh 的模型配置里的测试，从来没成功过？写了多久了？」——安装状态/测试结果不诚实。

### 原则 29 · 提交即文档

每个 commit 自解释：改了什么、为什么改、架构依据、运行时验证。反例是 `fix bug`/`update`/`tmp`。

**坑点**：commit 只有「fix bug」→ 三个月后没人记得改了什么、为什么改，只能考古。

### 原则 30 · 冷启动引导时序（前端入口可独立起）

`window.kernel` 引导、WS hello 帧序、Tailwind 源路径、数据根路径，这些启动期时序要事件驱动、不靠模块级副作用，
数据根路径不依赖 electron（node 服务器可独立起）。前端入口（Vite）不是独立应用，需 dsh web 注入 `window.__DSH_BOOT__`。

**坑点**：组件模块级读 `platform` → 黑屏；WS hello 帧序竞态 → 加载不出；`window.pi → window.kernel` 改名后 demo 脚本未同步。

### 原则 31 · 给内核补能力 = 写插件/扩展，严禁修改外部内核仓库

要给 pi 补能力，写 pi 扩展（TS 扩展装进 `~/.pi/agent/extensions/`）；要给 dsh 补能力，写 dsh 的 Cordis 插件/扩展。
**严禁修改 deepseek-harness 等外部仓库的核心**——内核的能力缺口用「内核插件」补齐，而不是去改对方仓库。

**坑点（用户原话，出现 ≥6 次）**：「本次修改，不可能需要修改 deepseek-harness」「严禁严禁写 ds-harness 仓库」
「不要动 dsh，没不让你写扩展啊？冲突吗？」「这个还得改内核？能不能改成 dsh 插件的形式去搞？」
**反模式**：把 goal/续跑/setModel 缺面做成「改内核」，而不是「写内核插件」——「为啥要修改到内核呢？我理解应该是纯插件修改呀？」
正确落地：pi 侧合并成统一 `my-harness-fit-pi-extension`，dsh 侧合并成统一 `my-harness-fit-dsh-extension`，随 desktop 分发。

### 原则 32 · 统计是壳子自己的事，与内核无关

轮数、step 数、token、上下文占用这些**统计量由壳从中性事件自己算**，不向内核要统计。
内核只负责吐中性事件（消息增量/工具调用开始结束），壳拿同一份事件流做统计——两种内核下统计逻辑完全一致。

**坑点（用户原话）**：「这个是都是壳子自己的事情，这些数据啥的，都是壳子能统计的，本质上跟内核无关」。
**反模式**：`getStats()` 里 `this.asPi(proc).getSessionStats(...)`——统计投递只走 pi 路径（asPi 泄漏），dsh 实时统计整块为空。

### 原则 33 · 配置层统一 JSON 出入：get/set 两原语

内核配置的契约收窄为 **JSON 出入**：出参入参都是 JSON、字段通用化、更新也是 JSON 出入，砍到只剩 `get(): JSON` / `set(JSON): JSON`。
每个内核自己维护自己的信息、吐给 kernel 层；不搞跨内核「共享配置」，配置 TAB 退化成通用 JSON 编辑器（或只留「打开原始文件」）。

**坑点（用户原话）**：「这些全该砍成只剩 get(): JSON / set(JSON): JSON」「应该是两个内核，自己维护自己的信息，然后吐给 kernal」
「我不理解，为啥 dsh 的其他字段，里面都是 json？这个太扯了」——配置展示把整段 JSON 甩给用户而非字段化。
**反模式**：为「默认内核」新增独立配置项（默认内核应从默认模型推导，不该新造配置）。

### 原则 34 · 展示类数据（图片等）由壳的 kernel 层统一维护，同步时过滤

图片、展示附件等**纯展示数据由壳的 kernel 层统一维护**，不进入内核会话文件（pi 的 JSONL）；同步给内核发起时可直接过滤，不发送给 AI。
分叉 = 完整复制（含展示数据），fork 的是 kernel 层的版本再拿去内核发起。

**坑点（用户原话）**：「kernal 已经负责所有的展示了……这些 imag 啥的，应该是纯 kernal 维护。然后传递给 pi 的时候，甚至它可以直接过滤了」
「分叉，怎么 custom 的 img 没有分叉出去？你这个还不是复制？」——图片存 `session-images.json`（不在 JSONL），只复制 JSONL 时分叉产物自然丢图，「这个根因就很坏」。

### 原则 35 · 前后端分离 + 目录整洁 + 项目只存代码

物理目录第一层就是 `server/`（后端）+ `web/`（前端）+ `plugins/`（内容）+ `packages/`（发布面），共享契约收进 workspace 包（`packages/shared` 的 domain/contract）。
**项目仓库只存代码**：坚决杜绝提前编译安装的中间产物（node_modules、dist、编译产物），历史 commit 里的中间产物全部清理。
包结构不能「太平」——每层要么只放文件夹、要么只放文件。

**坑点（用户原话）**：「直接从代码上，就要分成前端后端吧，我感觉我没有在你的目录结构里，看出来你是一个前后端分离的项目」
「前后端分离顶到第一层，共享契约收进 workspace 包」「作为项目，肯定是只保存代码啊……坚决杜绝提前编译安装」
「整体的包不能太平……要么只放文件夹，要么只放文件」。

### 原则 36 · 开发节奏硬纪律：只读模式先行 + 盲审 + commit + worktree 闭环

动手前先「只读模式」出方案（先分析、给方案，不直接改）；写设计文档后「盲审」几轮（clean-room reviewer 找矛盾/漂移/可落地性问题）；
每步 `commit`（提交即文档）；代码修改走「标准 worktree 工作流：建 worktree → 改 → 验证 → commit → 合并回 main → 清理中间产物」。

**坑点（用户原话，高频）**：「只读模式」≥6 次、「记得盲审几遍」≥8 次、「commit 一下」≥15 次、
「标准 worktree 工作流，合并回 main 分支，然后清理中间产物」≥8 次。
**反模式**：拿用户当测试——不亲自验证就交付、反复「假成功」；「根本就不行啊，你这成了在拿我当测试了，你自己他妈的都不测是否成功的」。

### 原则 37 · 对标先行者，1:1 复刻现成实现，别重复造轮子

写 pi 的能力先抄 dsh 现成实现（或反之），「PI 珠玉在前」就 1:1 复刻。UI 不只是功能等效，**界面也要等效**。
框架已有现成机制（save/dirty、打开原始文件、导出配置）就复用，不重写一套。

**坑点（用户原话）**：「现在 dsh 的实现，我很满意，所以我希望要新增 pi 的插件，就是复制 dsh 的，去看怎么抄合适」
「PI 珠玉在前，很棒啊，你为啥不 1:1 复刻呢？」「我理解 PI 和 DSH 的模型设置，应该是等效的……不只是功能等效，UI 界面也要等效」
「框架有现成的，你妈呀」「这个打开原始文件，就很蠢你知道吗？我本来就已经有相关的机制了，但你还是重新写了一个」。

## 四、高频坑点清单（用户反复点名的「不对的地方」）

> 每条 = 「坑」+「根因」+「正确做法」+「用户原话」。这些是跨 session 反复出现、被用户点名「说了多少遍/又是这个/垃圾」的地方。

1. **pi-only 惯性**（出现 N≥3 次）：从 pi-only 迁到 desktop + pi + dsh 后，残留的 pi 专属路径——兜底永远回落 pi、
   `window.pi` 直访、`if (kernel==="pi")` 分支、思考档位不门控、session list 读内核。根因：迁移没做「泄漏扫描」。
   正确：能力探测 + 门控 + 泄漏扫描（`core→client 归零`、`每次调用不泄漏 pi 进程`）。
   用户原话：「从 pi-only 转到 desktop + pi and dsh 之后，有好多之前到 pi-only 的惯性，这个不好，你研究研究，都有啥惯性还在现在」。

2. **会话流模型/内核来回切换失败**（出现 N≥5 次）：`Model not found`、在旧内核上切新内核的模型、切换后图标不变、
   发 dsh 请求从来没成功过。根因：模型路由没经 `ModelCatalog` 反查内核、切换目标写死旧内核、dsh setModel 缺面。
   正确：`setModel 跨内核路由`（`ModelCatalog` 反查）+ `setModel 透传 initialize 握手` + 缺面补丁持久化。

3. **dsh 假安装成功 / 测试永远失败**（出现 N≥3 次）：安装装不上或假装装上、模型测试从来没成功过。
   根因：安装状态不诚实、空 provider 路由毒化、密钥按 provider 注入竞态。正确：覆盖式安装清旧依赖 + 连通性实测 + 失败显式报错。

4. **表情包/附件发起 ≠ 等效点击发送**（出现 N≥3 次）：发了修改模型之前的内容。根因：UI 入口自写发起逻辑，绕过统一发送路径。
   正确：所有发起入口收敛到「等效点击发送」的唯一路径。

5. **session list 不是壳唯一源数据**（出现 N≥2 次）：被做成读内核/内核投影。正确：壳持有会话列表唯一源数据，同步给内核。

6. **静默缺面 / 缺面打断发送**（出现 N≥5 次）：dsh 缺 `setModel`/`fork`/`setSessionName`/`setThinkingLevel` 时抛错打断发送、
   重装内核后补丁丢失。正确：缺面 no-op/降级 + 桌面随附补丁持久化 + 能力探测守卫。

7. **壳内写死文案/颜色/业务分支**：壳出现具体颜色值、中文文案、`if (tool==="bash")`。正确：token key 进壳，值进主题/i18n 插件。

8. **插件硬编码 + 直访 window.kernel + 共享 store 互读写**：`const PLUGIN_ID`、`window.kernel.*`、`useUiStore().requestBookmark()`。
   正确：零硬编码（Context 注入）+ API 单入口 + 事件唯一通道（见 `plugin-isolation-principles.md`）。

9. **设计文档自相矛盾 / 术语漂移**：同一判据多套说法（空会话/无内容/有历史）、「底座 vs 内核 vs 壳」三词混用、
   文档说的和代码做的不一致。正确：术语单源 + 盲审（clean-room reviewer）+ 机械清扫规则 + 文档=代码双向核对。

10. **冷启动时序竞态 / 黑屏**：模块级读 platform、WS 帧序竞态、Tailwind 路径漂移、`window.pi→window.kernel` 改名漏改。
    正确：事件驱动引导、入口注入、改名后全局 grep 同步。

11. **泄漏 pi 进程 / core→client 依赖**：每次读树/收藏/删书签都 spawn pi；session-store 直接依赖 ModelsStore。
    正确：读操作走 catalog、依赖倒置、`core→client 归零`。

12. **面包屑/UI 细节回归**：面包屑压 mac 红绿灯（platform 归一化回 `process.platform` 约定）、归档按钮失效、
    图片下方多余 title 行。正确：platform 归一化单源、功能按钮做 e2e 验收回归。

13. **修改外部内核仓库 / 改内核而非写插件**（出现 ≥6 次）：给内核补能力时去改 deepseek-harness / dsh 内核，而不是写扩展。
    正确：写 pi 扩展 / dsh Cordis 插件，合并成统一 fit-extension 随 desktop 分发，绝不改对方仓库核心。
    用户原话：「严禁严禁写 ds-harness 仓库」「这个还得改内核？能不能改成 dsh 插件的形式去搞？」「为啥要修改到内核呢？我理解应该是纯插件修改呀？」

14. **拿用户当测试 / 没测过就交付 / 假成功**（出现 ≥3 次）：不亲自跑一遍就交付、功能点没测过（providerId 删不掉）、
    测试永远失败还不展示错误。正确：交付前亲自点一遍、连通性实测、失败显式报错。
    用户原话：「根本就不行啊，你这成了在拿我当测试了，你自己他妈的都不测是否成功的」「providerId，根本就删不掉你知道吧，你自己都没测试过」
    「测试就是不过啊！！然后超时，还不展示错误！！」

15. **契约单源漂移**：同一概念两套接口——domain 的 `PiExtensions`（16 方法）与 client 的 `PiBackendExtensions`（24 方法）并存，
    bookmark 路径规则在 session-store 与 pi-backend 各留一份。正确：圆心定义唯一源，外层 re-export，删掉副本。
    用户原话：「pi 扩展有两套接口……这是契约单源上的漂移风险点」「我感觉这个不是很对」。

16. **文档与实现矛盾（dependsOn 加载顺序等）**：文档说 dependsOn 拓扑排序控制加载顺序，CLAUDE.md/实现说「生命周期护栏，不控制加载顺序」；
    fork 返回类型文档写 `Promise<string>`、代码是 `Promise<ForkResult>`；插件 tier 三级 vs 四级。正确：文档=代码双向核对，以真实代码为准。
    用户原话：「都声称 dependsOn 做拓扑排序控制加载顺序；CLAUDE.md §8.2 说……没实现好感觉」「fork 返回类型错……Promise<ForkResult> 合理」。

17. **发现机制不通用 / 各内核各写一套**：skills/tools/i18n 的发现机制应由壳统一搞一层，而非 pi、dsh 各写一套。
    正确：壳统一发现层（递归扫描 + manifest 声明），内核侧缺的用插件补。
    用户原话：「我要求发现机制，都是要壳子搞一层，你咋能不通用呢？」「pi 的就不改了？」

## 五、插件开发的一条总纲（背下来就能少踩坑）

> 把上面的原则压成一段可背的行动纲领：

**新写一个功能，永远按这个顺序想：**

1. 先想「这个功能是一个**独立的壳插件**吗？」——是，就收进 `src/plugins/{domain}/{feature}/`，一个 plugin 一个功能。
2. 插件内部按需四件套：`locales/`（文案）+ `renderer/`（desktop UI）+ `pi-extension/`（pi 内核补面）+ `dsh-extension/`（dsh 内核补面）。
3. **绝不为了这个插件去改壳的内核**（薄壳不可动），**也绝不改外部内核仓库**（deepseek-harness / dsh 核心，只写扩展不写对方核心）；
   需要内核侧能力，用内核插件（pi-extension/dsh-extension）补，或用「有则用、无则降级」探测。
4. 要改别人的功能 → **首选改对方插件**：对方插件提供槽位，本插件去填槽（timeline/file-tree/sessions-list 都是薄壳插件，往里填）。
5. 插件只从 `usePluginContext()` 拿能力，零硬编码、不直访 `window.kernel`、不共享 store 互读写，插件间只走事件。
6. 高内聚、低耦合、洋葱架构、薄壳架构、开闭原则——每一条都在这五步里。

**一句话**：*壳是机制、插件是内容、内核是被适配的能力；改功能 = 改/加插件或适配器，永远不动壳的圆心。*
