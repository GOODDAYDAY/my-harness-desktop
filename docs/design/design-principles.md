# 设计原则与反模式总纲

> 本文是 my-harness-desktop 的「设计原则 + 反模式」总纲，从三条真相源交叉提炼：
> **① 用户全部历史输入（176 个 session 逐条分析）② 真实代码与目录结构 ③ 1300+ 条 commit 历史**。
>
> 本文不是新造原则，是把散落在 CLAUDE.md、kernel-design-spec.md、008-thin-shell.md、
> plugin-isolation-principles.md 里的纪律，重组成一份**可被 AI 识别与自检**的对照表：
> 每条原则都落成「原则陈述 → 判别气味（可 grep / 可当场判）→ 反模式 → 正确做法」四段。
> 阅读时可直接把「判别气味」当作 lint / code review / 盲审的检查项。
>
> 术语口径以 `kernel-design-spec.md §4` 为准：**内核** = pi/dsh 运行时（同级），**壳** = 薄壳，
> **中立契约** = 壳向内核索要的最小意图，**适配器** = 内核形状 ↔ 契约的翻译层。
> 历史文档中的「底座」「pi 底座」一律读作「内核」，不再使用「底座」一词。

## 一、设计目标

一句话：**内核无关的薄壳 + 壳插件生态**。

1. **内核无关的壳**：壳同时托管任意个同级内核（现在是 pi 和 dsh，将来可加第三个），
   **换内核 = 换适配器，壳和壳插件一行不改**。pi 和 dsh 同级，谁也不比谁更「内建」。
   三条错误路线：继续 pi-only（拆了 dsh 的插件树只搬一个 adapter）、给 dsh fork 一份壳（槽位/渲染双份维护）、
   翻译层让 dsh 装 pi（让 dsh 重写 pi 的 31 命令/parentId 树，真长处全埋掉）。
   —— `kernel-design-spec.md §2`。

2. **薄壳**：壳的功能含量趋近于零，只有机制（加载器、槽位契约、权限沙箱、进程隔离、生命周期、事件总线），
   内容（文案/配色/管理页/渲染逻辑/业务分支）全部外挂给壳插件。极薄的功能含量 + 极强的机制保障（「薄不等于弱」）。
   —— `008-thin-shell.md`。

3. **洋葱架构**：依赖只向内。圆心（`packages/shared/src/domain` + `contract`）零依赖，只放类型和纯函数；
   外层逐层是会变的细节（协议、进程、内核实现、UI）。换 Electron/React/内核/存储，圆心一行不动。

4. **插件生态**：内置壳插件与第三方壳插件无特权差异，走同一套加载器/契约/权限，优先级最低、可被覆盖。

5. **高内聚 + 低耦合 + 开闭原则**：一个功能收进一个壳插件（及其内核侧扩展）整体交付；插件之间只走事件总线；
   新逻辑通过扩展（新插件/新槽位/新适配器）实现，不修改已有稳定代码。

## 二、设计理念

1. **机制与内容分离**：让功能能挂上来的机制留在壳，挂在上面的功能推给插件。判据：拿掉它系统能不能启动 + 一年后会不会换。
2. **依赖只向内（洋葱的根）**：外层可依赖内层，内层绝不依赖外层。不解释、不通融、没有例外。
3. **高内聚**：同一件事只在一处。一个功能的 UI、i18n、pi 内核扩展、dsh 内核扩展收进**同一个 plugin 目录**。
4. **低耦合**：插件之间不共享 store 互读写、不直读对方文件，唯一通道是事件总线。
5. **开闭原则**：对扩展开放（加插件/加槽位/加适配器），对修改关闭（不碰稳定内核与已有插件）。
6. **契约单源**：一个概念只有一份定义，外层 re-export，永不复制一份「本地版」。
7. **消费而非翻译**：主动消费内核吐出的结构化数据自己画 UI，不造「内核 UI 翻译层」。
8. **构造与执行分开**：怎么拼（Assembler）和怎么发（Gateway）两件事，一个函数既构造又执行就是坏味道。
9. **框架管通用，特化归外层**：多调用方共用的逻辑收进框架，差异只在参数；行为级差异才各自保留。
10. **完整设计一次落地**：先设计终态，再一步做完；拒绝「方案菜单里混补丁」「步骤切片交半成品」。
11. **根因修复不打补丁**：改完能说清根因是什么、为什么之前会触发、为什么改完不再触发。
12. **设计先行 + 提交即文档**：文档驱动代码；每个 commit 自解释（改了什么/为什么/架构依据/运行时验证）。

## 三、原则清单（编号，可对照执行）

> 每条 = 「原则陈述 + 判别气味 + 反模式/正确做法」。判别气味可直接作为检查项执行。

### 原则 1 · 依赖只向内（洋葱架构）

外层可以依赖内层，内层绝不依赖外层。圆心（`domain`/`contract`）出现对 `electron`/`better-sqlite3`/`react`/内核实现的 import 即红线。

- **判别气味**：内层 import 外层包；业务函数里直接出现 spawn / fetch / ORM / 进程调用。
- **反模式**：为「临时方便」在内层用一下外层工具函数——import 就是依赖，没有「只是用一下」的例外。

### 原则 2 · 圆心零依赖 + 契约单源

圆心只放类型定义和纯函数，零依赖。类型（`KernelId`/`BaseBackend`/中性事件/模型/配置）在圆心定义一次，外层 re-export。
内核身份 `"pi" | "dsh"` 只允许 `domain/kernel.ts` 一处定义。

- **判别气味**：两个文件出现同一概念的两份定义（哪怕一份「精确」一份「兼容」）；`"pi" | "dsh"` 字面量散落全仓。
- **反模式**：`if (provider.includes("deepseek")) kernel = "dsh"`——内核身份由 provider 名反推，而非「从哪个内核的配置扫出来」赋值。

### 原则 3 · 机制与内容分离（薄壳）

壳零功能含量：不出现写死的颜色 hex、写死的用户可见文案、针对具体内核/业务类型的 if-else 分支。
token key 合规（`t("shell.settings")`），token 值违规（`"#89b4fa"`、`"设置"`）。

- **判别气味**：打开壳任何文件，找到一处写死颜色/文案/业务分支即违规。
- **自检**：删掉 i18n 插件，界面文案应退化成 key 原文——这是设计（证明壳没内嵌文案），不是 bug。

### 原则 4 · 无特权差异

内置壳插件与第三方壳插件同一套加载器/契约/权限，优先级最低、可被覆盖。pi 与 dsh 同级，谁也不比谁更内建。

- **判别气味**：壳出现「识别内置件并特殊对待」「识别 pi 并特殊对待」的代码路径。
- **自检**：删掉任一内置插件壳照常启动；复制到用户目录以更高优先级覆盖；禁掉 dsh 壳照常启动只是少了 dsh 的能力。

### 原则 5 · 多内核默认：内核先抽象、后实现

任何涉及内核的开发，第一步先问「壳要的是一个什么抽象」，把抽象落进中立契约（`BaseBackend`/`SessionCatalog`/`KernelModelSource`），
第二步才想 pi/dsh 怎么实现。内核永远是抽象的一个实现，不是抽象本身。

- **判别气味**：会话意图链路上出现 `if (kernel === "pi")` 或 `asPi()` 类型守卫——壳在漏内核身份。
- **正确做法**：用能力接口（`backend.capabilities.pi`）探测——「有则用、无则降级」，不按内核身份硬分支。

### 原则 6 · 壳的三条内核无关不变量

1. 壳不读任何内核的存储（pi 的 JSONL、dsh 的 log 都不碰，只认不透明 `sessionId`）。
2. 壳只认中性事件（内核事件由适配器投喂成中性事件）。
3. 壳的渲染是纯函数（给定同一条中性事件流，timeline 怎么画与内核无关）。

- **判别气味**：会话意图链路上出现 `if (kernel === "pi")` 即一处泄漏。
- **自检项**：`domain`/`application` 是否直接 import 了 `client/{pi,dsh}` 的具体实现（泄漏）。

### 原则 7 · 能力拉平三分法：适配器翻译 → 内核补面 → 显式降级

壳看到 pi/dsh 的差异，三条出路按优先级：① 有「同一个语义、只是形状不同」→ 适配器翻译；② 形状翻译不了的能力缺失 → 内核插件补面
（pi 侧 TS 扩展，dsh 侧 Cordis 插件）；③ 补不了 → 显式降级（入口隐藏/置灰 + tooltip），不静默、不伪造成功。

- **唯一不允许的状态**：静默缺面——壳调了内核没有的能力，既不翻译、不补面、不降级，静默吞掉或假装成功。
- **高频实例**：dsh 缺 `setModel`/`fork`/`setSessionName` 时应缺面 no-op/降级，且**重装内核后缺面补丁不再丢**（桌面随附补丁持久化）。

### 原则 8 · 高内聚：一个功能 = 一个 plugin，内部四件套

一个功能收进**同一个壳插件目录**，内部按需四件：
- `locales/`——i18n 文案（desktop UI 文案）
- `renderer/`——desktop 壳插件（UI 组件 + 槽位贡献 + 事件）
- `pi-extension/`——pi 内核插件（给 pi 内核补能力的 TS 扩展）
- `dsh-extension/`——dsh 内核插件（给 dsh 内核补能力的 Cordis 插件）

一个功能的所有内核侧适配都内聚在这一功能自己的 plugin 下，而不是散落到壳的内核层。
参考实现：`src/plugins/sessions/goal/`（`renderer/` + `pi-extension/` + `dsh-extension/`）、
`src/plugins/insight/llm-recorder/`（`core/` + `renderer/` + `pi-extension/` + `locales/`）。

- **反模式**：新写插件时去改动 desktop 的内核（壳）来容纳这个插件——把会变的内容焊进壳，破坏薄壳。
- **正确做法**：尽可能集中到插件自身；有细节出入可以，但方向是「一个功能一个 plugin」。

### 原则 9 · 非必要不修改薄壳内核；要改动，首选改对方插件

默认不改壳的内核。确需改别人功能时，首选「改对方插件」，而不是动壳：比如要扩展会话流 UI，
是「会话流插件（timeline）提供槽位，本插件去填槽」——动的是对方插件和本插件，动不到壳的核心内核。
文件列表（file-tree）、会话列表（sessions-list）同理：它们本身就是薄壳插件，别的插件往里填槽，而不是改壳。

- **判别气味**：改动一个功能时，diff 落在 `server/`（壳）而非 `plugins/` 或内核插件。
- **正确做法**：对方插件提供槽位，本插件填槽；内核侧缺能力写内核插件；都不行才显式降级。

### 原则 10 · 低耦合：插件间只走事件，不共享 store 互读写

插件之间唯一合法通道是 `ctx.events.emit/on`。不通过共享 store 互读写、不直读对方配置文件、不经 `window.kernel` 直调对方能力。
共享 store 允许插件「读」框架状态，禁止调 setter——setter 只归框架。要改变框架状态走 ctx API。

- **反模式**：插件 A 写 store、插件 B 读 store（隐式握手，无依赖声明、payload 形状两处手写、改一边漂移）。
- **判别气味**：`dependsOn` 缺失时，删掉被依赖插件，依赖方静默读到空对象而非报错「缺依赖」。

### 原则 11 · 零硬编码

插件代码不允许出现 plugin ID、component 注册名、slot contribution ID、配置文件路径、**内核身份**的字符串字面量。
pluginId 由 `PluginIdContext` 自动注入，component 名由框架从 manifest 自动匹配，slot 可见性由框架传 `isActive` prop，
配置路径由框架按 pluginId 推导，内核身份由适配器/框架抹平。唯一例外：事件 channel 名是发布方的对外契约。

- **反模式**：`const PLUGIN_ID = "xxx"` 和 manifest `"id"` 手写两遍——改一处忘一处，运行时静默失败。

### 原则 12 · API 单入口（usePluginContext，不直访 window.kernel）

插件只经 `usePluginContext()` 拿受控 API（pluginId 绑定层 / 系统级 API 层 / 事件层），不直访 `window.kernel`，不 `usePiApi()` 拿裸对象。

- **判别气味**：插件代码里出现 `window.kernel.*` / `usePiApi()`——绕过 pluginId 绑定和权限校验，IPC 边界拿到裸调用，不知道调用方是谁。

### 原则 13 · 构造与执行分开

一个函数既构造又执行（既拼命令又 spawn、既拼请求又 fetch）就是坏味道。拆成：一个返回构造结果，一个接收构造结果并执行。

- **判别气味**：`sendCommand` 里既拼 JSON 又写 stdin 又等响应又解析 JSONL——改格式/改写入/改超时/改解析都要动同一个函数。

### 原则 14 · 框架管通用，特化归外层

多调用方共用的逻辑（save/dirty/reset、组件注册、pluginId 注入、事件 channel 注册、样式、语言、配置通道）收进框架统一承担，
调用方只传参数。差异是「参数级」就收敛，是「行为级」才各自保留。

- **反模式**：几十个设置页插件各写一份 save/dirty/拦截逻辑；或把 pi/dsh 处处相反的会话模型/事件形状/fork 语义硬塞进基类共享。

### 原则 15 · 依赖倒置连通内外

接口定义在内层，实现在外层，启动期注入。`session-store` 持 `BackendFactory` 接口而非 `new PiBackend()`；
`KernelManager` 持 `KernelRuntime` 接口而非直接 `spawn("npm")`。内层不直读 `process.cwd()`/`process.env.HOME`，路径由外层注入。

- **判别气味**：`session-store` 直接依赖 `ModelsStore`（core→client 依赖）；domain 直接请求 pi/dsh 内核，不经 kernel 层抽象。

### 原则 16 · 继承 + 实现：接口 → 抽象基类 → 具体实现

「接口 + 两个平行实现」的重复代码（缺面抛错、装/查机制）用「接口 → 抽象基类 → 具体实现」三段式收敛：
`BaseBackend`（契约）→ `AbstractBackend`（骨架 + 缺面默认）→ `PiBackend`/`DshBackend`（override 差异）。
基类只 import `core/domain`，绝不 import 具体内核；子类只填差异；组装归 bootstrap。

- **反模式**：pi/dsh 各写一份「缺面抛错」「装/查机制」；为「看起来能复用」预支往基类塞模板方法。

### 原则 17 · 手写收敛到成熟包

版本比较（semver）、类型解析（TS Compiler API）、拖拽、右键菜单、深合并（deepmerge）、UUID——成熟包千锤百炼，收敛掉。

- **反模式**：字符串字典序比较版本（`0.10.0 < "0.9.0"` 误判）；正则解析 `.d.ts`（嵌套/extends/联合面前脆弱）。

### 原则 18 · 事件驱动，不轮询不 sleep

用事件驱动替代轮询和固定延迟。组件只读 store、零拉取，基线 + 事件增量应用。冷启动不 sleep 猜就绪，而是向内核发探测命令以结果为准。

- **反模式**：固定 sleep 赌时序（赌输是偶发 bug 永远复现不了）；组件各自 useEffect 拉数据（同一数据拉三遍）。

### 原则 19 · 根因修复，不打补丁

定位真因再修，每个 fix 标注根因（哪个闭包旧值/时序竞态/useEffect 没重跑/IPC 监听器没返回清理）。
治标 = 改完能跑但说不清为什么；治本 = 说清根因 + 为什么之前会触发 + 为什么改完不再触发。

- **反模式**：UI 入口自写一套发起逻辑，绕过统一发送路径（导致发的是切换模型之前的旧状态）——这是「构造与执行分开 + 统一入口」没守住的典型。

### 原则 20 · 会话列表是壳的唯一源数据，同步给内核

壳拥有自己的会话列表作为**唯一源数据**，通过同步方法同步给内核（pi/dsh），而不是反过来让内核持有会话列表、壳去读内核。
这是「壳不读内核存储」在会话列表上的具体形态。

- **反模式**：把 session list 做成内核的投影/读内核（pi-only 惯性 + 泄漏）。
- **正确做法**：壳持有唯一源数据 → 同步给内核；会话 id 三端统一（无映射表）。

### 原则 21 · 等效点击发送（统一发起路径）

表情包、附件、任何 UI 入口发起会话，必须走**与点击发送按钮完全等效**的统一发起路径，
不能「自写一套发起逻辑」。自写发起必然与发送按钮的模型/参数/时序不同步。

- **反模式**：旁路入口自己拼发起（拿到修改模型前的旧状态）。
- **正确做法**：所有发起入口绑定到同一个发送功能上。

### 原则 22 · 不兜底、立即报错；内核身份跟随模型

兜底模型、默认内核、默认模型应**全部移除**，缺了就**立即报错**，绝不静默回落。
内核身份是**模型的派生量**：用户选哪个模型，就进哪个内核，选择时内核即已知——不存在「默认内核」，也不需要「反查」。
`ModelInfo.kernel` 由「模型从哪个内核的配置扫出来」决定，不由 provider 名反推。
pi 专属能力（`refreshThinkingLevels`/`abortRetry`）在非 pi 内核下要门控（非 pi 不拉取/回落中性实现）。

- **反模式**：`if (provider.includes("deepseek")) kernel = "dsh"`；「兜底永远回落 pi」；为「默认内核」新增独立配置项。
- **判别气味**：代码里出现 `getFallbackModel`/「默认内核」/「回落 pi-only」字样。

### 原则 23 · 多内核会话/模型切换全对称

模型切换要支持 pi↔dsh **来回切换**，模型选择即确定目标内核（不是「在旧内核上切新内核的模型」），
会话页在切换内核时带过渡动画、图标跟随内核切换。会话启动、模型握手、事件流在两种内核下行为一致。

- **反模式**：切换目标写死旧内核（`Model not found`）；纯 dsh 会话只能靠「切换」诞生，不能直接创建。

### 原则 24 · 开闭原则（对扩展开放、对修改关闭）

新逻辑通过「加一个壳插件 / 加一个内核适配器 / 给缺面内核加一个内核插件」实现，不修改已有稳定代码。
这是薄壳 + 多内核 + 插件化的合流：扩展的载体是插件和适配器，不是给壳打补丁。

- **反模式**：每加一个功能就改一次壳——壳从薄变胖，特权分支累积。
- **正确做法**：「对方插件提供槽位，本插件填槽」（原则 9）。

### 原则 25 · 设计先行 + 设计文档盲审（终态一致、无自相矛盾）

先写设计文档再搭骨架再填代码；设计文档是真相源。写完后做**盲审**（clean-room reviewer）：
以真实代码为真相源核对「文档说了但代码不是那样」「文档自相矛盾/术语漂移/读者定位不到唯一判据」。

- **判别气味**：同一判据多套说法；「底座 vs 内核 vs 壳」术语混用；文档与代码签名不一致（如 fork 返回类型）。
- **正确做法**：术语单源 + 机械清扫规则 + 文档=代码双向核对。

### 原则 26 · 内核身份不进配置文件；能力探测而非身份硬分支

`ModelInfo.kernel` 由「从哪个内核的配置扫出来」赋值，不由 provider 名反推；会话意图链路上用 `capabilities` 探测（有则用、无则降级），
不用 `if (kernel === "pi")` 硬分支。内核身份、模型类型、事件类型、配置类型、lineage 类型全部从圆心发出。

- **判别气味**：会话链路上 `asPi()` 类型守卫；内核 logo/身份标由外部保存再自己路由（应由内核自己提供）。

### 原则 27 · 进程不泄漏（每次调用不泄漏内核进程）

`getTree`/`bookmark`/`deleteBookmark` 这类读操作要走 catalog（会话目录），不能每次调用都 spawn 一个内核进程（进程泄漏）。
内核子进程的生命周期由壳统一持有/回收，读操作是纯目录查询，不拉起进程。

- **反模式**：每次读树/收藏/删书签都 spawn pi；统计投递只走 pi 路径（`asPi` 泄漏），dsh 实时统计整块为空。

### 原则 28 · 安装/升级诚实：不「假安装成功」

内核/插件安装要么真失败、要么真成功，不允许「假安装成功」。覆盖式安装要清旧 `node_modules`+lock（堵 ERESOLVE），
版本走正确的 dist-tag（next 而非 latest 陈旧依赖），安装后验证连通性（模型测试）。

- **反模式**：安装状态不诚实、空 provider 路由毒化、密钥按 provider 注入竞态、测试超时还不展示错误。

### 原则 29 · 提交即文档

每个 commit 自解释：改了什么、为什么改、架构依据、运行时验证。反例是 `fix bug`/`update`/`tmp`。

### 原则 30 · 冷启动引导时序（前端入口可独立起）

`window.kernel` 引导、WS hello 帧序、Tailwind 源路径、数据根路径，这些启动期时序要事件驱动、不靠模块级副作用，
数据根路径不依赖 electron（node 服务器可独立起）。前端入口（Vite）不是独立应用，需 dsh web 注入 `window.__DSH_BOOT__`。

- **反模式**：组件模块级读 `platform` → 黑屏；WS hello 帧序竞态 → 加载不出；`window.pi → window.kernel` 改名后 demo 脚本未同步。

### 原则 31 · 给内核补能力 = 写插件/扩展，严禁修改外部内核仓库

要给 pi 补能力，写 pi 扩展（TS 扩展装进 `~/.pi/agent/extensions/`）；要给 dsh 补能力，写 dsh 的 Cordis 插件/扩展。
**严禁修改 deepseek-harness 等外部仓库的核心**——内核的能力缺口用「内核插件」补齐，而不是去改对方仓库。

- **反模式**：把 goal/续跑/setModel 缺面做成「改内核」而非「写内核插件」。
- **正确落地**：pi 侧合并成统一 `my-harness-fit-pi-extension`，dsh 侧合并成统一 `my-harness-fit-dsh-extension`，随 desktop 分发。

### 原则 32 · 统计是壳子自己的事，与内核无关

轮数、step 数、token、上下文占用这些**统计量由壳从中性事件自己算**，不向内核要统计。
内核只负责吐中性事件（消息增量/工具调用开始结束），壳拿同一份事件流做统计——两种内核下统计逻辑完全一致。

- **反模式**：`getStats()` 里 `this.asPi(proc).getSessionStats(...)`——统计投递只走 pi 路径（asPi 泄漏），dsh 实时统计整块为空。

### 原则 33 · 配置层统一 JSON 出入：get/set 两原语

内核配置的契约收窄为 **JSON 出入**：出参入参都是 JSON、字段通用化、更新也是 JSON 出入，砍到只剩 `get(): JSON` / `set(JSON): JSON`。
每个内核自己维护自己的信息、吐给 kernel 层；不搞跨内核「共享配置」，配置 TAB 退化成通用 JSON 编辑器（或只留「打开原始文件」）。

- **反模式**：配置展示把整段 JSON 甩给用户而非字段化；为「默认内核」新增独立配置项。

### 原则 34 · 展示类数据（图片等）由壳的 kernel 层统一维护，同步时过滤

图片、展示附件等**纯展示数据由壳的 kernel 层统一维护**，不进入内核会话文件（pi 的 JSONL）；同步给内核发起时可直接过滤，不发送给 AI。
分叉 = 完整复制（含展示数据），fork 的是 kernel 层的版本再拿去内核发起。

- **反模式**：图片存 `session-images.json`（不在 JSONL），只复制 JSONL 时分叉产物自然丢图。

### 原则 35 · 前后端分离 + 目录整洁 + 项目只存代码

物理目录第一层就是 `server/`（后端）+ `web/`（前端）+ `plugins/`（内容）+ `packages/`（发布面），共享契约收进 workspace 包（`packages/shared` 的 domain/contract）。
**项目仓库只存代码**：坚决杜绝提前编译安装的中间产物（node_modules、dist、编译产物），历史 commit 里的中间产物全部清理。
包结构不能「太平」——每层要么只放文件夹、要么只放文件。

- **判别气味**：目录结构里看不出前后端分离；仓库里出现编译产物/中间产物；包内文件与文件夹混放。

### 原则 36 · 开发节奏硬纪律：只读模式先行 + 盲审 + commit + worktree 闭环

动手前先「只读模式」出方案（先分析、给方案，不直接改）；写设计文档后「盲审」几轮（clean-room reviewer 找矛盾/漂移/可落地性问题）；
每步 `commit`（提交即文档）；代码修改走「标准 worktree 工作流：建 worktree → 改 → 验证 → commit → 合并回 main → 清理中间产物」。

- **反模式**：不亲自验证就交付、反复「假成功」；把未完成项标「较低优先级」后交付半成品。

### 原则 37 · 对标先行者，1:1 复刻现成实现，别重复造轮子

写 pi 的能力先抄 dsh 现成实现（或反之），已有成熟实现就 1:1 复刻。UI 不只是功能等效，**界面也要等效**。
框架已有现成机制（save/dirty、打开原始文件、导出配置）就复用，不重写一套。

- **反模式**：框架已有现成机制还自己重写一份；两个内核的模型设置/管理页「功能等效但 UI 不等效」。

## 四、高频反模式清单（按根因归类）

> 每条 = 「反模式 + 表现 + 根因 + 正确做法」。这些是跨 session 反复出现、被反复纠正的问题。

1. **pi-only 惯性**：从 pi-only 迁到 desktop + pi + dsh 后，残留的 pi 专属路径——兜底永远回落 pi、
   `window.kernel` 直访、`if (kernel==="pi")` 分支、思考档位不门控、session list 读内核。
   根因：迁移没做「泄漏扫描」。正确：能力探测 + 门控 + 泄漏扫描（`core→client 归零`、`每次调用不泄漏 pi 进程`）。

2. **会话流模型/内核来回切换失败**：`Model not found`、在旧内核上切新内核的模型、切换后图标不变、dsh 会话发不出去。
   根因：模型路由没经 `ModelCatalog` 反查内核、切换目标写死旧内核、dsh setModel 缺面。
   正确：`setModel 跨内核路由` + `setModel 透传 initialize 握手` + 缺面补丁持久化。

3. **假安装成功 / 测试永远失败**：安装装不上或假装装上、模型测试从来失败。
   根因：安装状态不诚实、空 provider 路由毒化、密钥按 provider 注入竞态。正确：覆盖式安装清旧依赖 + 连通性实测 + 失败显式报错。

4. **旁路发起 ≠ 等效点击发送**：表情包/附件发的是切换模型之前的内容。根因：UI 入口自写发起逻辑，绕过统一发送路径。
   正确：所有发起入口收敛到「等效点击发送」的唯一路径。

5. **session list 不是壳唯一源数据**：被做成读内核/内核投影。正确：壳持有会话列表唯一源数据，同步给内核。

6. **静默缺面 / 缺面打断发送**：dsh 缺 `setModel`/`fork`/`setSessionName`/`setThinkingLevel` 时抛错打断发送、重装内核后补丁丢失。
   正确：缺面 no-op/降级 + 桌面随附补丁持久化 + 能力探测守卫。

7. **壳内写死文案/颜色/业务分支**：壳出现具体颜色值、中文文案、`if (tool==="bash")`。正确：token key 进壳，值进主题/i18n 插件。

8. **插件硬编码 + 直访 window.kernel + 共享 store 互读写**：`const PLUGIN_ID`、`window.kernel.*`、store setter 互读写。
   正确：零硬编码（Context 注入）+ API 单入口 + 事件唯一通道（见 `plugin-isolation-principles.md`）。

9. **设计文档自相矛盾 / 术语漂移**：同一判据多套说法、「底座 vs 内核 vs 壳」三词混用、文档说的和代码做的不一致。
   正确：术语单源 + 盲审（clean-room reviewer）+ 机械清扫规则 + 文档=代码双向核对。

10. **冷启动时序竞态 / 黑屏**：模块级读 platform、WS 帧序竞态、Tailwind 路径漂移、`window.pi→window.kernel` 改名漏改。
    正确：事件驱动引导、入口注入、改名后全局 grep 同步。

11. **泄漏内核进程 / core→client 依赖**：每次读树/收藏/删书签都 spawn 内核；session-store 直接依赖 ModelsStore。
    正确：读操作走 catalog、依赖倒置、`core→client 归零`。

12. **UI 细节回归**：面包屑压 mac 红绿灯（platform 归一化回 `process.platform` 约定）、归档按钮失效、图片下方多余 title 行。
    正确：platform 归一化单源、功能按钮做 e2e 验收回归。

13. **修改外部内核仓库 / 改内核而非写插件**：给内核补能力时去改 deepseek-harness / dsh 内核，而不是写扩展。
    正确：写 pi 扩展 / dsh Cordis 插件，合并成统一 fit-extension 随 desktop 分发，绝不改对方仓库核心。

14. **未验证即交付 / 假成功**：不亲自跑一遍就交付、功能点没测过、测试失败还不展示错误。
    正确：交付前亲自点一遍、连通性实测、失败显式报错。

15. **契约单源漂移**：同一概念两套接口（如 domain 的 `PiExtensions` 与 client 的 `PiBackendExtensions` 并存）、路径规则多处复制。
    正确：圆心定义唯一源，外层 re-export，删掉副本。

16. **文档与实现矛盾**：dependsOn 加载顺序、fork 返回类型、插件 tier 级别等文档与代码不一致。
    正确：文档=代码双向核对，以真实代码为准。

17. **发现机制不通用 / 各内核各写一套**：skills/tools/i18n 的发现机制应由壳统一搞一层，而非 pi、dsh 各写一套。
    正确：壳统一发现层（递归扫描 + manifest 声明），内核侧缺的用插件补。

## 五、插件开发的一条总纲

> 把上面的原则压成一段可背的行动纲领：

**新写一个功能，永远按这个顺序想：**

1. 先想「这个功能是一个**独立的壳插件**吗？」——是，就收进 `src/plugins/{domain}/{feature}/`，一个 plugin 一个功能。
2. 插件内部按需四件套：`locales/`（文案）+ `renderer/`（desktop UI）+ `pi-extension/`（pi 内核补面）+ `dsh-extension/`（dsh 内核补面）。
3. **绝不为了这个插件去改壳的内核**（薄壳不可动），**也绝不改外部内核仓库**（deepseek-harness / dsh 核心，只写扩展不写对方核心）；
   需要内核侧能力，用内核插件（pi-extension/dsh-extension）补，或用「有则用、无则降级」探测。
4. 要改别人的功能 → **首选改对方插件**：对方插件提供槽位，本插件去填槽（timeline/file-tree/sessions-list 都是薄壳插件，往里填）。
5. 插件只从 `usePluginContext()` 拿能力，零硬编码、不直访 `window.kernel`、不共享 store 互读写，插件间只走事件。
6. 高内聚、低耦合、洋葱架构、薄壳架构、开闭原则——每一条都在这五步里。

**一句话**：*壳是机制、插件是内容、内核是被适配的能力；改功能 = 改/加插件或适配器，永远不动壳的圆心。*
