1. 为什么"一直都有接下来要搞的事"

你的感受是对的——每轮报告末尾都挂着待办。这不是我在拖延，而是这类工作的结构决定的。三个机制：

① 棘轮式治理：每收紧一层，就暴露下一层

大量债务不是一次能清完的（比如"发射后不管的 void promise"全仓 212 处）。 做法是：先量化（写守卫数出真实值）→ 立棘轮基线（只许减不许增）→ 每轮消化几处 → 基线跟着实测值下调。 所以"待办"其实是一个正在下降的数字，不是无限的清单：

棘轮起点现在性质
i18n 死键2310已清零（硬断言）
动态前缀缺键680已清零（硬断言）
发布面零测试引用导出5717下降中
void 发射后不管21321215 条已入正当账本
德语单词级未译69607 条正当豁免
busy-flag 无 finally / config.set 双重播报—0硬断言 + 反向注入已验

读法：0 的那些已经不是待办了，是守卫在看着的既成事实；剩下的都是"有上限、在下降"的债务。

② 覆盖是有层次的，绿灯不等于覆盖

这是后期最主要的"新待办"来源，也是最有价值的发现。举一个真实例子（r233–r249 一条线走到底）：

  1. dom-audit 跑出来 0 条发现 → 看着很干净；
  2. 读它的实现才发现：检查④跳过不可见子树，而设置页是 keep-mounted 的（display:none）→ 非激活页根本没被扫；
  3. 再读才发现真正原因是一个上限常量（if (visited >= 14) break，而候选有 73 个）→ 内核页全在后面；
  4. 改成按稳定锚点走完 17/17 个设置条目 → 立刻查出 5 条新东西（逐条读后全是正当例外，于是补了两条窄豁免）；
  5. 于是断言从 28 项长到 47/48 项（两个语言），r229 修的"内核版本页裸键"才第一次有真机证据。

通则（写进 skill 的）："剧本里有这项检查"≠"这项检查覆盖到了那个页面"； "覆盖到了那个页面"≠"走到了那个分支"。覆盖要落到分支级。 每往下一层，就会冒出上一层看不见的待办——这不是效率低，这是验证深度在增加。

③ 有些缺口需要外部条件，不是我能在本地关闭的

需要真实内核与 token 的剧本（dsh-*、pi-*、multi-kernel-round、fork.e2e、 fork-cross-kernel、goal-command、kernel-thinking-matrix）在"纯本地、不与远程交互"的约束下跑不了。 它们会一直躺在待办里，直到你给一次真实额度。

所以怎么判断该停？我在 r247 给自己立过一条判据并真的执行了（r249）： "这一轮有没有让下一轮的工作量变小？" 有 → 继续；连续两轮卡在同一格且没有新信息 → 停， 删掉半成品，把"已确证 / 仍缺"分栏记下。目标本身在第 256 轮已按九项逐条自评后标记完成， 剩下的都是可选增量，不是未完成的目标。

2. 七条主线：具体都干了啥

A. 架构与抽象：把"内核"从特权变成插件

  • 能力面从单 bit 改成十一轴（steering / retry / compaction / snapshot / stats / modelCycle / toolExec / busFrames / questions / thinking + fileBacked）。 此前"某内核缺多路并发"会连带禁掉它本可有的压缩与统计——违背"内核同等地位、同等功能"。
  • 删掉按内核身份取面的助手：asPi() / piSend() 退役，改成按轴取面，错误消息点名轴不点名内核； opaque 桶 capabilities.extensions 删除（它逼 application 去 type-only import 内核实现）。
  • 真实的第四内核 probe4：不是 mock，是与 pi/dsh 同级的注册内核，用来实测开闭原则——加它时壳一行未改。
  • 机制层零内核名：路径常量、manifest.piExtension 这类按内核名分的字段、catalogFor("pi") 全部消失； 内核目录自包含（对外只暴露动态 require 的 plugin.js）；字面量键访问（kernels.pi / kernelConfig["dsh"]）归零。
  • 契约单源清理：ChannelMeta.label → labelKey；删死字段 maxTokens；IPC 表 34 处字面量改常量； 圆心 20 个零引用纯函数清零并加防回潮守卫。

现状：内核目录 core / pi / dsh / minimal / probe4；内核插件 src/plugins/kernels/{pi,dsh}； 测试内核 test-plugins/kernels/{minimal,probe4}（结构性杜绝测试内核在真实项目留幽灵会话）。

B. 静默失败与反馈通道（这是最大的一条线）

把"用户点了按钮、什么都没发生、也没人告诉他"这类缺陷分类学化，定出四种形态：

#形态典型代码为什么静默
①裸奔void p / 无保护 await p结果与错误一起被丢弃
②通道失效播报存在，但宿主能力是 no-op以为说了，其实没人听
③有 catch 无反馈try/catch + console + 回滚用户看不到任何输出
④通道只覆盖一半失效来源结果对象 {ok,error} 覆盖"操作失败"，不覆盖"调用被拒"busy 标志永不清 ⇒ 按钮卡死

并定出三条通道（判据是"有没有用户动作在等它"）：有用户动作 ⇒ 播报给用户；用户正看着这块 UI ⇒ 如实渲染三态（失败/空/数据）； 两者都不是 ⇒ 带模块标签的 console.warn。空 catch 一条都不满足。

  • 收敛出原语 fireAndReport，并加"接线对账守卫"（用了原语就必须接对）。
  • 修掉的具体站点（举要）：stickers 5 处、sessions-list 多处、git-review 的 doCommit/doPush、 kernel-version-page 的 install/apply、timeline 的 handleSendNow、session-bookmarks、session-tree、im-graph、 projects 的 switchCwd、font-tab、model-config 导出、session-colors 的 openSession。
  • 三态渲染：remote-access（status/qr/devices）与 llm-recorder 从"空列表"改成"装载失败"， 因为空列表 ≠ 装载失败，谎报比留空更糟。
  • 43 处非 UI 的 .catch(() => {}) 改成带模块标签的 console.warn（13 个文件）。
  • 回退过一次自己的修复（r216）：发现 ctx.config.set 在框架层已经播报，插件层再包一层就是双重播报 ⇒ 撤掉 9 处、删 28 个死键、加守卫 config-set-double-announce（0 命中硬断言、注入已验）。

C. i18n 全链路（四语言：zh-CN / zh-TW / en / de）

  • 死键 231 → 0：给"键的消费方"建模八类（含最难的一类：键当数据传—— 圆心把 timeline.modelChange 写进 divider 条目的 i18nKey，渲染侧才 t(i18nKey, args)， 所以按文案 grep 永远找不到消费处）。
  • 动态前缀缺键 68 → 0：KernelVersionPage / ModelConfigPage 是共享页面， 键名由调用方的 i18nPrefix="dsh|kernel|dshModels|models" 拼出；缺键时 i18next 把键名当译文返回 ⇒ 页面上出现 dsh.applied 这样的裸键。守卫按"组件 ↔ 实际传入的前缀"配对算（不是笛卡尔积，那会造出 708 个假阳性）。
  • 德语单词级盲区：既有守卫明确跳过"≤1 个词"的译文，于是单立一条把这类量化到 60（7 条正当豁免：字段名如 apiKeyEnv）。
  • 真机面：dom-audit 在 de 下断言"界面里不该出现任何中文串"，只豁免语言自称（简体中文/繁體中文）。

这一条线上我犯过整个周期最严重的错（r229）：批量补键的脚本没有对每个文件设前置条件， 结果写进了 488 个语言文件（1036 条），而预期只有 8 个。 发现方式是脚本自己打印了"触及 488 个文件"与预期不符 ⇒ git checkout -- 全量还原 ⇒ 三重验证还原（git status 干净 + 全量测试 + 污染串全仓 grep 归零）⇒ 重做时限定到"含该前缀的 8 个文件"。 由此立下纪律：批量写入脚本的每条写路径都要能回答"为什么是这个文件"，并对触及文件数设预期值。
