# i18n 插件技术文档

## 1 定位与分层

- i18n 插件是 my-harness-desktop 的**语言槽插件**，物理位置 `src/plugins/system/i18n/`，由 `plugin.json` + `renderer/index.tsx` + `locales/` 三部分组成，是壳插件（UI 插件）而非内核插件。
  - 它同时贡献两个槽位：`languages`（16 项语言包贡献，见 `plugin.json` 的 `contributes.languages`）和 `settings`（一个语言设置页入口，`id: "language"`）。
  - `plugin.json` 顶层声明 `"protected": true` 与 `"tier": "official"`：前者对应 `PluginManifest.protected`（`packages/shared/src/domain/contributions.ts` L501，受保护插件可禁用但不可卸载），后者对应 `PluginTier = "official" | "verified" | "community"`（同文件 L523）。
  - 它的角色在整仓里是**内容生产者**：产出四语言文案给全仓所有插件的 `t(key)` 消费；它自己不拥有任何会话/工具/模型能力，零 `permissions`、零 `configFile`、零内核扩展（无 `piExtension`/`dshExtension` 字段）。

- 从洋葱分层看，这个插件站在最外层"内容层"，圆心与壳只提供机制。
  - 圆心 `packages/shared/src/domain/contributions.ts` 定义了契约类型 `LanguageContribution`（L130）与 `PluginContributes.languages`（L418），是**纯类型零依赖**的发布面。
  - 壳后端 `src/server/application/i18n/merge.ts` 与 `translator.ts` 是机制实现：前者把各插件的 languages 贡献合并成 i18next resources，后者持 i18next 单例并做 locale 检测。
  - 壳前端 `src/web/app/i18n-init.ts` + `src/web/stores/ui-store.ts` 是 renderer 侧的机制：初始化 react-i18next、订阅 locale 变化、落 prefs。
  - i18n 插件只依赖 `@my-harness-desktop/react`（`usePluginContext`/`useUiStore`/`SettingsSection`/`ListItem`/`SettingsComponentProps`）和 `react-i18next`（`useTranslation`），不 import 任何 `src/server/`、`src/web/`、`packages/shared` 之外的内部实现，守壳插件依赖边界。

- 与文档 `docs/plugins/i18n.md`（旧版）的关系：旧版描述的是 `window.pi.*`、`@my-harness-desktop/core`、48 文件 12 命名空间的历史形态，本仓库当前代码已演进为 `window.kernel.*`、`@my-harness-desktop/shared`/`react`、16 文件 4 命名空间。本文以 `src/plugins/system/i18n/` 当前真实代码为准。

## 2 languages 槽契约

### 2.1 类型定义与字段语义

- `LanguageContribution` 定义在 `packages/shared/src/domain/contributions.ts` L130-137，是纯声明式契约，无 main/renderer 代码。
  - `id: string`：语言包贡献项标识，注释约定"通常 `{pluginId}` 或 `{pluginId}.{namespace}`；`(插件, locale)` 维度唯一"（L131）。
  - `locale: string`：locale 标识，注释明确 `zh-CN / zh-TW / en / de` 等，且 L127-128 注明"偏离 05 §2.1 只用 2 位短码——简繁必须靠区域码区分，放开为接受区域码"，这是 BCP 47 地理区域码而非纯语言码。
  - `resources: Record<string, string> | string`：**key→文案 扁平映射**（dot namespace，如 `"sessions.title"`），或指向外部 JSON 文件的相对路径（L135-136）。这是契约里唯一一个"或对象或字符串"的联合类型。

- `PluginContributes.languages?: LanguageContribution[]`（L418）是顶层挂载点：一个插件可以在 `contributes.languages` 里声明任意多条贡献项。
  - i18n 插件声明了 16 条（4 locale × 4 文件），每条 `id` 是 `i18n.common`/`i18n.settings`/`i18n.plugin`/`i18n.shell`，`resources` 全是相对路径字符串。
  - 对比其他插件的声明（grep 全仓 `plugin.json` 的 `languages` 字段命中 38 个插件）：`projects` 插件用 `id: "projects.projects"` + `resources: "./locales/zh-CN/projects.json"`，`theme-manager` 用 `id: "theme-manager.theme"` + `./locales/zh-CN/theme.json`，`timeline` 用 `id: "timeline.shell"` 等——`id` 普遍采用 `{pluginId}.{语义}` 命名，但这不是框架强制的约束。

### 2.2 关键契约点：namespace 由 key 首段推导，不由 id 决定

- 这是理解整个语言槽最容易误判的地方：`LanguageContribution.id`（如 `i18n.common`）**不参与** i18next namespace 的判定，它只是 `(插件, locale)` 维度的去重/日志标识。
  - 真正决定 namespace 的是**每个 key 的第一个 dot 之前的段**。`mergeLanguageContributions`（`src/server/application/i18n/merge.ts` L90-95）对每条 key 执行 `key.indexOf(".")`，`dotIdx === -1` 时走 `defaultNS=common`，否则 `ns = key.slice(0, dotIdx)`、`k = key.slice(dotIdx + 1)`。
  - 因此 `common.refresh` → ns `common`、key `refresh`；`plugin.i18n.displayName` → ns `plugin`、key `i18n.displayName`；`shell.settings` → ns `shell`、key `settings`。
  - i18n 插件的四个 JSON 文件各自把 key 首段统一成 `common`/`settings`/`plugin`/`shell`，于是每个文件恰好对应一个 i18next namespace——这是"文件→namespace"映射的**约定**而非**机制**，机制只看 key 首段。

- `(插件, locale)` 唯一性是注释里点明的维度：同一个插件在同一 locale 下不应出现两条 `id` 相同的贡献项，但不同插件、不同 locale 可以各自贡献同首段 key（这正是跨插件 key 级 union 的前提）。
  - 例如 `shell.copy` 由 i18n 插件贡献、也由 timeline 插件贡献（`src/plugins/sessions/timeline/locales/zh-CN/shell.json` 里就有 `shell.copy`），两条贡献在合并时按来源优先级仲裁。

### 2.3 resources 两种形态与解析语义

- `resources` 可以是内联对象，也可以是相对路径字符串；i18n 插件全部用字符串路径（指向 `./locales/{locale}/{file}.json`）。
  - 内联对象形态：`resources` 直接是 `Record<string, string>`，供不想拆文件的插件把文案写进 plugin.json 本身。
  - 字符串路径形态：路径**相对插件目录**解析（不是相对 cwd、不是相对 i18n 插件目录），解析函数 `resolveLanguageResources`（merge.ts L46-70）用 `join(pluginPath, r)` 拼绝对路径。

- `resolveLanguageResources` 的失败语义是"跳过该贡献项而非炸掉启动"。
  - 文件不存在 → `console.error` 后返回 `null`（L53-55）；`JSON.parse` 抛错 → 记 error 返回 `null`（L64-66）；顶层非对象（`null`/数组/原始值）→ 记 error 返回 `null`（L59-61）。
  - 返回 `null` 的贡献项在 `mergeLanguageContributions` 里被 `continue` 跳过（L85），保证单个语言文件的笔误不会让应用启动失败——这是"内容层笔误不得炸应用"的薄壳原则在 i18n 的落地。

## 3 框架合并机制：mergeLanguageContributions → i18next resources

### 3.1 收集层：registry 把贡献项带来源信息归档

- `PluginRegistry`（`src/server/application/loader/registry.ts`）专门为 languages 槽保留了**一个原始数组**而非 `ArraySlot`，这是它和其他数组类槽位的本质差异。
  - 其他槽位（settings/sidePanel/sidebar/titlebar/fileActions 等）走 `arraySlots` 映射（L107-128），注册时 `reg.removeById(id)` 去重再 push（L155-157），语义是"贡献项级二选一"。
  - languages 槽则是 `private languages: { contribution; pluginId; source; pluginPath }[]`（L104），`registerOne` 里直接 `push({ contribution: l, pluginId, source, pluginPath })`（L160-162），**不去重、不二选一**——因为语言槽是字典 union，同 id 的贡献项（不同插件或不同来源）要全部保留供 key 级仲裁。
  - `languageContributions()`（L403-405）原样返回这个数组，供 assemble 阶段的合并器消费。

- 来源优先级在收集时就已经绑定到每条贡献项上。
  - `source` 来自 `DiscoveredPlugin["source"]`（`project | user | installed | builtin`），由加载器的 `discoverPlugins(dir, source)` 在发现阶段打标（`src/server/bootstrap/assemble.ts` L206-209 依次 `discoverPlugins(builtinDir, "builtin")`、`installed`、`user`、`project`）。
  - `pluginPath` 是插件目录绝对路径，`resolveLanguageResources` 靠它定位 `./locales/...` 相对文件。

### 3.2 装配层：assemble 的注册序决定同优先级胜负

- `assemble.ts` L206-214 的装配序是合并正确性的前提：`registry.registerAll` 按 `builtin → installed → user → project` 顺序注入，然后取 `languageContributions()` 交给 `mergeLanguageContributions`。
  - 这个顺序配合 `mergeLanguageContributions` 里"等优先级先处理者胜"（merge.ts L98-101）的规则，实现了 `project > user > installed > builtin` 的覆盖语义：高来源的贡献项后进，遇到等优先级冲突时先处理者（低来源）已占位、后处理者（高来源）不覆盖——但真正把"高来源覆盖低来源"做出来的是 `SOURCE_PRIORITY` 的数值比较（高值胜），等优先级才退回"先处理者胜"。

- `assemble.ts` 只做"合并 + 给 renderer"，不在 main 侧初始化 react-i18next。
  - L213-214：`const languageContributions = registry.languageContributions(); const i18nResources = mergeLanguageContributions(languageContributions);`。
  - L506-511 把四样东西塞进 `MainContext.i18n`（类型在 `src/server/application/context/main-context.ts` L137-142）：`resources`（合并结果）、`namespaces`（`collectNamespaces`）、`supportedLngs`（`collectSupportedLngs`）、`localeList`（`collectLocaleList`）。
  - 注释 L212 写明"main 只合并 + 给 renderer；renderer 端 init i18next + react-i18next（跨堆，各持实例）"——main 与 renderer 各自持一个 i18next 实例，查询语义一致、实例独立。

### 3.3 合并器：两步 key 级 union

- `mergeLanguageContributions`（merge.ts L77-139）分两步：先按 locale 做 key 级 union，再把扁平 key 折叠成 i18next 的嵌套资源树。
  - **第一步（L80-103）**：`byLocale: Map<locale, Map<nsKey, {value, priority}>>`。外层遍历所有 `LanguageContributionWithMeta`，内层遍历 `resolveLanguageResources` 解出的每条 `[key, value]`。key 先做 dot 拆解（首 dot 前为 ns、无 dot 走 `common`），拼成 `${ns}:${k}` 作为 union 键。`SOURCE_PRIORITY`（L21-26）把 `builtin:1/installed:2/user:3/project:4` 映射成数值；覆盖条件是 `!existing || existing.priority < priority`（L99），即**严格大于才覆盖**——高值胜，等值不覆盖（先处理者胜）。
  - **第二步（L105-137）**：把每个 `nsKey` 再拆回 ns 与 k，把 k 按剩余 `.` 拆成 `parts`，逐段下钻成嵌套对象，叶子写文案值。i18next 配 `keySeparator: "."`，查找路径按 `.` 分层解析，所以扁平 key 若带剩余点（如 `plugin.i18n.displayName` 拆 ns 后剩 `i18n.displayName`）必须再拆成 `{i18n:{displayName:...}}`，否则 `t("plugin.i18n.displayName")` 会 miss——注释 L106-107 专门强调这点。

- 第二步里还有一层**叶/枝冲突容错**（L118-134），防御的是"内容层笔误"而非正常覆盖。
  - 当某 key 的中间段已经是一个字符串叶子（如已有 `a.b` = "x"，又来 `a.b.c` = "y"），或叶子位置已经是子树，则记 `console.error` 并 `continue` 跳过该 key（L122-126、L131-134），规则与 key 级合并的"先处理者胜"一致。
  - 这层容错保证任何一个插件的语言文件里 key 命名与其它插件的 key 前缀撞车时，应用启动不被炸掉，只是丢弃后到的冲突 key 并告警。

### 3.4 三个收集器：全部动态、不写死内置清单

- `collectNamespaces`（L143-149）：遍历合并结果 `resources` 的每个 locale 下的 ns 键，去重返回。注释 L141-142 标注这是评估 P3 的修复——此前硬编码 8 个内置 namespace 兜底，改为纯动态收集。
- `collectSupportedLngs`（L153-157）：遍历 `contributions` 数组取 `contribution.locale` 去重。注释 L151-152 标注此前硬编码 `["zh-CN","zh-TW","en","de"]`，改为动态——任何第三方插件贡献的 locale 都会自动进支持列表。
- `collectLocaleList`（L163-173）：把 `supportedLngs` 映射成 `{id, name}[]`，`name` 从合并结果的 `common.locale.{code}` 查（各语言用自己的语言表达其它语言名），缺失回退 locale code 本身。i18n 插件的 `common.locale.zh-CN/zh-TW/en/de` 四条 key 就是为这个收集器供数据，使设置页语言列表能显示"简体中文 / 繁體中文 / English / Deutsch"。

## 4 i18n 插件自身的语言包如何分发

### 4.1 plugin.json 的 16 条声明

- `plugin.json` 的 `contributes.languages` 数组（L10-91）声明 16 条贡献项，结构是 4 locale × 4 文件。
  - 前 12 条是 `common`/`settings`/`plugin` 三个 id 在 `zh-CN/zh-TW/en/de` 下的各一份，后 4 条是 `shell` 这一个 id 在四语言下的各一份（L71-90）。
  - 每条 `id` 为 `i18n.common`/`i18n.settings`/`i18n.plugin`/`i18n.shell`，`locale` 与 `resources` 路径一一对应，`resources` 全部是 `./locales/{locale}/{file}.json` 相对路径。
  - 没有一条用内联对象——i18n 插件把全部文案外挂到 16 个 JSON 文件，plugin.json 只留路径声明，这是"文案是内容、内容外挂"的范式样本。

### 4.2 四个文件各自承载的命名空间

- `common.json`（每语言 22 条 key）承载通用动作与状态词：`common.refresh/clear/unknown/notInstalled/loading/installing/checking/latest/installed/on/off/default/send/cancel/confirm/close/copy/delete` 共 18 条，外加 `common.locale.zh-CN/zh-TW/en/de` 四条"语言自称名"。
  - 这四条 `common.locale.*` 是 `collectLocaleList` 的数据源，键名带点但首段是 `common`、剩余段 `locale.zh-CN`，合并后成为 `common.locale.zh-CN` 的嵌套查找路径。
- `settings.json`（每语言 2 条）承载语言设置页自身文案：`settings.language`（"语言"）与 `settings.languageDesc`（"选择界面语言，实时生效。"）。
  - 这两条 key 的 ns 是 `settings`，与 `theme-manager` 贡献的 `settings.font/settings.theme` 等共享同一个 `settings` 命名空间——设置页把 `settings.{item.id}` 当翻译 key 查，见下文 §6。
- `plugin.json`（每语言 6 条）承载插件元信息与通用错误文案：`plugin.i18n.displayName/description`（本插件自身的显示名/描述），加上 `plugin.error.notLoaded/notFound/protected/dependents` 四条通用插件错误文案。
  - 注意 `plugin.error.*` 的 ns 是 `plugin`，但它的消费方是 plugin-manager 插件的错误提示，而非 i18n 插件自己——i18n 插件顺带承担了"插件管理域通用错误文案"的贡献，这是它作为官方语言插件的职责外溢。
  - `plugin.error.dependents` 带 `{{deps}}` 插值占位（zh-CN 里是 "以下插件依赖此插件: {{deps}}"），对应 i18next 的 `interpolation.prefix="{{" suffix="}}"`（translator.ts L65、i18n-init.ts L35）。
- `shell.json`（每语言 38 条）承载壳 chrome 的界面文案：`shell.settings/backToChat/toggleLeft/toggleRight/openConfig/noConfig/unsavedChanges/discardChanges/confirmChanges/saving/savePrompt/saveAndContinue/componentNotRegistered`、思考档位 `shell.levelOff/levelMinimal/levelLow/levelMedium/levelHigh/levelXhigh`、空态 `shell.newChat/openFolderFirst/kernelRequired/renderFailed/noModels/mainViewEmpty`、配置分层 `shell.saveToGlobal/removeProjectOverride/configSourceProject/configSourceGlobal` 等。
  - 这一命名空间是**壳自身 UI 字符串的来源**——壳不内嵌任何用户可见文案，文案全由 i18n 插件经 `shell.*` key 贡献，壳代码只写 `t("shell.settings")` 这类 key 查询。这是"token key 合规、token 值违规"纪律的直接体现：key 是壳里的稳定契约，值被推到 i18n 插件。

### 4.3 renderer：LanguageSettings 设置页

- `renderer/index.tsx` 是纯 renderer 插件，唯一导出 `LanguageSettings`（L16），供 `contributes.settings[0].component = "LanguageSettings"` 按名自动匹配。
  - 组件签名 `({ refreshSignal }: SettingsComponentProps)`：`SettingsComponentProps`（`packages/react/src/index.ts` L403-409）给设置页组件提供 `refreshSignal`/`config`/`dirty`/`onChange`，但 `LanguageSettings` 只用 `refreshSignal`。
  - 组件内部：`useTranslation()` 拿 `t` 翻译自身标题与描述；`usePluginContext()` 拿 `ctx.i18n.list?.()` 拉语言列表；`useUiStore` 读 `currentLocale`、写 `setCurrentLocale`。
  - 渲染一个 2 列 grid（`gridTemplateColumns: "repeat(2, 1fr)"`，L30），每个语言一个 `ListItem`，`active={currentLocale === l.id}` 决定选中态（radio 圆点，边框色 `--color-primary` vs `--color-border`），点击 `onClick={() => setCurrentLocale(l.id)}`。
  - `useEffect` 依赖 `[ctx.i18n, refreshSignal]`（L23-25），`refreshSignal` 变化时重拉语言列表——对齐框架的设置页刷新按钮语义。

- 组件的文件头注释（L1-6）把设计意图钉死：切语言只调 `useUiStore.setCurrentLocale`（落 prefs），`i18next.changeLanguage` 由 renderer 入口的 locale 订阅自动触发，**插件不碰 shell/i18next，守插件式边界**。

### 4.4 settings 槽：saveMode manual + order 999

- `contributes.settings` 只有一项（plugin.json L92-101）：`id: "language"`、`title: "语言"`、`icon: "globe"`、`component: "LanguageSettings"`、`saveMode: "manual"`、`order: 999`。
  - `saveMode: "manual"` 对应 `SettingsContribution.saveMode`（contributions.ts L23-24）：manual=实时生效，无保存浮层/拦截。语言切换本来就是即时全局生效，没有"未保存编辑"状态，所以走 manual 而非 framework。
  - `order: 999` 把语言设置页排到设置页列表最末（order 小的在前）。
  - `title: "语言"` 是 manifest 里的**字面值兜底**，不是最终显示文案：设置页渲染标题时用 `t(\`settings.${item.id}\`, { defaultValue: item.title })`（`src/web/components/settings-page.tsx` L88、L506），即查 `t("settings.language")`，命中 i18n 插件贡献的 `settings.language` 时显示对应语言名，查不到才回落 manifest 字面值 "语言"。

## 5 双实例翻译器与语言切换

### 5.1 main 侧：translator.ts 的单例与检测

- `translator.ts`（`src/server/application/i18n/`）是 main 侧（application 层）的 i18next 封装，但**实际只在 renderer 侧用到检测纯函数与 IPC 兜底**。
  - `DEFAULT_LOCALE = "zh-CN"`（L12）是"无偏好时的兜底"，`FALLBACK_LOCALE = "en"`（L15）是 fallback 链末端（当前 locale → en → manifest 字面值 → key）。
  - `detectLocale(navigatorLanguage, supported)`（L21-37）是纯函数，两边共用：精确匹配大小写不敏感；`zh-TW/zh-HK/zh-MO/zh-hant` 及 `zh-tw/zh-hk/zh-mo` 前缀 → `zh-TW`，其余 `zh-*` → `zh-CN`，`en-*` → `en`，`de-*` → `de`，匹配不到 → `en`。归约结果若不在 `supported` 里就回退 `en`（L30-35 的 `supported.includes(...) ? x : FALLBACK_LOCALE`）。
  - `initTranslator`（L49-73）持 `initialized` 单例标志防重复 init，配置 `fallbackLng: en`、`defaultNS: common`、`nsSeparator: "."`、`keySeparator: "."`、`interpolation.escapeValue: false`（React 自带转义）、`returnEmptyString: false`（空串当缺失）、不配 `parseMissingKeyHandler`（缺 key 时优先 defaultValue 兜底，否则 i18next 默认返回完整 key）。
  - `t(key, vars?)`（L88-91）在未 init 时直接返回 key 本身，init 后走 `i18next.t`。

- 实际接线：main 侧并不在启动时调 `initTranslator`（渲染查询在 renderer），`detectLocale` 被 IPC 层复用。
  - `src/server/controllers/appearance.ts` 的 `registerAppearance`（L10-22）注册三条 IPC：`IPC.i18n.resources`（返回 `{resources, ns, supportedLngs}`）、`IPC.i18n.list`（返回 `localeList`）、`IPC.i18n.detect`（调 `detectLocale(navigatorLanguage, i18n.supportedLngs)`）。
  - `IPC.i18n.*` 通道名在 `packages/shared/src/channel/channel-contract.ts` L85-88 声明：`detect: "i18n:detect"`、`list: "i18n:list"`、`resources: "i18n:resources"`。

### 5.2 renderer 侧：i18n-init.ts 的初始化与订阅

- `initI18n`（`src/web/app/i18n-init.ts` L14-45）在 `createRoot` 前 await，保证 `useTranslation` 首帧可用。
  - 先 `window.kernel.i18n.resources()` 拿合并后的 resources/ns/supportedLngs；再取 `useUiStore.getState().currentLocale`，若为空则 `window.kernel.i18n.detect(navigator.language)` 检测并 `store.setCurrentLocale(lng)` 落盘（L20-25）。
  - 然后 `i18next.use(initReactI18next).init({...})`，配置与 main 侧 `initTranslator` 完全一致（`fallbackLng: "en"`、`keySeparator: "."`、`interpolation` 同参），随后 `document.documentElement.lang = lng`（L41）。
  - 失败不阻塞 render：整个 try/catch 里 `console.error` 后返回（L42-44），此时 i18next 未 init，`t` 返回完整 key，注释 L6 写明这是"超时兜底"。

- 语言切换有两条等价路径，最终都收敛到 `i18next.changeLanguage` + `document.lang` 同步。
  - `changeLocale(locale)`（L48-52）：显式切——`setCurrentLocale` 落 prefs → `i18next.changeLanguage` → 同步 `document.documentElement.lang`。
  - `subscribeLocaleChange()`（L57-69）：renderer 入口挂一次的订阅——监听 `useUiStore.currentLocale` 变化，变化时若 `i18next.isInitialized && i18next.language !== locale` 则 `changeLanguage`，并同步 `document.lang`。注释 L54-56 写明"插件/设置页只调 setCurrentLocale，locale 切换自动生效"。

### 5.3 locale 持久化：ui-store → prefs

- `useUiStore`（`src/web/stores/ui-store.ts`）是 locale 的运行时真源，`setCurrentLocale`（L286-289）做两件事：`set({ currentLocale })` 更新 zustand 状态，`window.kernel.prefs.set(PREF_KEYS.currentLocale, locale)` 落盘。
  - `PREF_KEYS.currentLocale = "currentLocale"`（L40）是 prefs 里的键名，默认值 `currentLocale: "zh-CN"`（L217 与 hydrate 兜底 L477）。
  - 落盘走 `window.kernel.prefs.set` → main 进程 `JsonPrefsStore`（`src/server/application/config/json-prefs.ts`）——`set` 写内存 `data` 并异步 `writeJsonFile`（L20-23），替代历史 electron-store，用 `config-file` 的 `readJsonFile/writeJsonFile` 原语、不 import electron。

## 6 与其他插件的交互

### 6.1 全局合并：一份 i18next 资源供所有插件 t(key) 消费

- 全仓 38 个插件在 `plugin.json` 声明 `languages` 槽，它们的贡献项与 i18n 插件的 16 条一起进入 `mergeLanguageContributions`，产出一份 `I18nResource`。
  - 这份资源经 `IPC.i18n.resources` 下发到 renderer，renderer 侧唯一 i18next 实例以它初始化——**所有插件的 `t(key)` 共享同一个实例、同一份字典**。
  - 插件的消费方式分两种：React 组件里 `useTranslation()` 拿 `t`（如 i18n 插件自己的 `LanguageSettings` 用 `t("settings.language")`），或经 `usePluginContext()` 的 `ctx.i18n.t(key, vars)`（`packages/react/src/plugin-context.ts` L33-37，`i18nApi` 的 `t` 是 `useTranslation` 的 `t` 的封装）。
  - `I18nApi` 契约在圆心 `packages/shared/src/domain/context.ts` L209-213 定义：`t` 同步查字典、`locale` 当前语言、`list?()` 拿语言列表；renderer 侧 `plugin-context.ts` 只实现 `t/locale/list` 三字段，`list` 走 `window.kernel.i18n.list()`。

### 6.2 共享命名空间：shell/settings/common/plugin 是跨插件的 union

- i18n 插件不是这些命名空间的唯一贡献者，合并器把同名 namespace 的 key 做**跨插件 key 级 union**。
  - `shell` 命名空间：i18n 插件贡献壳 chrome 的 38 条，timeline 插件贡献 `shell.copy/copied/bookmark/bookmarked/emptyMessage/greeting.1/...`（`src/plugins/sessions/timeline/locales/zh-CN/shell.json`），token-stats 也贡献自己的 `shell.*`——三方 key 并进同一 ns，不冲突全保留。
  - `settings` 命名空间：i18n 贡献 `settings.language/languageDesc`，theme-manager 贡献 `settings.font/settings.theme/...`，general-config 贡献 `settings.*`——设置页左列表标题统一用 `t(\`settings.${id}\`)` 查询，各自命中各自的贡献方。
  - `plugin` 命名空间：每个插件贡献自己的 `plugin.{pluginId}.displayName/description`，i18n 插件额外贡献 `plugin.error.*` 四条通用错误——plugin-manager 渲染插件显示名时 `t("plugin.{pluginId}")` 命中对应插件，渲染错误时 `t("plugin.error.protected")` 命中 i18n 插件的贡献。
  - `common` 命名空间：i18n 是主力贡献者（22 条通用动作词），但任何插件都可往 `common` 加 key。

### 6.3 覆盖语义：无特权差异的落地

- i18n 插件是 `source: "builtin"`（`discoverPlugins(builtinDir, "builtin")` 注入），`SOURCE_PRIORITY.builtin = 1` 是全仓最低。
  - 因此任何 `user`/`project`/`installed` 来源的插件贡献同名 key 都会覆盖 i18n 插件的文案（`existing.priority < priority` 时覆盖，L99）。
  - 这意味着第三方语言插件可以覆盖 i18n 插件贡献的任意 key（如覆盖 `common.cancel` 或 `shell.settings`），用户看到的是第三方的文案——壳不"识别 i18n 插件的 key 不让覆盖"，这正是无特权差异纪律（内置壳插件可被更高优先级来源覆盖）在语言槽的直接体现。
  - 同一优先级（如两个 builtin 插件）撞同名 key 时先处理者胜——`registerAll` 的注入顺序与 `mergeLanguageContributions` 的遍历顺序共同决定胜负，结果确定性、不随机。

### 6.4 语言切换的全局效应

- i18n 插件设置页的点击只做一件事：`setCurrentLocale(locale)`，其余全部由框架的订阅链自动完成。
  - `setCurrentLocale` 更新 zustand 状态 → `subscribeLocaleChange` 侦测到变化 → `i18next.changeLanguage(locale)` → i18next 换资源包 → 所有持有 `useTranslation()` 的 React 组件自动重渲染。
  - 整个过程 i18n 插件没有 emit 任何事件、没有 notify 任何插件，它只改共享状态（`currentLocale`），所有订阅者被动响应——这是"插件之间不直接通信，通过共享状态 + 框架订阅间接通信"的落地，i18n 插件与其他插件之间是**单向的产出-消费关系**，没有反向调用。

## 7 纪律边界

- i18n 插件是"机制与内容分离"的正例：壳只提供 `mergeLanguageContributions`/`initI18n`/`subscribeLocaleChange` 这套机制，全部文案值被推到 i18n 插件的 16 个 JSON 文件里。
  - 壳代码里只出现 key（`t("shell.settings")`、`t("settings.language")`），不出现文案值；值（"设置"、"Language"）全部在 `src/plugins/system/i18n/locales/` 里，改文案只动插件 JSON，壳一行不动。
  - 对应 `merge.ts` L141-142、L151-152、L160-162 三处"评估 P3"注释：框架侧一度硬编码了 namespace 清单、四语言清单、四语言展示名，已全部改为从贡献项/合并结果动态收集——这是"内容不进壳"的自我纠偏，本文档记载的是纠偏后的现状。

- i18n 插件自身也守"插件式边界"：`LanguageSettings` 不 import `i18next`、不调 `changeLanguage`，只调 `setCurrentLocale`，i18next 的初始化和切换全部在 shell 的 `i18n-init.ts`。
  - `renderer/index.tsx` 的 import 只有 `react`、`react-i18next` 的 `useTranslation`、`@my-harness-desktop/react` 的五个导出（L7-13），零对 `src/server`/`src/web`/`packages/shared` 内部文件的直接引用。
  - 组件注册走框架自动匹配：`registerPluginComponents`（`packages/react/src/index.ts` L510-530）读 `contributes.settings[].component`，在 module exports 里找同名 `LanguageSettings` 并 `registry.set`，插件不手写 register。

- 契约单源：`LanguageContribution` 只在 `packages/shared/src/domain/contributions.ts` 定义一次，合并器 `merge.ts` 经 `import type { LanguageContribution } from "@my-harness-desktop/shared"` 引用（merge.ts L11），renderer 经 `@my-harness-desktop/react` 的 re-export 兜底，没有第二份"本地版"类型。

## 8 QA

**Q：`LanguageContribution.id`（如 `i18n.common`）和 i18next 的 namespace 是什么关系？**

没有机制上的关系。`id` 只是 `(插件, locale)` 维度的标识，i18next 的 namespace 由**每个 key 的第一个 dot 前的段**决定（`mergeLanguageContributions` L92-95）。`i18n.common` 这个 id 能对应到 ns `common`，纯粹是因为它指向的 `common.json` 里所有 key 都以 `common.` 开头——是命名约定，不是框架约束。你把 `common.json` 的 key 首段改成 `foo`，合并后 ns 就变成 `foo`，id 还是 `i18n.common`。

**Q：为什么 languages 槽在 registry 里不是 `ArraySlot`，而是独立数组？**

因为语言槽的语义是**字典 union**，不是贡献项级二选一。`ArraySlot` 注册时会 `removeById` 去重（同 id 只留后注册者），而语言槽要保留不同插件、不同来源的**全部**贡献项，交给 `mergeLanguageContributions` 做 key 级仲裁（不冲突全保留、冲突按优先级取高）。所以 `PluginRegistry` 专门给 languages 开了一个 `push` 不去重的原始数组（registry.ts L104、L160-162）。

**Q：两个插件贡献了同名同 key 的文案，最终谁赢？**

按 `SOURCE_PRIORITY` 数值：`project(4) > user(3) > installed(2) > builtin(1)`，高值胜（merge.ts L99 的 `existing.priority < priority`）。同优先级（如两个 builtin）时先处理者胜——`registerAll` 按 builtin→installed→user→project 注入，`mergeLanguageContributions` 按数组顺序遍历，等值不覆盖。i18n 插件是 builtin（最低），第三方（user/project）可覆盖它任何 key。

**Q：i18n 插件自己的设置页标题 "语言" 会被翻译吗？**

会。设置页渲染标题的代码是 `t(\`settings.${item.id}\`, { defaultValue: item.title })`（`settings-page.tsx` L88/L506），即查 `t("settings.language")`——命中 i18n 插件贡献的 `settings.language` 时，英文环境显示 "Language"、德文显示 "Sprache"。manifest 里的 `title: "语言"` 只是 defaultValue 兜底（fallback 链末端：当前 locale → en → manifest 字面值 → key 本身）。

**Q：main 和 renderer 各有一个 i18next 实例，会不会文案不一致？**

不会。main 侧的 `initTranslator` 与 renderer 侧的 `initI18n` 用**完全相同的 init 参数**（`fallbackLng: "en"`、`keySeparator: "."`、`nsSeparator: "."`、同 interpolation），且喂给它们的 resources 是同一份 `mergeLanguageContributions` 产物，查询语义一致。main 侧实例主要用于 IPC 兜底和 `detectLocale` 纯函数复用，实际 UI 查询在 renderer 实例上发生。

**Q：加一种新语言（比如法语 fr）要动壳吗？**

不用动壳。在 i18n 插件（或任何插件）的 `locales/` 加 `fr/` 目录与 JSON，再在 `plugin.json` 的 `contributes.languages` 声明 `{ locale: "fr", ... }`。`collectSupportedLngs` 动态收集 locale，`collectLocaleList` 动态生成展示名（缺失 `common.locale.fr` 时回退 code 本身），`detectLocale` 目前只归约 zh/en/de 前缀、其余落 `en`——要识别 `fr-*` 需在 `detectLocale` 加一个 `lang.startsWith("fr")` 分支，但合并/列表/存储链路零改动。

**Q：删掉 i18n 插件，系统会怎样？**

壳照常启动、所有插件照常加载——i18n 插件是 builtin 且无任何插件 `dependsOn` 它。但 `mergeLanguageContributions` 只剩其它插件的语言贡献，`shell`/`common`/`settings`/`plugin.error` 这些 key 大多没了值，`t("shell.settings")` 回退完整 key 或 manifest 字面值，界面退化成"key 模式"（开发者能看，普通用户不能用）。第三方语言插件完全可以替代它：贡献 `languages` + `settings` 即可，且能覆盖任何同名 key。

**Q：i18n 插件的文案为什么是 `shell.*` 而不是 `i18n.*`？**

因为 `shell.*` 是**壳 chrome 文案**的命名空间，i18n 插件只是这些文案的贡献方，不是"i18n 插件的私有文案"。壳代码里 `t("shell.settings")` 查的是壳自己的界面字符串，值被 i18n 插件外挂提供；`plugin.i18n.displayName` 才是 i18n 插件自己的元信息。命名空间按"消费方是谁"划分，不按"贡献方是谁"划分——同一 `shell` 命名空间里还有 timeline、token-stats 等插件贡献的 key，合并器把它们 union 在一起。
