# pi 对话流:消息有状态,接回宽源,渲染走槽位

对话流的核心是会话,会话的契约该写在 `domain` 里——但圆心现在有五个事件走 `{type:string}` 兜底丢了强类型,`content` 是 `unknown` 靠注释和渲染代码反推,`NeutralMessage` 没有 `entryId` 锚点,错误信号散在 RPC 层没聚合进 `SessionEvent`。更根本的问题:`NeutralMessage` 无 `pending`/`stopped`/`error` 状态标记,`applyEvent` 靠"末条是 assistant 就替换它"而非按 messageId 精确 patch,发送时只加 user 乐观回显不等 assistant 占位就发——消息是无状态投影,不是有状态对象。对比 `../toy` demo 的会话流(toy 的 `Message` 带 `pending`/`stopped`/`error`、`patchAssistant(set, convId, assistantId, { content })` 按 id 精确 patch、`send` 同时创建 user+assistant 占位消除空窗、空态 composer 始终钉底不跳变、`onScroll` 驱动 `autoScroll` 用户上滑停跟尾),pi-desktop 的会话流从体验层就是残缺的。这次改造先把这些会话核心契约补齐:消息模型从无状态投影改成有状态对象(`pending`/`stopped`/`error`/`id`);`applyEvent` 从末条替换改成按 messageId patch;发送即创建 assistant 占位;空态 composer 钉底不跳变;智能滚动用户上滑停跟尾。同时补齐圆心契约:事件类型补精确、`ContentBlock` 补判别联合、`entryId` 补透传、圆心加统一 error 事件。pi 底座推的二十一类事件里 `toolCallStart`/`autoRetryStart`/`sessionInfoChanged`/`compactionStart` 被 `applyEvent` 静默丢弃,三十一个命令里 `fork`/`compact`/`set_auto_retry`/`export_html` 十九个零调用——pi 是宽源,桌面端接成了窄漏斗,接回来。会话核心补齐、宽源接回之后,把焊在 `message-list.tsx` 的内容渲染推开:`bashExecution` 分支、divider 图标、空态文案走 `cardRenderers` 槽位可插拔,内核只留 role 透传和流式滚动/光标机制。会话核心对修改关闭,呈现槽位对扩展开放,ChatGPT 风格的光标、头像、scroll-to-bottom、自动命名、hover 操作行(含停止/重新生成/编辑)自然就有地方落。

> **实施状态（截至 2025-07）**：本文档描述的改造已部分落地。§0.3 的 `message-list.tsx` 已外推为 `plugins/timeline/renderer/index.tsx`，壳开 `mainView` 槽由 `MainViewHost` 查槽渲染（commit 375242c）。`bashExecution` 已从圆心 `STANDARD_ROLES` 移除（commit f96ef02）。分隔线文案已从圆心中文改为 i18n token + `i18nArgs`（commit 4edebb6）。`cardRenderers` 槽位尚未实施，bashExecution 分支渲染仍在 timeline 插件内部，未走可插拔渲染器。以下原文保留作为设计动机和未来改造的参照。

## 0 现状:宽源接成窄漏斗,渲染焊在内核

这一节不是源码盘点,是点破三个让对话流"看起来缺一半"的漏斗事实——每个事实落到一个真实符号,作为后面改造的动机。pi 底座能做的远比桌面端用到的多,问题不在 pi,在桌面端把它接窄了。

### 0.1 事件漏斗:pi 推二十一类事件,`applyEvent` 只接六类

pi 底座经 stdout 吐二十一类 `AgentSessionEvent`,经 `src/gateway/event-translator.ts` 的 `TYPE_MAP` 全部翻译成圆心中性事件——这一层是干净的,二十一个 type 全映射、零逻辑、未识别 type 兜底透传。问题出在渲染器侧:`packages/react/src/session-store.ts` 的 `applyEvent` 只处理三个进 messages 的(`messageUpdate`/`messageEnd`/`entryAppended`),加上 `onEvent` 侧的 `agentStart`/`agentSettled`/`agentEnd`/`modelSelect` 算六个,其余全部走 `return messages` 静默丢弃。

被丢的不是边角料,恰恰是对话流体验最该有的那批:

- `sessionInfoChanged`——pi 主动推会话信息变化(含会话名),是自动命名的银弹,但圆心没建模成精确类型、renderer 直接丢。
- `toolCallStart`/`toolCallUpdate`/`toolCallEnd`——工具执行的开始/进度/结束(带 `isError`),对话流里看不到工具在跑,只能等 `messageEnd` 一次性带出来。
- `autoRetryStart`/`autoRetryEnd`——自动重试第 N 次、成功与否,用户看到的是"卡住"而非"正在重试"。
- `compactionStart`/`compactionEnd`、`thinkingLevelChanged`/`thinkingLevelSelect`、`turnStart`/`turnEnd`、`queueUpdate`——同样被丢。

这不是 pi 不喊,是桌面端没在听。`event-translator.ts` 把二十一类都翻成了中性事件,`src/application/sessions/session-store.ts` 的 `dispatch` 也全部转发给了 listeners(只过滤非激活会话),是 renderer 的 `applyEvent` 把它们吃了。被丢弃的能力,不是要去 pi 那边要,是在桌面侧把漏斗扩开。

### 0.2 命令漏斗:三十一个 RPC 命令,`window.pi.sessions` 暴露十二个

`src/gateway/protocol/rpc-types.ts` 的 `RpcCommand` 联合定义了三十一个命令,`src/gateway/protocol/versions.ts` 的 `FALLBACK_COMMAND_SET` 与之一一对齐。但 `src/shell/electron-main/preload.ts` 经 `window.pi.sessions` 暴露到渲染器的只有约十二个:`prompt`/`abort`/`get_state`(经 sync)/`get_available_models`/`set_model`/`get_available_thinking_levels`/`set_thinking_level`/`get_session_stats`,加上 `resync` 一次拉齐的 `get_entries`/`get_tree`/`get_messages`/`get_commands`。

剩下十九个零调用,其中几个是对话产品的标配:

- `fork`/`clone`/`switch_session`/`get_fork_messages`——对话分支四件套,协议层全有,`SessionStore` 一行没接。重新生成、编辑历史后重发,全靠这套。
- `compact`/`set_auto_compaction`——手动压缩 + 自动压缩开关,长会话刚需。
- `set_auto_retry`/`abort_retry`——重试策略,命令没接(但事件 `autoRetryStart/End` 翻译了,开关却没暴露)。
- `export_html`——分享/导出会话。

`src/gateway/protocol/commands.ts` 只给七个命令配了构造器(`prompt`/`get_state`/`get_entries`/`get_tree`/`get_commands`/`set_model`/`abort`),其余命令 application 层裸拼字面量(`resync` 里 `{ type: "get_messages" }`、`getStats` 里 `{ type: "get_session_stats" }`)。这不算违规——类型由 `RpcCommand` 联合守住——只是构造器没补全,新接命令时顺手补。

### 0.3 渲染焊死:`cardRenderers` 槽位在 `SlotName` 预留名字、`PluginContributes` 没接字段

`src/domain/contributions.ts` 的 `SlotName` 联合里已经有 `"cardRenderers"` 这个名字(第 79 行),但同文件 `PluginContributes` 接口(第 87–95 行)只有 `themes/settings/sidePanel/sidebar/languages` 五个数组字段,没有 `cardRenderers` 字段——注释写着"其余槽随各阶段补"。全代码库 grep `cardRenderers` 只出现这一次,loader/registry/渲染层都没读它。槽开了门没装:插件在 manifest 里写 `contributes.cardRenderers` 会被加载器当未知字段忽略。

与此同时,对话流渲染焊在 `src/shell/renderer/components/message-list.tsx`,这个文件同时背着用户气泡、AI 流式文本、思考块、bashExecution 终端、divider、custom_message 兜底六种角色的渲染。其中 `message.role === "bashExecution"` 的专门分支(第 292–315 行)——Terminal 图标、`$ {cmd}` 前缀、exit code 红字、`color-mix` 深底——正是 `CLAUDE.md` §1.2 原文点名的反模式:"如果工具名是 bash 就渲染成终端"。`DIVIDER_ICONS`(第 370–378 行)把 `model/thinking/compaction/branch/info/label/entry` 这些 kind 和 lucide 图标绑死,同属内容焊在内核。

还有四处硬编码中文绕过 i18n(同文件别处都走 `t("shell.*")`):`message-list.tsx:195` "从左栏打开一个文件夹开始"、`:226` "agent 思考中…"、`:238` "切换会话…"、`:331` "思考过程"。这是铁律一"token 值违规"的实例——token key 合规(`theme["color.primary"]`),token 值违规(写死文案)。

### 0.4 顺手发现的死锁风险:`extension_ui_request` 监听器是空的

这条不属对话流,但顺路发现的风险越早修越安全。pi 底座有一类反向调用 `extension_ui_request`(`select`/`confirm`/`input`/`editor`/`notify`/`setStatus`/`setWidget`/`setTitle`/`set_editor_text`),由底座发向桌面端请求用户交互。`src/gateway/rpc-adapter.ts` 的 `onExtensionUI` 监听器接了转发,但 `src/shell/electron-main/index.ts` 里没有 handler 处理这些请求,下行 `extension_ui_response` 也没发回。

这是个潜在死锁:底座一旦依赖 extension_ui 响应才继续(比如发一个 `confirm` 等用户确认),桌面端静默吞掉,底座永远等不到响应,会话卡死。它和对话流的窄漏斗是同一类病——机制层接了,应用层没接——但后果更严重(死锁 vs 体验缺失)。修复方向在 L0 顺手做:handler 缺失时至少回一个默认响应,避免底座无限等待;或补完整的 UI 请求分发 + 弹窗 + 回填。前者是兜底,后者是完整。这次取完整。

## 1 分界原则:会话核心留 domain,呈现内容走槽位

前面三个漏斗是症状,根因是一条没划清的分界线。会话和呈现是两层东西,开闭原则落在它们之间,不是落在"内核 vs 会话"之间——这个区分搞错,就会把会话本身当内容推出去,或者把呈现焊死在会话核心里。这一节划清这条线,后面 L0–L4 各层都挂在这条线上。

### 1.1 会话是核心,这次是补齐 `SessionsApi`/`sessionEntryToNeutral` 不是外推

会话是对话流的业务本质。`src/domain/sessions.ts` 的 `SessionsApi` 契约、`src/domain/events/session-state.ts` 的 `SessionEvent` 联合和 `sessionEntryToNeutral` 纯函数——换掉 Electron、换掉 React、换掉 SQLite,它们都不该动。这是圆心"换壳测试"该通过的:明天把 Electron 换成 Tauri、把 React 换成 Vue,`SessionsApi` 还在不在?在。它是圆心。

但圆心现在有缺口,这些缺口不是"会话太重该推出去",而是会话核心契约本身没补齐:

- 五个事件(`turnStart`/`turnEnd`/`sessionInfoChanged`/`thinkingLevelChanged`/`thinkingLevelSelect`)走 `{type:string;[k:string]:unknown}` 兜底,丢了强类型,下游没法消费——不是会话不该管这些,是会话没把它们建模出来。
- `content` 字段是 `unknown`,块结构(`text`/`thinking`/`toolCall`)靠注释和渲染代码反推,每个渲染器自己 `as Record<string,unknown>` 取字段——这是契约漂移的温床,圆心该定义 `ContentBlock` 判别联合。
- `NeutralMessage` 没有 `entryId` 字段,而 `SessionEntry.id` 是有的——fork 需要这个锚点,圆心该透传上来。
- 进程 crash、RPC reject、`autoRetryEnd(success:false)`、`toolCallEnd.isError` 四类错误信号散在 RPC 层和被丢的事件里,圆心 `SessionEvent` 没有统一 error 类型——错误是会话状态的一部分,该在圆心建模。

所以 L0 做的是强化会话核心,不是弱化它。补完这些,`SessionsApi` 更稳、更强类型、更经得起演化,会话核心的地位不是下降是上升。这点要强调,因为"机制与内容分离"这个说法容易被误读成"把会话也推出去"——不是,推出去的是呈现(下一节),会话核心往里收。

### 1.2 开闭落在会话核心与呈现之间:核心对修改关闭、槽位对扩展开放

开闭原则的两面,分别落在两个地方:

会话核心(domain 契约)对修改关闭。`SessionsApi`、`SessionEvent`、`ContentBlock`、`NeutralMessage` 这些契约补齐之后,新增一种工具卡片不该改 `domain/sessions.ts`,新增一种 divider kind 不该改 `sessionEntryToNeutral` 的分支。圆心 `role` 设计成开放 `string` 而非判别联合,正是为了这个——`session-state.ts:94` 有意让 role 是字符串,任何底座新 role 或插件 customType 都能透传,圆心不枚举业务 role。这是"对修改关闭"在类型层的落地:加一种 role 不改圆心。

呈现内容(cardRenderers 槽位)对扩展开放。`message-list.tsx` 里焊死的 `bashExecution` 分支、`DIVIDER_ICONS`、`CustomCard`、空态布局——这些是会话的呈现,不是会话本身。它们走 `cardRenderers` 槽位可插拔:加一种工具卡片渲染器,贡献一个 `match:"bashExecution"` 的渲染器即可,不改内核 `MessageRow`。bashExecution 作内置插件贡献,走同一槽位、同一匹配规则、同一优先级——这是 `CLAUDE.md` §1.4 无特权差异的落地:内置渲染器和第三方"git-review 卡片渲染器"平等。

这条线划在"会话核心 vs 呈现内容"之间,不是"内核 vs 会话"之间。划错了有两个坏结果:把会话推出去,圆心空了,换壳测试过不去;把呈现焊在会话核心里,加一种卡片要改 domain。两条都是架构腐化。这条线划对了,L0 补齐会话核心(对修改关闭)、L2 接上呈现槽位(对扩展开放),两面同时成立。

### 1.3 消费而非翻译:不翻译底座 UI,只消费结构化数据

`CLAUDE.md` §3.1 的原发原理:不要把自己定位成别人的翻译层。本项目的教训是现有方案把桌面端定位成"底座 extension 的 UI 翻译层",造了三十几个纯 JSON adapter 翻译底座的 TUI 组件树——Web 吃不下终端组件,只能退而求其次。pi-desktop 重新来过:不翻译,只消费。底座经 RPC 吐出结构化数据,桌面插件自己决定怎么画。

这条原理在对话流改造里有两个具体边界:

协议层该翻译还是要翻译。底座经 stdout 吐 JSON Lines,`src/gateway/event-translator.ts` 把它翻译成中性 `SessionEvent`——这是协议翻译,把一种数据格式转成另一种(JSON → TypeScript 对象),是必要的边界工作。L0 补齐事件类型,做的是这条线上的事:把走兜底的五个事件在圆心建模出精确类型,translator 产出的中性事件才有强类型归宿。

UI 层不翻译。底座不吐 TUI 组件树,吐的是结构化消息(`role`/`content` 块/`entryId`),桌面端拿到数据自己画——用什么组件、什么布局、什么交互,是桌面的事,和底座无关。`cardRenderers` 槽位是这条原理的落地:插件消费 `NeutralMessage` 的 role 和 content,自己贡献渲染器,内核不翻译底座的 UI 意图。`bashExecution` 不是"翻译底座的 bash 终端",是"消费 `role:"bashExecution"` 的消息,桌面插件自己画成终端样"——一字之差,前者是被动翻译(追底座变化),后者是主动消费(底座吐什么数据我决定怎么画)。

这条边界守住,L1 接回事件(消费更全的数据)和 L2 接上槽位(消费方式可插拔)才不会走回翻译层的老路。

## 2 L0 圆心契约补齐:会话核心对修改关闭

### 2.1 事件类型补精确:五个走 `{type:string}` 兜底的事件收口

圆心 `SessionEvent` 联合显式建模了 17 个事件类型,其余一律落 `{ type: string; [key: string]: unknown }` 兜底(`src/domain/events/session-state.ts:161`)。translator 的 `TYPE_MAP` 把 pi 的 21 个 type 全翻了名(`src/gateway/event-translator.ts:10-33`),但圆心只认 17 个,中间差的那 5 个——`turnStart`、`turnEnd`、`sessionInfoChanged`、`thinkingLevelChanged`、`thinkingLevelSelect`——翻译完照样走兜底。名字翻了,类型没翻,下游拿到的还是 `unknown`。

兜底的代价不是"少个类型标注"那么轻。消费者要读字段,只能 `as Record<string, unknown>` 现取——字段名靠人记、靠注释、靠看 pi SDK 猜,编译器一字节都不把关。这和 §2.2 要解决的 `content: unknown` 是同一种病:圆心不建模,漂移就散到每个消费点。

五个事件分两类。`turnStart`/`turnEnd` 是一轮对话的边界——pi 推这两类标记一个 turn 的起止,renderer 现在完全无感,流式状态只能靠 `messageStart`/`messageEnd` 间接推。`sessionInfoChanged`/`thinkingLevelChanged`/`thinkingLevelSelect` 是会话级状态变更——其中 `sessionInfoChanged` 是 H5 自动命名的银弹:pi 给会话自动起了名,推一条事件让前端知道新名字。预期它带 `name` 字段,但这要实证。

实证的态度要诚实。`sessionInfoChanged` 带什么字段,不能照"名字就叫 sessionInfoChanged,那肯定带 name"想当然——pi 可能推 `{ type, name }`,也可能推 `{ type, sessionId, name }`,甚至把重命名拆成 `session_info` 条目走另一条路(§2.3 的 `sessionEntryToNeutral` 已经在处理 `session_info` 条目,见 `session-state.ts:202`)。圆心这一节先按调研预期建模:`SessionInfoChangedEvent { type: "sessionInfoChanged"; name?: string }`,字段标 optional,注释写明"待实证确认 pi 实际推送字段"。§3 上探针抓真实事件流后,字段定不准就回来修圆心——这是契约单源的好处,改一处全链路同步。

另外四个同理建模。`turnStart`/`turnEnd` 带 `turnId?: string`(待实证 pi 是否给 turn 编号);`thinkingLevelChanged` 带 `level?: string`(已变更后的新强度);`thinkingLevelSelect` 带 `level?: string`(用户选择的目标强度,与 changed 的语义差在一个是已落地一个是候选——待实证区分)。四个 interface 加进 `SessionEvent` 联合显式列出,五个不再走兜底。

兜底不删。pi 未来还会推新事件,圆心没建模的不该丢,兜底 `{ type: string; [key: string]: unknown }` 留着给未识别事件原样透传——这和 §2.2 `ContentBlock` 的开放兜底是同一个设计哲学:已知的精确、未知的兜住。删兜底等于赌"pi 再也不会加新事件",这个赌输的代价是静默丢事件。

补完谁受益。renderer 的事件流 effect(`message-list.tsx:108-114`)现在只认 `messageEnd`/`agentSettled`/`agentEnd` 三个 type 刷新统计,`turnEnd` 来了它不知道——补精确后,`turnEnd` 可以作为更准的统计刷新点(一轮真结束)。`sessionInfoChanged` 让侧栏会话列表能实时更新会话名,不用等下次 resync。`thinkingLevelChanged` 让 composer 的思考强度指示器跟着变,不必轮询 state。所有消费者从 `as Record` 取字段换成 `event.name`/`event.level` 直读,编译器挡住打错字段名。

### 2.2 `ContentBlock` 判别联合:`content` 不再是 `unknown`

`NeutralMessage.content` 现在是 `unknown`,注释写着"string 或内容块数组([{type:"text"|"thinking"|"toolCall",...}])"(`session-state.ts:95`)。圆心知道有块、知道块的 type 字段,但不定义块长什么样。结果是每个渲染器自己 `as Record<string, unknown>` 现取字段——`message-list.tsx:34-58` 三个提取函数就是现成样本:`textOf` 滤 `c.type === "text"` 取 `c.text`,`thinkingOf` 滤 `c.type === "thinking"` 取 `c.thinking ?? c.text`,`toolNamesOf` 滤 `c.type === "toolCall"` 取 `c.name`。三个函数各自把 `content` 当 `unknown` 现拆,字段名 `text`/`thinking`/`name` 全靠人记,pi 哪天把 `thinking` 改名 `reasoning`,这里编译不报错,运行时静默取空——漂移就这样长出来。

判别联合把字段名焊死在类型上。圆心定义 `ContentBlock` 联合:

- `TextBlock { type: "text"; text: string }` —— 纯文本块。
- `ThinkingBlock { type: "thinking"; thinking: string; text?: string }` —— 思考块,`text` 留作兼容 fallback,renderer 取 `thinking ?? text` 的逻辑直接落进类型。
- `ToolCallBlock { type: "toolCall"; name: string; toolCallId?: string; args?: unknown; result?: unknown; isError?: boolean }` —— 工具调用块,`toolCallId` 标"待实证"(pi 是否在 content 块里带 toolCallId,还是只在顶层 `ToolCallEnd` 事件里带,§3.5 接),先标 optional 占位。
- `ImageBlock { type: "image"; data: string; mimeType: string }` —— 图片块,同构于 `gateway/protocol/rpc-types.ts:22-26` 已有的 `ImageContent`。
- 兜底 `{ type: string; [key: string]: unknown }` —— 开放扩展。

兜底这一项是关键,它呼应 `NeutralMessage.role` 的设计哲学。`role` 在圆心是 `string` 不是 `"user" | "assistant"` 联合(`session-state.ts:94`),原因是插件可以贡献 `custom_message` 带任意 `customType`,`role` 得开放。`ContentBlock` 同理:pi 现在推 text/thinking/toolCall/image 四种,明天可能推 `reasoning`、`citation`、`toolResult` 块——圆心把它们焊死成闭联合,新块一来编译报错、运行时丢;留兜底 `{ type: string; [k]: unknown }`,新块原样透传,renderer 兜底渲染原始 JSON(和 `sessionEntryToNeutral` 末条 `divider(String(e.type), "entry", ...)` 的兜底逻辑同构,见 `session-state.ts:213`)。已知的精确、未知的兜住,不是非此即彼。

`ImageBlock` 和 `ImageContent` 的关系要顺手收。两者结构同构(`{ type: "image"; data: string; mimeType: string }`),但一个在圆心、一个在 gateway/protocol——契约单源说概念只有一份定义,这里有两份。正解是圆心定义 `ImageBlock`(或直接叫 `ImageContent`,圆心零依赖,纯 TS 类型),gateway 的 `ImageContent` 改成 `export type { ImageBlock as ImageContent } from "../../domain/events/session-state"` 的 re-export。这样 `prompt` 命令的 `images` 参数(`rpc-types.ts:72`)和 assistant 消息里的图片块用同一个类型,改一处两处同步。这一步是 §2 顺带做的契约对齐,不顺带做就是埋一份同构副本等漂移。

`content` 字段类型从 `unknown` 改成 `string | ContentBlock | ContentBlock[]`。留 `string` 是向后兼容——pi 的 `get_messages` 可能直接返回字符串 content(纯文本消息),`sessionEntryToNeutral` 现有分支也透传 string。联合三种形态,renderer 用 `typeof content === "string"` 早返回,数组走判别联合,单块走兼容。

收益落到 renderer。`textOf` 从 `content.filter(c => c.type === "text").map(c => String(c.text ?? ""))` 变成有类型守卫的 `content.filter(isTextBlock).map(b => b.text)`——`isTextBlock` 是 `(c: ContentBlock): c is TextBlock => c.type === "text"`,编译器在 `b.text` 处知道是 string,不用 `String()` 包。`toolNamesOf` 同理,`b.name` 直读。新块类型加进联合,所有消费点编译器强制更新字段访问——漂移从"运行时静默取空"变成"编译期报错",这是圆心契约该有的约束力。

### 2.3 `NeutralMessage` 补 `entryId`:fork 的锚点

`MessageEntry` 有 `id`(`session-state.ts:68`),那是会话树条目的标识。但 `NeutralMessage`——renderer 真正拿来画对话的那条消息——没有 `entryId`。`sessionEntryToNeutral`(`session-state.ts:172-214`)把 entry 翻成 NeutralMessage 时,只透传 `role`/`content`/`timestamp`,`e.id` 一路丢。结果是 renderer 拿到的 messages 数组里,每条消息都不知道自己是哪个 entry。

这直接卡死 fork。`fork` 命令参数是 `{ type: "fork"; entryId: string }`(`rpc-types.ts:95`)——fork 一条消息,得告诉 pi 从哪个 entry 分叉。但 renderer 没有 `entryId`,Fork UI 按下"从这里分叉"时,手上只有一条 NeutralMessage,传不出 anchor。这是 H6 的根因:不是 fork 命令没实现,是 fork 的输入锚点在圆心契约这一层就断了。

改法是 `NeutralMessage` 加 `entryId?: string`,然后 `sessionEntryToNeutral` 每个返回分支把它带上。注意 `message` 分支(`session-state.ts:177-179`):现在是 `return { ...(e.message as Record<string, unknown>), timestamp: ts }`,展开 `e.message` 在前——如果 `e.message` 里恰好有同名字段会被覆盖,反之 `e.id` 会被 `e.message` 里的字段盖掉。`entryId` 要显式放在展开后:`return { ...(e.message), entryId: typeof e.id === "string" ? e.id : undefined, timestamp: ts }`,保证 entry 的 id 不被 message 内容覆盖。`custom_message` 分支(`session-state.ts:182-187`)和 `divider` 合成分支(`session-state.ts:216-218`)同理带 `entryId`——divider 是合成的居中分隔线,严格说它不是用户消息、不该被 fork,但带上原 entry id 不亏(fork UI 对 divider 不挂 fork 按钮,entryId 留着不用就是),不带反而是丢信息。

透传后链路接通。renderer 的 `MessageRow` 拿到 `message.entryId`,Fork UI 从这里取锚点直传 `pi.sessions.fork(message.entryId)`;session-store 在 `appendOptimisticUser`/事件应用时保留 `entryId`,不丢。`entry_appended` 事件(`EntryAppendedEvent`,`session-state.ts:140`)带来的新 entry 也能经 `sessionEntryToNeutral` 染上 `entryId`,流式追加的消息同样有锚点。H6 在这一层闭环:fork 命令、renderer、session-store 三方对 `entryId` 的认知统一到圆心一份契约,不再各猜各的。

`entryId` 标 optional 而非 required,是有意。`sessionEntryToNeutral` 对 `session` 条目(文件头,`session-state.ts:211`)和 `custom` 扩展私有状态返回 `null`,这些根本不进 messages;对未知条目走 divider 兜底,`e.id` 可能不存在。optional 让"有 entry id 的带上、没有的留 undefined"自然表达,renderer 用 `message.entryId` 判断"这条能不能 fork"——没有 entryId 的不是对话消息,不挂 fork 按钮。required 会逼着给所有分支硬填一个假 id,语义更乱。

### 2.4 统一 `SessionErrorEvent`:进程 crash/RPC reject/autoRetry 失败/toolCall isError 四类聚合

四类错误信号现在散在四个角落,没有一个进事件流。

进程 crash 走的是 RPC 层 reject。`rpc-adapter.ts:93-103` 的 `onceExit` 把进程退出合成 `RpcProcessError`,调 `this.correlator.rejectAll(err)`——这是把所有在途命令的 Promise reject 掉,信号只到 await `adapter.send` 的调用方(session-store.prompt),不进事件流。renderer 订阅的是 `pi.sessions.onEvent`,收到的是 `SessionEvent`,进程死了一个 `SessionEvent` 都不会有,UI 只能靠"发送按钮突然 throw"间接感知。

RPC reject 是命令级失败。pi 返回 `{ type: "response", success: false, error: "..." }`,correlator resolve 出来的是失败 response,session-store.prompt 的 `await adapter.send` 拿到后 throw。这个 throw 只到调用方,renderer 的 `.catch(() => {})` 把它吞了(`message-list.tsx:142,146` 是 setModel/setThinkingLevel 的静默 catch,prompt 路径是 `console.error` 后 `finally` 收场,见 `message-list.tsx:157-162`)。用户看到的是"发送没反应",不知道是 pi 报了错。

autoRetry 和 toolCall isError 是"已经被翻译却静默丢弃"的两个。`autoRetryStart`/`autoRetryEnd` 已在圆心建模(`session-state.ts:149-150`),`autoRetryEnd` 带 `success?: boolean`——重试失败时这个字段是 false,但 renderer 的事件 effect 只看 `messageEnd`/`agentSettled`/`agentEnd`(`message-list.tsx:110`),`autoRetryEnd` 来了什么都不做。`toolCallEnd` 带 `isError?: boolean`(`session-state.ts:129`),工具执行失败时为 true,同样静默丢弃。两类错误信号明明已经在事件流里了,消费者却当没看见。

统一抽象:四类是同一个东西——"会话错误"——的不同来源,不是一个东西的四种 if 分支。圆心定义一个 `SessionErrorEvent` 贯穿,四类是它的 `source`:

```
SessionErrorEvent {
  type: "sessionError";
  source: "processCrash" | "rpcReject" | "autoRetry" | "toolCall";
  message: string;
  toolCallId?: string;   // source === "toolCall" 时带
  recoverable?: boolean; // 进程死=false,其余默认 true
}
```

`source` 是判别联合的 tag,但它和"反 kind-switch"不冲突。区别在于:事件 `type`(和这里的 `source`)是消费者读的数据——renderer 拿 `source` 决定怎么渲染这条错误(crash 画"进程已退出"、toolCall 画"工具 X 失败"),不是引擎拿 `source` 去 switch 外挂分支。四类的合成发生在 application 的四个不同触发点,不是"一个地方收了之后 switch source 分流"——这点必须守住,否则就是声明式类型标签驱动引擎,违反对齐。

聚合放在 application(session-store 的事件 reducer),不放 gateway。依赖方向决定:gateway 只翻译 pi 协议事件(stdout 推的 `AgentSessionEvent`),processCrash 和 rpcReject 根本不是协议事件——前者是传输层进程退出信号,后者是命令响应的 success:false,它们不是 pi "推"的,是 rpc-adapter 在收发过程中产生的。translator 没有素材合成它们,硬塞进 translator 就是让 gateway 知道它不该知道的东西(进程生命周期)。application 是事件流的状态机汇聚点,四个触发点在此合成同一个 `SessionErrorEvent`:

- **processCrash**:`rpc-adapter` 的 `onceExit` 已经 rejectAll,session-store 额外订阅 adapter 的进程死信号(经 `lastError` 或新增 `onDead` 出口),合成 `SessionErrorEvent({ source: "processCrash", recoverable: false })` 推进事件流。
- **rpcReject**:session-store.prompt 的 `await adapter.send` throw 时,catch 里除了 console,再合成 `SessionErrorEvent({ source: "rpcReject", message: err.message, recoverable: true })` 推进事件流——进程还活着,用户可重试。
- **autoRetry**:reducer 收到 `autoRetryEnd` 且 `success === false`,合成 `SessionErrorEvent({ source: "autoRetry", recoverable: true })`。translator 不动,它已经翻对了,聚合在消费侧判字段。
- **toolCall**:reducer 收到 `toolCallEnd` 且 `isError === true`,合成 `SessionErrorEvent({ source: "toolCall", toolCallId: event.toolCallId, recoverable: true })`。

四个触发点产同一个类型,renderer 只需订阅 `SessionEvent` 里新增的 `sessionError` 一种,按 `source` 渲染。这是"框架管通用,特化归外层"的落地:application 管四类信号的汇聚合成(通用),renderer 管每种 source 画成什么样(特化)。

失败路径里最难的是进程 crash 时 messages 数组怎么处理。已收到的消息不能丢——那是用户和 assistant 已经产生的对话,进程死不是它们的错,标错会污染原消息语义(assistant 的部分回复本身没问题,错的是进程后续不工作了)。也不能在末条标错,因为"末条"可能是一条正在流式的 assistant 消息,标错等于说"这条消息是错的",而它只是没流完。正解是 `SessionErrorEvent` 推进事件流,renderer 收到后自己决定渲染——画一条独立的 error 条目(role 借 `"divider"` 的合成模式或新增 `"error"` role,renderer 现有 `MessageRow` 对未知 role 走 `CustomCard` 兜底,见 `message-list.tsx:318`,正好能接),不碰已收到的 messages。进程死同时标记 state:`isStreaming: false` 收尾流式,加一个 `processAlive: false` 让 composer 禁用发送按钮、提示"进程已退出,需重启"。事件负责时序(错误在某个时刻发生),state 负责状态(进程现在死着),两者不冲突。

`recoverable` 是给 renderer 和 composer 的决策输入,不是给引擎的开关。`processCrash` 的 `recoverable: false` 让 composer 禁发并提示重启;`rpcReject`/`autoRetry`/`toolCall` 的 `recoverable: true` 让 composer 允许重试。renderer 也可以读它决定 error 条目是红色(crash)还是黄色(toolCall)——但这是渲染决策,不是引擎分支。圆心只提供数据,不指挥行为。

这一节的四件事——事件补精确、ContentBlock 判别联合、entryId 透传、SessionErrorEvent 聚合——都是 L0 的圆心契约补齐,不动 gateway 翻译逻辑、不动 renderer 渲染、不动 session-store 编排,只在 `domain/events/session-state.ts` 加类型定义。地基稳了,L1 的 translator 对齐、L2 的 session-store reducer 接入、L3 的 renderer 消费、L4 的 cardRenderers 槽位填充,才有强类型可依。圆心对修改关闭,靠的不是"不让改",是"改圆心的一处辐射到所有消费点"——契约单源让修改的成本收敛到一处,这才是"对修改关闭"的工程含义。

## 3 L1 事件漏斗扩宽:接回被丢的能力

### 3.1 `applyEvent` 从窄漏斗改选频消费,不是全接

§0 看到的窄漏斗是真窄:`packages/react/src/session-store.ts` 的 `applyEvent` 只对 `messageUpdate`/`messageEnd`/`entryAppended` 三类动 `messages`,其余十四类 `return messages` 原样退回,语义就是丢。`onEvent` 那侧(同文件 118 行)另外接了 `agentStart`/`agentSettled`/`agentEnd` 管 `streaming` 旗、`modelSelect` 更新 `snapshot.state.model`,四类之外还是退。但"接回被丢的能力"不等于"21 个事件全灌进 `messages` 数组"。那是另一种灾难。

判据是去路,不是来路。三类去路按"一年后会不会重放回看"分:**持久进 `messages`** 的是消息类——`messageStart`/`messageUpdate`/`messageEnd`/`entryAppended`,它们就是会话本身,文件读基线和事件流增量都该长在 `messages` 上,这一类扩宽只补 `messageStart`(开个空 assistant 占位,让 `streaming` 期间时间线有地方落字)。**进单独 store 切片**的是工具执行状态和错误/重试——`toolCallStart`/`Update`/`End` 一组、`SessionErrorEvent` 一组、`autoRetryStart`/`End` 一组。它们不是消息,塞进 `messages` 会让时间线变成"消息+工具+错误+重试"混拌泥,文件读基线和事件流增量也对不齐(工具事件是流式瞬时,重读会话时它们已经过期)。所以另开切片:`toolExecutions: Record<toolCallId, ToolExecutionState>`、`errors: SessionError[]`、`retrying: { attempt: number } | null`,组件用 selector 读,不污染 `messages`。**瞬时反馈不持久**的是 `compactionStart`/`End` 和 `queueUpdate`——压缩进度是"现在正在压",下一轮对话开始这条反馈就过期了,排队计数同理。这类只在 Footer/UI 标志位驱动渲染,落一个 `feedback: { compacting?: {reason}; pending?: number } | null` 派生态,`agentEnd` 一到就清。

为什么不全接?两个理由,一个是噪声,一个是膨胀。噪声:`messages` 是时间线,是用户滚回去要能完整复现一轮对话的东西。把 `toolCallStart` 追加进 `messages`,滚回去看到的是"工具开始了但没结果"的半截状态,因为 `toolCallEnd` 在另一轮才到——这不是信息,是误导。膨胀:`messages` 会被 `Virtuoso` 全量 key 化、会被文件读基线对比去重、会被 `textOf`/`toolNamesOf` 反复扫。一个工具调用拆成三条 `message` 元素塞进去,百轮对话下来 `messages` 翻三倍,虚拟滚动白 key 一堆不展示的瞬时态。切片就没事——切片是 `Map`,按 `toolCallId` 配对是 O(1),组件只读它关心的那一条。

这条对应 CLAUDE.md §3.3 框架管通用:工具执行/错误/重试的消费,多个组件(时间线渲染工具卡、Footer 显示重试、sessions-list 副标题要统计工具数)都要,该收进 store 统一承担,不让每个组件各自 `onEvent` 各写一遍。当前 `message-list.tsx` 109 行那条 `pi.sessions.onEvent` 监听只为了 `messageEnd`/`agentSettled`/`agentEnd` 刷统计——已经是"组件各自订阅事件流"的雏形,本节要把这种订阅收敛进 store。

### 3.2 工具执行落进 store:按 `toolCallId` 配对 toolCallStart/Update/End

`toolCallStart`/`Update`/`End` 三个事件(`src/domain/events/session-state.ts:114-130`)都带 `toolCallId`,这是配对键。start 携 `toolName` + 可选 `args`,update 携可选 `partialResult`,end 携可选 `result` + `isError?`。配对就是按 `toolCallId` 往 `toolExecutions: Record<string, ToolExecutionState>` 这个切片里写:

- start 建:`{ toolCallId, toolName, args?, status: "running", partialResult?: undefined, result?: undefined, isError: false, startedAt }`。没有的 end 之前,卡片显示"运行中"。
- update 填:`{ ...prev, partialResult: event.partialResult ?? prev.partialResult }`。流式工具(如长跑 bash、流式搜索)一边跑一边喂 partial,卡片跟着长。
- end 落:`{ ...prev, result: event.result, isError: event.isError ?? false, status: "done" }`。卡片定稿,`isError` 决定红边还是正常边。

三条事件按 `toolCallId` 同一 key 更新同一 record,store 是纯函数 `applyEvent` 之外再开一个 `applyToolEvent(toolMap, event)`,和 `applyEvent` 并列在 `initSessionStore` 的 `onEvent` 里调,各管各的切片。`agentEnd` 到了清 `toolExecutions` 里 `status==="done"` 的(或整轮清空,看 §6 定的会话边界),避免切片无限长。

这条要注意一个事实:工具的 `name` 同时出现在两个地方。`message.content` 块里有 `{ type:"toolCall", name:"bash" }`(`message-list.tsx:48` 的 `toolNamesOf` 就是抽这个),事件流里 `toolCallStart.toolName` 也有。两条数据通道:`name` 在 `content` 块(定稿后随 message 落盘),`args`/`result`/`partialResult`/`isError` 在事件流(不落 `message.content`)。当前 pill 只有 name 没结果,根因就在这——`toolNamesOf` 只读 content 块的 name,事件流的结果被 `return messages` 丢了。接回后协调方式:渲染工具卡时,从 `message.content` 块拿到 `name`(以及 `toolCallId` 如果块里有,见 §3.5),再用 `toolCallId` 去 `toolExecutions` 切片查结果。`name` 仍是 content 块主,事件流只补 args/result——避免一条 name 在两处各写一遍漂移。

组件怎么消费:`useToolExecutions(toolCallId?)` selector 返回切片或单条。时间线里渲染 assistant 气泡时,先扫 `message.content` 的 `toolCall` 块拿 name 和(若有)toolCallId,再去切片查结果,渲染成可展开的执行卡(运行中转圈、完成可看 args/result、错误红条 + result)。pill 退化成卡片的折叠态——卡片合起来就是 name,展开才是 args/result,现有 pill 样式不丢,只是多了内容。

### 3.3 错误与重试接回:驱动 inline 红条和"重试第 N 次"反馈

错误分两类,接回方式不同。**进程级错误**(`RpcProcessError`,`src/gateway/rpc-adapter.ts:28`/95)压根没进事件流——pi 进程 crash 了,谁还发事件?这条不靠事件接,靠 `session-store` 的 `openSession`/`prompt` 调用点 catch,落进 `errors` 切片标 `level: "fatal"`。当前 `message-list.tsx:157` 的 `send` 把 `prompt` 失败 `console.error` 完事、`:142`/`:146` 的 `.catch(()=>{})` 把 `setModel`/`setThinkingLevel` 静默吞,都该改成写 `errors` 切片。**协议级错误**走 L0 §2 定义的 `SessionErrorEvent`(聚合了 messageError/toolError/abort 那四类信号),`onEvent` 收到就 push 进 `errors` 切片,带 `entryId`(L0 加的)定位是哪条 assistant 气泡出的错。

inline 红条的数据流:`errors` 切片按 `entryId` 索引,时间线渲染 assistant 气泡时查这个气泡的 entryId 有没有挂错,有就在气泡尾或气泡下叠一条红条(`var(--color-accent-error)` 边/文),文案走 i18n key,带"重试"按钮。重试点了调 `pi.sessions.prompt(原文本)`——同文本再发一次(§6.2 会讲重试的 prompt 契约)。这是用户手势驱动,不走 `errors` 切片,直接发命令,成功后清掉对应 `entryId` 的错误记录。

重试反馈靠 `autoRetryStart`/`End`(`session-state.ts:149-150`)。`autoRetryStart.attempt` 是第几次(底座自己重试,不是用户点的),落进 `retrying: { attempt } | null` 派生态。Footer 的"agent 思考中…"条(现在 `message-list.tsx:223-228`)在 `retrying` 非空时改成"正在重试第 N 次…",`autoRetryEnd.success` 到了清 `retrying`。这是瞬时反馈,不进 `messages`,不进 `errors`——重试是底座自己干的事,它成功了用户根本不该看到一条"出错了又好了"的记录,只该看到"思考中"那个点一直在转。失败到 `autoRetryEnd.success===false` 才升级成一条 `errors`(标 `level: "retry-exhausted"`),inline 红条才出来。

### 3.4 会话信息与压缩:`sessionInfoChanged` 驱动自动命名、`compaction*` 驱动反馈

`sessionInfoChanged` 是自动命名的银弹,理由是它不用猜。当前 sessions-list 的 fallback 链(`index.tsx:75`):`s.name ?? new Date(s.created).toLocaleString()`——没名字就显示创建时间,新会话标题留 null。全仓没有 summariz 逻辑(我搜过,无 `summariz` 命中)。但 pi 自己会主动推 `session_info_changed`(翻译后 `sessionInfoChanged`,`event-translator.ts:21`),带 `name`。这是最低成本路径:不用拉取、不用等首条消息后客户端猜名字、不用调 `summarize` 命令——pi 自己想好了名字推过来,我们只要接住。

接法:`onEvent` 收到 `sessionInfoChanged` 且带 `name`,更新 `snapshot.state.sessionName`(`SessionState` 已有这个字段,`session-state.ts:60`)。sessions-list 订阅 `snapshot.state.sessionName`——它现在的 `select` 设 title 是 `setSessionTitle(s.name ?? ...)` 一次性快照,改成优先读 `snapshot.state.sessionName`,有就用它,没有再 fallback 创建时间。这样 pi 推名字的瞬间,左栏当前会话那行标题自动刷,不用用户手动 rename。还要触发 sessions-list 的 `refresh`(它现在 `agentSettled` 才刷一次列表,sessionInfoChanged 也该刷,因为 `ctx.sessions.list` 返回的 `SessionInfo.name` 字段也会被 pi 写进文件头)。注意 `sessionInfoChanged` 不进 `messages`——它不是消息,是元数据变更,进 `snapshot.state` 就够。

`compactionStart`/`End`(`session-state.ts:144-145`,翻译在 `event-translator.ts:28-29`)当前被 renderer 丢。`compactionStart.reason` 进 `feedback.compacting = { reason }`,`compactionEnd` 清掉。Footer 在 `feedback.compacting` 非空时叠一条"上下文压缩中…"(`reason` 有就带上,如"超过 80% 上下文窗口")。注意区分:这里说的是**压缩中**的瞬时反馈,不是 `entryAppended` 里那条 `type:"compaction"` 的 divider——divider 是压缩**完成后**落进时间线的摘要记录(`sessionEntryToNeutral` 的 `compaction` 分支,`session-state.ts:194-198`),那个仍然进 `messages` 当分隔线。一个是过程(feedback,不入数组),一个是结果(divider,入数组),别混。

### 3.5 待实证:`toolCall` 块带不带 `result` 引用,决定聚合卡片可行性

这条标**待实证**,§7.1 实证先行。问题只有一个:`messageEnd` 落定的 assistant message,它的 `content` 块里那个 `{ type:"toolCall", name:"..." }`,带不带 `toolCallId` 和 `result` 引用?当前代码(`message-list.tsx:48`)只读 `.name`,`toolCallId`/`result` 字段在 content 块里是否存在,代码里没确认——`NeutralMessage.content` 是 `unknown`(`session-state.ts:96`),宽松透传,圆心不约束块形状。所以必须跑真实会话看。

怎么实证:开一个会话,跑几轮带工具调用的对话(bash、文件搜索都行),在 `onEvent` 的 `messageEnd` 分支 `console.log(JSON.stringify(msg.content, null, 2))` 打印末条 assistant 的 content 块,或者直接 `window.pi.sessions.getSnapshot()` 后打印 `snapshot.messages` 里 assistant 的 content。看 `toolCall` 块的字段:`{ type:"toolCall", name, toolCallId?, result?, args?, isError? }` 哪些有、哪些没有。

两种结果走两条方案。**带 `toolCallId` + `result`**:做聚合卡片。一个 assistant 气泡里有 N 个 `toolCall` 块,卡片顶部"Used N tools"(N 个 name 去重计数),展开列出每个工具的 name + result 摘要("搜索了 12 个来源""运行了 3 条 bash"),`toolCallId` 用来和 `toolExecutions` 切片关联拿流式 partial。这是理想形态——一张卡聚合整轮工具使用,而不是现在一堆散 pill。**不带**(只有 name,没有 toolCallId/result):只能 pill 聚合。pill 数 name 个数("Used N tools" 但点不开看结果),结果数据完全靠事件流 `toolExecutions` 切片,但切片和 content 块没有 `toolCallId` 关联键——只能按"本轮 assistant 气泡的 toolCall 块顺序"和"本轮收到的 toolCall* 事件顺序"位置配对,脆且不可靠(并发工具、乱序到达)。这种情况下聚合卡片退化为 pill + 单独的工具执行浮层(按时间序展示本轮所有 toolCall 事件,不挂回具体气泡)。

为什么这条要实证而不是直接定方案:聚合卡片 vs pill 浮层是两套 UI、两套 store 关联逻辑,代码量和交互形态差一截。猜错了写完发现 content 块没 toolCallId,关联不上,整套聚合卡片白写。所以 §7.1 先跑会话打印 content,拿到事实再选方案,符合 CLAUDE.md §3.7 根因修复不打补丁——这里"根因"是数据形状未知,实证是定位根因的动作,不是补丁。

## 4 L2 机制与内容分离:`cardRenderers` 槽位接上

### 4.1 槽位契约 `CardRendererContribution`:`role` 开放字符串做匹配键

`cardRenderers` 槽位在圆心已经留了门——`src/domain/contributions.ts:79` 的 `SlotName` 联合里有它,但 `PluginContributes`(line 87-95)没补对应字段,loader 和渲染层都没读它。这一步是把门装上,而不是另开一道门。复用现有 themes/settings 槽位范式,不造新加载机制。

`CardRendererContribution` 的字段定在圆心 `domain`,和 `SidebarContribution`/`SettingsContribution` 同构:

- **`id: string`**——渲染器唯一标识,注册表去重和覆盖判定要用。
- **`match: string | RegExp | ((msg: NeutralMessage) => boolean)`**——匹配键。看起来是三种并列形态,实质是同一抽象的参数化:`match` 就是"这条消息该不该用我渲染"的判定,形态差异只在判定的强度上。精确字符串最窄(命中一个 role)、正则中等(命中一类 role)、谓词最宽(能看 message 全字段决定)。三者不是三个槽位、不是三个并行机制,是同一个"匹配"参数的三档,统一由注册表遍历调用——`String` 走 `role === s`、`RegExp` 走 `r.test(msg.role)`、`function` 走 `fn(msg)`。选 string/RegExp/predicate 不是"选哪种槽位",是"我的匹配有多严",这是参数级的差异,正是 §3.3 框架管通用调用方传参的形态。
- **`component: string`**——指向插件 `renderer` 导出的组件名,加载器按这个名字从插件模块取组件。和 sidebar 槽位 `component` 字段同构,不发明新约定。
- **`order?: number`**——同优先级内的微调,默认按声明顺序。注意这条 `order` 和加载器层面的 `builtin`/`user`/`project` 三档优先级是两个尺度:`builtin < user < project` 是加载器按来源决定的(见 CLAUDE.md §9.2),`order` 是同一来源内多个 contribution 之间的次序。两个尺度叠加——先按来源分档,同档内按 `order` 再排。这和现有 themes 槽位完全一致,不另造规则。

类型定义只放 `domain/contributions.ts`,gateway/application re-export 一行不写逻辑,不在外层重写一份"宽松版"。这条是契约单源(§1.3):圆心定义唯一源,外层 re-export,编译器帮你守一致性。`PluginContributes` 补上 `cardRenderers?: CardRendererContribution[]` 字段,注释"其余槽随各阶段补"该撤了——槽补完了,门装上了。

### 4.2 `MessageRow` 改成查注册表遍历 `match`,fallback 内置兜底

现状的 `message-list.tsx` 是一台按 role 写死的分支机:`message.role === "bashExecution"`(line 292)一段、`CustomCard`(line 343)、`ThinkingBlock`(line 321)、`EntryDivider`(line 381)……每加一种 custom_message 类型就得改 `MessageRow` 加一个分支。这是内容驱动的反面——引擎按 kind 分支,加内容改引擎,违反开闭。

改造后 `MessageRow` 干一件事:从 store 拿 `cardRenderers` 注册表(按来源优先级排好序的数组),遍历找第一个 `match` 命中的 contribution,用它的 `component` 渲染;全没命中走兜底。伪代码:

```
const renderers = useCardRenderers()  // store 切片,已按 builtin/user/project + order 排序
const hit = renderers.find(r => matchMsg(r.match, message))
if (hit) return <hit.component message={message} />
return <FallbackCard message={message} />  // 兜底
```

`matchMsg` 是把 string/RegExp/predicate 三态收口的纯函数,放在圆心或 application,不放进渲染组件——它是个纯判定,不该和 React 绑。

这一步是内容驱动不是 switch,要把区别讲清。switch 的形态是 `if (role==="bashExecution") X else if (role==="git") Y else if (role==="...") Z`——引擎里写死有哪些 role、每个 role 配哪个组件,加一种 role 改引擎。遍历注册表的形态是 `renderers.find(r => r.match(msg))`——引擎只认"有一组带 match 的 contribution,遍历问它们",不知道也不关心 role 有哪些、每个配什么组件,加一种 role 贡献一个 match 该 role 的渲染器,引擎一行不动。差别在哪:switch 把"role → 组件"的映射焊在引擎里,注册表把这张映射变成数据、推给插件贡献。这是 §3.7 的根因修复不是补丁——补丁是把 switch 再加一个 else if,根因是把映射外置成可查的注册表。

fallback 兜底不是装饰,是契约安全网。没插件 match 时不能崩——`FallbackCard` 是内核的,渲染一个中性的、走 token 的卡片壳,把 message.role 当标题、把 content 按 text block 朴素渲染。它的意义是:删掉任何一个内置渲染器,内核照常启动,该消息不崩,只是少了那块呈现。这正是 §1.4 检验一落地的实证。没有 fallback,删内置件就会崩,无特权差异就守不住。

### 4.3 `bashExecution` 迁出内核:作内置插件贡献走同一槽位同一优先级

`message-list.tsx:292-315` 的 bashExecution 分支是 §1.2 点名的反模式——内核里识别一种业务类型、写死它的渲染。它读 `message.command`/`output`/`exitCode`(custom_message content 旁的字段,由 §3 sessionEntryToNeutral 把 customType 提到 role 上),渲染成"命令 + 输出 + 退出码"的卡片。这段迁成一个内置插件贡献 `match: "bashExecution"` 的 cardRenderer。

迁移分三步,顺序不能反:

1. **建内置插件**——在 `plugins/` 下建一个内置 bash 卡片渲染器插件,`plugin.json` 声明 `contributes.cardRenderers` 一项,`match: "bashExecution"`,`component` 指向插件导出的 `BashCard` 组件。组件里把现有 292-315 的 JSX 搬过去,文案硬编码一并收进插件的 i18n(见 §4.4)。这是内容,该走插件 i18n,不漏。
2. **改 MessageRow 走注册表**——按 §4.2 的遍历逻辑改 `MessageRow`,删掉 292-315 这段分支。改完后 `MessageRow` 不再认识 bash,只认识注册表。
3. **删内核残留**——确认 `message-list.tsx` 里所有 bash 专用分支都迁走了,内核 import 的 lucide 图标里 bash 专用的清掉。

落地的关键是"作内置插件走同一槽位同一优先级":这个内置 bash 渲染器走的加载器、契约、优先级和第三方渲染器完全一样——加载器是 `loader/discover.ts` + `loader/registry.ts`,契约是 `CardRendererContribution`,优先级是 `builtin`(最低)。没有"识别内置 bash 渲染器特殊对待"的代码路径。验证两条:

- **检验一**:删掉这个内置 bash 渲染器插件目录,内核照常启动,bash 消息走 `FallbackCard` 兜底(命令和输出按 text block 朴素展示,不是崩)。
- **检验二**:用户在用户级目录放一个 `match: "bashExecution"` 的渲染器,以 `user` 优先级覆盖内置,内核用用户的那版。内置渲染器在注册表里被排在用户版后面,`find` 先命中用户版,内置版透明失效。

这两条不是额外要写的东西,是 §1.4 两条检验的具体落地——bashExecution 迁出后,这两条检验就能跑通,bash 成了无特权差异的第一个实证样本。

### 4.4 divider 与空态:`DIVIDER_ICONS` 外迁、四处硬编码中文收 i18n

`message-list.tsx:370-378` 的 `DIVIDER_ICONS` 把 divider 的 `kind`(model/thinking/compaction/branch/info/label/entry)和 lucide 图标焊死在内核里——`kind === "model"` 用 `Bot`、`kind === "thinking"` 用 `Brain`……这是内容,kind→图标的映射会变、图标库会换、主题会想覆盖,焊死在内核就是违规。`EntryDivider`(line 381-404)和 `ThinkingBlock`(line 321-340)同理,都是针对具体业务 kind 的渲染逻辑,都该外迁。

外迁的形态有两种选法,选对的不选省事的:

- **方案一:并入 `cardRenderers`,用 match 匹配 divider role**。divider 消息的 role 可以定成 `"divider"`,渲染器 match 里用谓词看 `message.kind` 细分——`msg => msg.role === "divider" && msg.kind === "model"` 命中 model 分割线渲染器。好处是只有一套槽位、一套加载器、一套优先级,不增机制。坏处是 divider 和 card 的渲染形态差挺多,混在一个槽位里 match 谓词会变复杂。
- **方案二:单开 `dividerRenderers` 槽位**,字段和 cardRenderers 同构(match/component/order),只是 match 的对象是 divider 消息的 kind。好处是职责清晰、match 谓词只看 kind 不用先判 role;坏处是多一个槽位、多一套注册表查询。

倾向方案二。divider 和 card 是两种渲染形态——分割线和卡片,混在一个槽位靠谓词内部分流,是"看起来差不多但行为不同"(§3.3 的反收敛信号)。各自一个槽位,各自一个注册表,`MessageRow` 里 divider 分支查 `dividerRenderers`、card 分支查 `cardRenderers`,干净。`CardRendererContribution` 和 `DividerRendererContribution` 字段同构,加载器复用同一套 discover/register,只是注册表分两个数组——机制没增,槽位多一个,这是槽位契约该有的演化。

`DIVIDER_ICONS` 外迁后,内核不再 import 一堆 lucide 图标做 kind→图标的映射。图标选择是插件的事——divider 插件的 `component` 自己决定用什么图标、什么动效,甚至不画图标画别的。这是 §1.2 token key 合规 token 值违规的推广形态:`kind === "model"` 是 key(契约稳定),"用 Bot 图标"是值(内容可变)。

四处硬编码中文(line 195/226/238/331)和外迁是同一件事,不是两件事。现在硬编码在内核里是因为内核直接写了那段 JSX,文案没法走插件 i18n。外迁到插件后,渲染器是插件的,文案自然是插件的,走 `plugins/i18n/locales/{zh-CN,zh-TW,en,de}/shell.json` 加 key,组件里 `t("shell.*")`。`composer.tsx` 是正面教材(全走 t + token),照它来。内核删掉这四处硬编码后,grep 内核源码不应该再出现一条用户可见中文——这是 §1.2 的可机器检验红线。

### 4.5 内核只留 `user`/`assistant`/`divider` 兜底 + 流式滚动/光标机制

`MessageRow` 改完、bashExecution 和 divider 渲染外迁后,内核里还剩什么?剩两类东西,要讲清为什么它们留内核不算违规。

**`user`/`assistant` 兜底渲染留内核**。这两条是对话流的存在前提——拿掉 user 消息渲染,对话流里"用户说了什么"没了;拿掉 assistant 渲染,流式 token 往哪吐没了。§2.1 判据是"拿掉它系统还能不能启动",user/assistant 是不能启动的那类。它们的渲染朴素——user 一个右对齐气泡、assistant 一段 markdown,不识别任何业务类型、不绑任何图标、不写死任何文案。这是消息的本质机制,不是内容。判定方式:换一个完全不同的 agent 产品形态(从 coding agent 换到通用对话),user/assistant 的基础渲染还在,只是插件在上面叠加更多卡片。这和 bashExecution 不同——bashExecution 是 coding agent 特有的业务内容,换产品形态就该没了。

**`divider` 兜底留内核,但只是最朴素的一条线**。`divider` 这个 role 留内核是因为分割线是消息流的本质结构(对话被分成"思考段/模型切换段/上下文压缩段"),拿掉它消息流就糊成一片。但内核的 divider 兜底只画一条中性分隔线——不画图标、不画 label、不识别 kind。具体 kind(model/thinking/compaction…)的图标和 label 全在 dividerRenderers 插件里。内核 divider 是"有分割这件事"的机制,插件是"分割长什么样"的内容。这条线就是 §1.2 的分界落地。

**流式滚动和光标机制留内核**。光标闪烁、流式 token 追加、自动滚到底——这些是消息流的呈现机制,不是任何具体消息内容。它们不识别 role、不绑 kind、不写死文案,拿掉它们对话流能启动但流式体验没了。机制不是内容,留内核。判定方式:换一整套渲染插件,光标和滚动机制一行不动,所有插件共用同一套流式呈现——这是框架管通用(§3.3)的体现,不是某个插件该自己写一遍的。

这条分界线守住,§1.2 就守住了:内核的功能含量趋近零——不是什么都没有,是只剩"拿掉就启动不了"的机制(user/assistant 基础渲染、divider 中性分隔线、流式机制),所有"长什么样"的内容(图标、label、bash 卡片、divider kind 的视觉)全部推给槽位插件贡献。内核 grep 不到写死颜色、写死文案、`if role === "具体业务类型"` 的分支,这节就过了。

## 5 L3 ChatGPT 风格交互补齐

L0 补了圆心契约、L1 扩了事件漏斗、L2 把 `MessageRow` 的硬编码分支换成了 `cardRenderers` 槽位注册表。地基到 L2 都是数据和槽位的事,这一层(L3)只补表现层:光标怎么闪、滚动跟不跟、名字从哪来、hover 出什么按钮、屏幕阅读器播不播、公式能不能渲染。这些纯交互细节,数据流和槽位形状已经就位,不需要再动圆心契约,也不需要再扩 `applyEvent`。本节六条都落在 `shell/renderer`,消费 `packages/react` 的 store 和 hooks,不跨层 import `application`/`domain` 的实现。

### 5.1 流式光标与 AI 头像

流式光标现在缺位。`message-list.tsx` 的 Footer 在 `streaming` 时只渲染一个 `animate-pulse` 的单圆点加"agent 思考中…"(`message-list.tsx:221-229`),assistant 气泡正文末尾(`message-list.tsx:286` 那条 `Markdown`)没有闪烁竖线光标。全仓 grep `blink`/`caret`/`stream.*cursor` 零命中,`markdown.tsx` 也无尾部光标渲染。补法是在末条 assistant 消息的 `Markdown` 文本末尾,`streaming === true` 且该条是 `messages` 末尾时,插一根 1px 宽、`color.primary` 色、`@keyframes blink` 驱动的竖线,对齐正文基线。粒度不是问题——`packages/react/src/session-store.ts:43-47` 的 `messageUpdate` 末条 assistant 替换机制是逐 token 粒度,每次 `messageUpdate` 重渲末条消息,光标自然跟在文末重新挂上,不需要轮询,不需要 sleep,不需要单独计时。这是纯 `streaming` 状态驱动的视觉,事件驱动不轮询这条纪律在这里天然成立。

光标和思考态三圆点是两个分工不同的东西,不能混。光标 = 已经开始吐字、正文在生长,挂在正文末尾;三圆点 = 还在思考、一个字没吐,挂在 Footer。当前 Footer 的单圆点 `animate-pulse`(`message-list.tsx:225`)该换成三圆点错峰骨架(5.6 讲),那是"思考中"的视觉;光标是"生成中"的视觉。两者覆盖的时间窗不同:`agentStart` 到 `messageStart` 之间是思考态(三圆点),`messageStart` 之后是生成态(光标)。把这个分工写进 `cardRenderers` 的渲染约定,光标和三圆点都由 `streaming` + 消息阶段共同决定显隐,而不是各写各的 if。

AI 头像也缺。`message-list.tsx:271-289` 的 assistant 分支无头像无左侧缩进,角色识别靠左右对齐:user `justify-end`(`:260`)、assistant 左对齐。ChatGPT 的基准是靠头像区分而非分边——每条消息左侧一个圆形头像,user 和 assistant 各一种,正文跟着头像右侧铺开。补法是在 assistant 前加一个 `size-8` 圆形头像(走 `color.primary` token 填色或边框),user 前同理加一个 user 头像(走 `color.muted` 或区分色),消息正文统一左对齐,靠头像图案区分角色而不是靠 `justify-end` 把 user 推到右边。这一改同时把 `justify-end` 的分边布局收掉,统一成 ChatGPT 形态的单列左对齐。

这两个东西的归属要分清。光标是机制——它是"流式视觉锚点",告诉用户"系统还在吐字、光标在动就是活着",这个语义不随主题变、不随语言变,留内核(`cardRenderers` 的兜底渲染或 `MessageRow` 兜底层)。头像的"长什么样"是内容——具体画什么图标、用什么颜色组合,是主题插件和语言插件该填的 token(`avatar.assistant`、`avatar.user`);但"有一条 assistant 就该有一个左侧圆形头像、有 user 也该有一个"这个布局规则是机制,留内核。换句话说,内核保证"头像槽位存在且位置正确",插件保证"槽位里画的图标好看"。这和 §1.2 的 token key 合规、token 值外推是同一套纪律:光标动画的 `@keyframes blink` 定义留内核(它是机制),头像的 SVG 图标走插件 token(它是内容)。

### 5.2 `scroll-to-bottom` 状态机:`atBottomStateChange` + 回底按钮

滚动跟随现在只有半截。`message-list.tsx:207-212` 给 `Virtuoso` 配了 `followOutput="smooth"` 和 `initialTopMostItemIndex`,流式时新消息会自动追到底。但缺三样:`atBottomStateChange` 没监听、`isAtBottom` state 没维护、"回到底部"按钮没有。用户上滑读历史,新消息照推,`followOutput="smooth"` 还在追,直接把用户刚滚到的位置拽走——这是和用户抢控制权。

补一个三态状态机。第一态是跟随:`isAtBottom === true` 且 `streaming` 中,`followOutput` 给 `"smooth"`,新消息平滑追底,这是默认行为。第二态是暂停:用户上滑触发 `atBottomStateChange({ atBottom: false })`,`isAtBottom` 置 false,`followOutput` 切成不自动追(可以是 undefined 或按需 `"auto"`),新消息照进 `messages` 数组但视图不动,用户停在原地读。第三态是回到底:用户点右下角浮出的"回到底部"按钮,调 Virtuoso 的 `scrollToIndex` 滚到末条,`isAtBottom` 回 true,`followOutput` 恢复 `"smooth"`。按钮的显隐由 `isAtBottom` 驱动——非底且 `messages.length > 0` 就显,到底就隐。

关键取舍在 streaming 时也要尊重用户上滑。`atBottomStateChange` 是 Virtuoso 主动推送的事件回调,不是轮询——用户一上滑它就推 `atBottom: false`,状态机立刻进暂停态。这比"streaming 时锁死跟随"正确得多:用户在长回复中途想回头看上一段,系统不该强行拽他回底。控制权交还用户的语义是——一旦用户主动离开底部,自动跟随就停,直到用户显式点回底按钮才恢复。`followOutput` 按 `isAtBottom` 切值是这个状态机的唯一输出,没有计时器、没有 sleep、没有"500ms 后自动回底"的赌时序逻辑。

`atBottomStateChange` 和"回到底部"按钮都是机制——"滚动跟随的暂停与恢复"是交互规则,不随主题变、不随语言变,留内核(`MessageList` 组件内,不走 `cardRenderers` 槽位,因为这是列表容器的行为不是消息卡的内容)。按钮的图标(向下箭头)和文案("回到底部")是内容,走插件 i18n 和 token;但"非底时显一个浮按钮、点击滚到底"这个行为规则留内核。

### 5.3 自动命名落地:`sessionInfoChanged` 优先,前端截断兜底

新会话标题现在留空。`index.tsx:159-161`(Shell 快捷键 `Cmd-N`)和 `startNewChat`(`session-store.ts:98-101`)都把标题设 `null`,选中已有会话时 fallback 到 `new Date(s.created).toLocaleString()`(`sessions-list/renderer/index.tsx:75`)。全仓没有 `summarize`/`generateTitle` 逻辑,标题要么是用户手改、要么是时间戳占位。

优先路径是 `sessionInfoChanged` 事件。`gateway/event-translator.ts:21` 已经把 pi 的 `session_info_changed` 翻译成中性的 `sessionInfoChanged`,只是圆心 `SessionEvent` 联合(`session-state.ts:153-161`)还没给它显式类型——它现在落在兜底的 `{ type: string }` 里。§2 L0 给它补精确类型后,`applyEvent`(§3)就能在收到 `sessionInfoChanged` 时把 `event.name` 写进 `SessionState.sessionName`(`session-state.ts:60` 已有这个字段),面包屑和左栏列表订阅 store 自动更新。pi 主动推名就用这条——零成本,纯推送,不拉取,不推理。

兜底是前端截断,给 pi 不推名的场景(底座版本不支持、或会话太短 pi 还没起名)。取首条 user 消息文本前 30 字,换行压成空格,超长加省略号。这套逻辑不是新发明的——`session-scanner.ts:156-174` 的 `lastMessagePreview` 已经做了"倒序找第一条有文本的消息、前 30 字 + …、换行压空格",那是给左栏副标题用的。自动命名复用同一个截断策略,区别只在 `lastMessagePreview` 取最后一条、自动命名取第一条 user。触发时机是首条 `messageEnd`(user)落定后——这时首条 user 文本已在 `messages` 数组里,取它前 30 字写进 `sessionName`,通过 `setSessionTitle`(`ui-store.ts:147`)推到面包屑。等 pi 后续推了 `sessionInfoChanged` 带 name,再覆盖前端截断版本(以底座为准,和 `messageEnd` 的乐观回显去重同源——底座版本到了就替换前端临时版)。

不走的路有两条。一是不用 LLM 生成标题——为起个名额外跑一次推理太贵,首条 user 的前 30 字对大多数会话够用,用户嫌不准自己改。二是不主动拉取——`sessionInfoChanged` 是推送零成本,主动 `get_state` 轮询查 `sessionName` 是违反"事件驱动不轮询"。pi 推了就用,不推就用前端截断兜底,两条路都不碰额外推理和额外请求。

### 5.4 hover 操作行:复制/重新生成/编辑分支,依赖 L4 fork

现状只有复制。`message-list.tsx:406-423` 的 `CopyMessageButton` 是唯一 hover 操作,`opacity-0 group-hover:opacity-100` 浮出,挂在 assistant 的 `group relative` 容器(`:275`)右上角。user 消息(`:258-268`)无任何 hover 操作。要补的是重新生成和编辑分支,这两个都依赖 fork——重新生成 = 在该 user 消息处 fork 一棵新子树 + `switch_session` 切过去 + resync 拉新树基线;编辑 = 同上,只是 fork 后的 prompt 文本换成用户编辑后的内容。协议层有 `fork`(`rpc-types.ts:95`,`{ type: "fork"; entryId: string }`)和 `switch_session`(`:94`),但全仓零调用、`commands.ts` 也没 builder——这块在 §6.1 `forkFromEntry` 编排里补,§5.4 只负责把按钮挂上、把动作接到 store action。

这里最要紧的是别又写成"复制按钮、重新生成按钮、编辑按钮"三个并列 if-else。那会重蹈 §4 把 `MessageRow` 写成一坨 `role === "bashExecution"` 分支的覆辙——每加一个按钮就改一处 switch。要想清楚这是机制还是内容。悬停浮出、键盘可达(Tab 能聚焦)、`aria-label`、`streaming` 门控(流式中不出操作行,流结束才出)——这些是机制,留内核,所有消息角色的 hover 行共享一套。具体按钮调哪个 API(复制调 `navigator.clipboard`、重新生成调 `forkFromEntry` action、编辑调 fork + 改 prompt)——这些是动作,动作是按钮声明的,不是内核 if-else 分支的。

统一抽象是这样:`cardRenderers` 槽位(§4)的每个渲染器除了渲染消息卡,再贡献一个 `hoverActions` 子槽——声明"这条消息 hover 时出哪些按钮、每个按钮的图标/文案/动作"。`MessageRow` 兜底层遍历当前消息的 `hoverActions` 子槽,按 role 取按钮集:user 消息的 `hoverActions` 是[复制、编辑],assistant 的是[复制、重新生成、点赞];同一渲染器机制(浮出时机、aria、focus),不同按钮集。按钮调的是 store action(`useSessionStore.getState().forkFromEntry(entryId)` / `navigator.clipboard.writeText`),action 自己知道怎么发 `fork` + `switch_session` + resync——这是 §6.1 的编排,不是 hover 按钮该管的。这样 hover 行是"声明按钮集 + 统一机制",不是"内核写死每个 role 出什么"。

为什么是 `cardRenderers` 的 `hoverActions` 子槽而不是独立的 `hoverActions` 顶层槽?因为 hover 按钮集和消息角色强绑定——user 消息出编辑、assistant 出重新生成,这个绑定关系和"这条消息怎么渲染"是同一个渲染器的职责。拆成独立槽会让"消息卡渲染器"和"消息 hover 按钮渲染器"各看一遍 role 各自 match,又回到两份 role 分支。合进 `cardRenderers` 让一个渲染器管"这条消息长什么样 + hover 出什么按钮",role 判一次,按钮集和卡片样式同源。

这个归属取舍的直接好处:第三方插件要给某种自定义消息类型加 hover 按钮(比如给 `bashExecution` 卡加"复制命令"按钮),只在它自己的 `cardRenderers` 贡献里加 `hoverActions` 子槽声明,内核一行不动,不用进内核加 `if (role === "bashExecution")`。机制(浮出/aria/门控)在内核兜底层统一,内容(按钮集)在渲染器声明。这正好是 §1.4 无特权差异的检验——内置的 user/assistant hover 按钮和第三方自定义消息的 hover 按钮走同一套机制。

### 5.5 aria-live 与可访问性:选择性播报、`aria-expanded`、`prefers-reduced-motion`

aria-live 全缺。grep `aria-live`/`aria-busy`/`role="status"`/`role="log"` 在 `src/shell/renderer/` 零命中,流式区是 Virtuoso 渲染的普通 div 列表(`message-list.tsx:207`),屏幕阅读器对"正在流式吐字"毫无感知。补法是在流式消息容器上挂 `aria-live="polite"`,但选择性播报——不是每个 `messageUpdate` 都播,那会让屏幕阅读器把逐 token 的碎片念出来,灾难。播的是阶段性事件:`agentStart`(开始)、`agentSettled`(结束)、`toolCallStart`(工具开始)、错误(`SessionErrorEvent`,§2 补的)、重试(`autoRetryStart`)。`messageUpdate` 逐 token 不播,只让 `aria-live` 容器在阶段性事件发生时插一条简短播报(如"正在生成回复…""工具执行中…""出错了,重试第 2 次")。`aria-live` 是机制属性——"流式区该被辅助技术感知"这个语义不随主题变,留内核;播报的具体文案是内容,走插件 i18n。

折叠按钮的 `aria-expanded`/`aria-controls` 也缺。`ThinkingBlock` 的折叠按钮(`message-list.tsx:326-330`)、`CustomCard` 的折叠按钮(`:353-358`)、`EntryDivider` 的可展开按钮(`:387-394`)都只管 `onClick` 切 state,没有 `aria-expanded` 告诉辅助技术"现在展开还是收起",也没有 `aria-controls` 关联被控区域。`CopyMessageButton`(`:410-422`)连 `aria-label` 都没有,只有 `title`——屏幕阅读器读不出"复制"二字。这些是机制属性,补法直接:折叠按钮加 `aria-expanded={open}`、`aria-controls={面板id}`、面板加对应 `id`;复制按钮加 `aria-label={t("shell.copy")}`。`chat-row.tsx:48-51` 的 `role="button"`+`tabIndex`+`onKeyDown` 已经是正向样本,照它对齐。

`prefers-reduced-motion` 兜底全缺。`index.css` 没有 `@media (prefers-reduced-motion: reduce)` 规则,手写动画 `pi-menu-in/out`(`:87-94`)、`pi-collapsible`(`:64-75`)、`panel-collapse-anim`(`:99-101`)都无降级。Tailwind v4 的 `animate-pulse`/`animate-spin` 间接有保护(它内置 `prefers-reduced-motion` 媒体查询),但光标 `@keyframes blink`、三圆点骨架、`pi-menu-in` 这些自己写的没有。补法是在 `index.css` 加一段 `@media (prefers-reduced-motion: reduce)`,把这些动画的 `animation-duration` 归零或 `animation: none`,只保留 `opacity` 过渡(信息仍在,只是不闪不跳)。这是机制——"尊重用户的减少动效偏好"不随主题变,留内核全局 CSS。

键盘可达的最后一公里是 hover 按钮的 focus 显隐。`CopyMessageButton` 现在 `opacity-0 group-hover:opacity-100`——纯 hover 驱动,键盘 Tab 聚焦时按钮还是 `opacity-0` 看不见(虽然能聚焦能按,但看不见聚焦在哪)。补法加 `group-focus-within:opacity-100` 或按钮自身 `focus-visible:opacity-100`,键盘聚焦时也浮出。这是机制(键盘可达性)留内核,和 5.4 的 hover 操作行统一机制同源——浮出规则该对鼠标和键盘一致。

### 5.6 数学公式与打磨项

数学公式全无。全项目 grep `remark-math`/`rehype-katex`/`KaTeX` 零命中,`$...$` 和 `$$...$$` 现在原样当文本渲染。补法在 `markdown.tsx:62-64` 的 `remarkPlugins` 加 `remark-math`、`rehypePlugins` 加 `rehype-katex`,装依赖,引 KaTeX 的 CSS(`katex/dist/katex.min.css`)。这是内容层能力(渲染数学是功能性内容),但因为它挂在 `Markdown` 这个兜底组件上、所有 assistant 消息共享,放内核 `shell/renderer` 的 `markdown.tsx` 合理——和 `rehype-highlight` 同层,都是渲染基础设施。加完 `$E=mc^2$` 才会变成公式而非裸文本。

## 4.5 L1.5 消息模型有状态化:体验层范式的地基

L0 补了圆心契约(`id`/`pending`/`stopped`/`error`/`ContentBlock`),L2 才把 `MessageRow` 的内容焊死外迁成槽位。但圆心契约补完、槽位还没接上的这段中间地带,有一组体验层范式必须在状态层先立起来——它们不是圆心契约本身(契约补完就能用),也不是 L3 的视觉打磨(光标闪不闪、头像好不好看),而是"消息作为有状态对象"这件事在会话流里怎么落地的范式地基:发送即创建 assistant 占位、流式 patch 按 messageId 精确定位、空态 composer 钉底不跳变、滚动控制权交还用户。这四条 toy demo 已经跑通(圆心契约 + 状态机 + 布局三件事一起成立),pi-desktop 现在 message-list.tsx 的 send/applyEvent/空态分支/Virtuoso 配置全是它们的残缺版。这一节把它们从体验症状抽象成状态层范式,作为 L2 槽位化之前、L0 契约之后的过渡地基——有了这层地基,L3 的光标/头像/hover 操作才有地方挂,L2 的 `cardRenderers` 遍历 `match` 才不是在一个会跳变、会丢消息、会抢控制权的视图上跑。每条都对照 toy 的真实实现,落在 pi 的真实符号上。

### 4.5.1 发送即创建 assistant 占位:消除空窗

当前 `message-list.tsx:149-162` 的 `send` 只调 `useSessionStore.getState().appendOptimisticUser(text)` 加一条 user 消息,不创建 assistant 占位,紧接着 `await pi.sessions.prompt(text)` 把文本发出去。pi 那边要等 `agentStart` → `messageStart` 一连串事件回吐,第一个可见 token 才落到屏幕。这段空窗在用户看来就是"消息发出去了但屏幕上什么也没动"——既没有 AI 气泡出现,也没有"思考中"的视觉锚定,体验上是断裂的。对照 toy 的 send(`useChatStore.ts:105-130`),它在 `appendMessages` 之前同时构造 `userMsg` 和 `assistantMsg`(`:116-122` 的 `{ role:'assistant', content:'', pending:true }`),两条一起塞进 messages——assistant 占位立刻渲染出"思考中…",用户按下回车的瞬间就有地方落字,没有视觉真空。

改法是在 renderer 的 `send` 里追加 `appendPendingAssistant()`,session-store 新增这个方法创建 `{ role:'assistant', content:'', pending:true }` 追加到 `messages` 末尾。占位的 id 要稳定(§2.6 L0 给 `NeutralMessage` 补 `id` 字段后,这个占位带一个本地生成的稳定 id)。pi 推 `messageStart` 时,按这个 id 找到占位替换(§4.5.2 的 messageId patch),随后 `messageUpdate` 的 delta 持续往同一条上追加。占位挂 `pending:true` 让 §5.1 的三圆点思考态有明确的挂载目标——`pending` 期间显示思考态,`messageStart` 后 `pending` 翻 false 切到流式光标态,两个视觉阶段由一个字段切换驱动,不需要单独计时,也不需要渲染层各写各的 if 推断"现在该思考态还是生成态"。这一步把"消息有无状态"从契约层(有 `pending` 字段)落到了状态机层(发送动作就创建带状态的占位),体验层范式在状态层就立住了。

### 4.5.2 messageUpdate 按 messageId patch 而非末条替换

当前 `packages/react/src/session-store.ts:41-68` 的 `applyEvent` 对 `messageUpdate` 的处理是"末条是 assistant 就替换它"——`const last = messages[messages.length-1]; if (last?.role === "assistant") return [...messages.slice(0,-1), msg]`。它靠消息在数组里的位置定位流式目标,不靠 messageId。这条逻辑在"末条就是流式目标"的简单对话里能跑通,但只要末条不是 assistant(比如 pi 在 assistant 气泡后插了一条 divider 分隔线,或 §4.5.1 的占位之后又来了别的元消息),`messageUpdate` 的 delta 会走到 `return [...messages, msg]` 分支被当成一条新消息追加——对话时间线上凭空多出一条半截 assistant 片段,断裂感极强。`messageEnd` 同样靠末条 role 比对(`:51` 的 `last.role === msg.role`),末条对不上就追加,定稿版本落不回原占位,占位永远停在 `content:''` 的空壳态。

对照 toy 的 `patchAssistant(set, convId, assistantId, { content: accumulated })`(`useChatStore.ts:346-365`,onDelta 调用点在 `:317`),它按 `assistantId` 在 `messages.map(m => m.id === assistantId ? {...m, ...patch} : m)` 里精确定位目标消息,和它在数组里的位置无关——流式期间插多少别的东西都不影响 patch 命中。这正是 pi 该学的。改法分两步:第一步是 L0 给 `NeutralMessage` 补稳定的 `id` 字段(§2.6 顺带做的契约补齐,`sessionEntryToNeutral` 透传 `entryId`,本地乐观回显和占位各自生成 id);第二步是 `applyEvent` 从"末条 role 比对"改成"id 查找"——`messageUpdate` 进来时 `messages.find(m => m.id === event.message.id)`,命中就 `messages.map` 替换那条、不命中才追加;`messageEnd` 同理按 id 定稿(置 `pending:false`),不再靠末条 role 替换。这样 §4.5.1 创建的占位、流式 delta、最终定稿三者用同一个 id 串成一条消息的完整生命周期,中间插多少 divider、多少 toolCall pill 都不会打断 patch 命中——这恰恰是 L2 `cardRenderers` 按 role 遍历 `match` 的前提:渲染层能信任"messages 数组里每条都是完整的、不会被流式冲散",才敢放心遍历。

### 4.5.3 空态 composer 始终钉底不跳变

当前 `message-list.tsx:183-202` 的空态分支把 composer 和 hero 一起做垂直居中——外层 `flex-1 flex flex-col items-center justify-center` 把 hero 推到视口正中,composer 挂在它下面(`{currentCwd && <div className="w-full px-5 ... pb-5">{composer}</div>}`)。一旦用户发了第一条消息,`messages.length` 不再为 0,组件切到 `:205` 往后的 Virtuoso 视图,composer 钉在底部的固定位置。结果是 composer 从"屏幕中间偏下"瞬间跳到"屏幕底部",位置跳变。用户发第一条消息时输入框跟着抖一下,是体验层的硬伤,也是 §5.6 顺手点名的打磨项——但它的根因不在视觉打磨,在布局结构:空态和有消息态走了两套不同的布局骨架。

对照 toy 的 `App.tsx:59-87`,`<main>` 里是固定顺序的 `<ChatWindow>` + `<Composer>`,两者位置永远不变;空态只是 `ChatWindow` 内部 `messages.length === 0` 时 `return <EmptyState />`(`ChatWindow.tsx:41-43`),Composer 在 main 末尾纹丝不动。空态和有消息态共享同一套布局骨架,不存在切换路径,自然没有跳变。改法是删掉 pi 空态分支的中置布局,改成 hero 居中(`flex-1 flex items-center justify-center`)+ composer 始终在底部(`shrink-0 pb-5`),和有消息态共享同一个外层 `flex-1 flex flex-col min-h-0` 结构。空态只是"hero 区显示 greeting、Virtuoso 区为空",composer 的容器和定位与有消息时一字不差。这样用户从空态发消息,composer 一个像素都不动,只有 hero 区收缩、消息列表长出来——位置稳定的连续感。这条收口后 §5.6 那条打磨项就自动成立,不用单写一条"空态 Composer 该钉底"。它的意义不止消除抖动:布局结构统一后,L2 的 `cardRenderers` 渲染容器、L3 的 hover 操作行、scroll-to-bottom 按钮的挂载点都有了稳定的布局锚,不会因为空态/有消息态切换而需要两套定位逻辑。

### 4.5.4 智能滚动:用户上滑停跟尾 + 回到底按钮

当前 `message-list.tsx:207-212` 给 Virtuoso 配了 `followOutput="smooth"` + `alignToBottom`——始终强制追尾。流式时每来一个 `messageUpdate`,Virtuoso 把视图平滑滚到底。问题是用户中途想上滑读历史:手指刚离开底部往上滚,`followOutput="smooth"` 还开着,新 delta 一到又把视图拽回底部,用户滚到哪都被拉回来。这是和用户抢控制权,长回复场景下尤其难受。对照 toy 的 `ChatWindow.tsx:19-28`,`onScroll` 回调计算 `nearBottom = el.scrollHeight - el.scrollTop - el.clientHeight < 120`——用户接近底部就保持 `autoScroll=true`,用户上滑离开底部 120px 以外就 `setAutoScroll(false)` 停止跟随,新消息照进数组但 `endRef.scrollIntoView` 不再触发。用户滚回底部附近 `nearBottom` 重新为真,跟随恢复。控制权在用户手上。

改法用 Virtuoso 原生的 `atBottomStateChange` 回调维护一个 `isAtBottom` state(不要轮询,Virtuoso 主动推):`atBottomStateChange={({ atBottom }) => setIsAtBottom(atBottom)}`。`isAtBottom` 为真时 `followOutput="smooth"` 保留追尾;用户上滑触发 `atBottom: false`,`followOutput` 切成 `undefined` 停跟随,新消息照进 `messages` 数组但视图停在用户读的地方。非底且 `messages.length > 0` 时浮出一个"回到底部"按钮(右下角绝对定位),点击调 `virtuosoRef.scrollToIndex({ index: messages.length-1, behavior:'smooth' })` 滚到底,`isAtBottom` 回 true,`followOutput` 恢复 smooth。这套和 §5.2 的 `scroll-to-bottom` 状态机是同一个东西,在这里一并落地——控制权交还用户,streaming 期间也尊重上滑,没有"500ms 后自动回底"的赌时序逻辑。把它放在 L1.5 而不是 L3 的理由是:滚动的暂停/恢复依赖 `messages` 数组在流式期间稳定增长(§4.5.1 的占位 + §4.5.2 的 id patch 保证了新 delta 落在已知消息上而非凭空追加),状态层不先把消息生命周期理顺,滚动状态机就是在沙地上盖楼——这就是它作为"体验层范式地基"的位置:契约(`id`)→ 状态机(占位 + id patch + 布局统一 + 滚动控制)→ 表现层(光标/头像/hover)逐层向上,每层都靠下一层稳住。

## 7 推进顺序与关键取舍

### 7.1 实证先行两件事:toolCall 块 result、fork 返回形状

实证先行不是仪式,是防猜错写白。两件待实证:`messageEnd` 落定的 assistant message 的 content 块里 `toolCall` 带不带 `toolCallId` + `result`(§3.5),`fork` 命令返回什么形状(§6.4)。前者决定聚合卡片 vs pill 浮层两套 UI,后者决定 fork→switch→resync 编排的具体步骤。实证方法:开真实会话跑几轮带工具调用的对话,`onEvent` 的 `messageEnd` 分支 `console.log(JSON.stringify(msg.content, null, 2))` 打印 content 块;`window.pi.sessions.send({ type: "fork", entryId: "..." })` 看返回 shape。拿到事实再定方案。

### 7.2 L0→L1.5→L1→L2→L3→L4 依赖排序:为什么这个顺序不可乱

L0(圆心契约补齐)在最前,因为所有上层消费强类型——`ContentBlock` 联合、`entryId`、`pending`/`stopped`/`error`、`SessionErrorEvent` 都是 type-level 的,先补了类型,translator/reducer/renderer 才有强类型归宿。L1.5(消息模型有状态化)紧跟 L0,因为 `applyEvent` 按 id patch 要 L1.5 做,而 id 要 L0 补。L1(事件漏斗)依赖 L1.5 的 id patch——如果还在末条替换,扩宽接回的事件没法正确落位。L2(槽位)在 L1.5 和 L1 之后——`MessageRow` 遍历注册表前提是 messages 数组在流式期间稳定。L3(交互)在 L2 之后——光标挂在 pending 消息末尾、hover 操作行依赖 L4 的 fork 命令。L4(零调用命令)最后,fork/compact 都依赖前面所有层稳了才能编排。

### 7.3 关键决策点回顾

三个决策各记一句话。**patch messageId vs 末条替换**:选 messageId patch(toy 范式),不选末条替换——末条替换靠数组位置定位流式目标,divider 插入或并发消息会错位;id patch 精确定位、不受插入干扰。**重新生成用 fork**:不删末条 assistant 重发,而是 `fork(末条 user 的 entryId)` → `switch_session(forked)` → `resync` 拉新树基线——pi 的会话树支持分支,fork 保留了"在这条消息处分叉"的语义,用户可以回到原分支。**自动命名来源**:优先 `sessionInfoChanged` 事件(pi 主动推 name,零成本),兜底首条 user 前 30 字截断(复用 `session-scanner.ts:156-174` 的 `lastMessagePreview` 策略)——不走 LLM 生成(贵)、不走主动拉取(违事件驱动)。

## 8 QA

**Q: pending 消息在 pi 进程 crash 后怎么处理?**
进程 crash 触发 `SessionErrorEvent({ source: "processCrash", recoverable: false })`,reducer 收到后把所有 `pending: true` 的消息置 `pending: false, stopped: true`。用户看到"已停止"提示,消息内容(部分流式文本)保留。重启 pi 后 `ensureForSend` 重新起进程,用户可点"重新生成"从末条 user 重新流式。

**Q: 多会话多进程下,assistant 占位的 id 怎么保证全局唯一?**
renderer 本地用 `crypto.randomUUID()` 或 nanoid 生成占位 id(和 toy 的 `nanoid()` 同构)。这个 id 是桌面端本地的,和 pi 的 entryId 不是一回事——pi 推 `messageStart` 时带底座的 message id,reducer 用底座 id 替换占位 id(按 §4.5.2 的 find-by-id 逻辑)。如果 pi 不推 messageStart(直接推 messageUpdate),reducer 找不到占位(id 不匹配)会追加——这种情况极罕见,追加的半截消息在 messageEnd 时按 id 定稿。

**Q: 空 cwd(没打开文件夹)时 composer 该显示吗?**
显示,但 disabled。toy 的 `Composer` 有 `disabled` prop,placeholder 改成"请先选择或新建对话…"。pi-desktop 的 composer 始终在底部,空 cwd 时 textarea disabled + placeholder 提示打开文件夹,和有 cwd 时位置一致(不跳变)。hero 显示"新对话"标题。

**Q: 用户上滑停跟尾后,新消息进了 messages 但视图不动,用户怎么知道有新消息?**
"回到底部"按钮带未读计数。按钮显隐由 `isAtBottom` 驱动(非底+有消息就显),按钮上叠一个小数字徽章,表示"N 条新消息"。用户点按钮滚到底,徽章清零,`followOutput` 恢复 smooth。

**Q: L1.5 的改动要动到 main 端 session-store 吗?**
不动。L1.5 全在 renderer 端——`appendPendingAssistant`、`applyEvent` 改 id patch、空态布局、Virtuoso 滚动,都是 renderer 侧的 store 和组件改动。main 端 session-store 不变(它管进程调度和事件路由,不管消息模型)。唯一需要 L0 先做的是 `NeutralMessage` 加 `id` 字段(§2.6),那是 domain 层类型补齐。

**Q: cardRenderers 和 dividerRenderers 是两个槽位还是一个?**
两个。`cardRenderers` 匹配 `message.role`,`dividerRenderers` 匹配 `message.kind`。字段同构(`match`/`component`/`order`),加载器复用同一套 discover/register,注册表分两个数组。`MessageRow` 各查各的,不混在一个槽位靠谓词内部分流。
