# 壳的 i18n 机制

## 1 本文讲什么、不讲什么

这篇文档讲的是 my-harness-desktop **壳的 i18n 机制整体**——文案从哪来、怎么合并、怎么分发、插件怎么写语言包、语言怎么切换。它和另外两份文档的边界要一次说清，避免读者拿着错误的文档对着错误的问题找答案：

- `docs/plugins/system/i18n.md` 讲的是 **i18n 插件本身**——那个位于 `src/plugins/system/i18n/` 的内置壳插件贡献了什么资源、它的语言设置页怎么渲染、删掉它系统会怎样。那是"一个具体插件"的文档。
- `docs/plugins/i18n.md` 是**旧版 05 插件文档**（历史遗留），里面还写着 `window.pi`、`core/application`、48 个 JSON、12 个命名空间这些**已经过时的名词与数字**——前后端分离后这些都对不上了。读那份文档会被带偏，本文是它的机制层事实校正版。
- **本文**讲的是壳这一侧的**机制**：`languages` 槽的契约形状、合并器的优先级语义、i18next 实例怎么起、`currentLocale` 怎么从一次点击传导到全局重渲染、语言包的目录与 namespace 约定、以及"key 合规值违规"这条纪律在这套机制里的落点。物理上对应 `packages/shared/src/domain/contributions.ts`（契约圆心）+ `src/server/application/i18n/`（合并与 translator）+ `src/server/application/loader/registry.ts`（贡献注册）+ `src/web/app/i18n-init.ts`（renderer 初始化）+ `src/web/stores/ui-store.ts`（locale 状态）这条链路。

一句话定位：**壳只有机制，文案全部外挂**。i18n 机制就是"让文案能被外挂"的那套机制——它自己不产出一句文案，只负责把 38 个插件各自贡献的语言包合并成一份 i18next 资源树，再让每个 `t("key")` 都能查到值。

## 2 一条主线：从贡献项到一次 `t()` 查询

在展开细节之前，先看这条链路的完整闭环。它只有五段，每一段后面都会单独成节展开：

- **贡献**：每个壳插件在 `plugin.json` 的 `contributes.languages` 里声明若干条 `LanguageContribution`——每条指向 `locales/{locale}/{namespace}.json` 一个扁平 JSON 文件（或内联对象），键形如 `"timeline.toolExecuting"`。
- **注册**：壳后端的 `PluginRegistry`（`src/server/application/loader/registry.ts`）在 `registerOne` 里把每条 `languages` 贡献连同它的 `pluginId`、`source`（builtin/installed/user/project）、`pluginPath` 收进一个**纯数组**（不是按 id 去重的 Map，也不是 removeById 的 array slot）。
- **合并**：`src/server/application/i18n/merge.ts` 的 `mergeLanguageContributions` 在启动时一次性地把数组里的所有贡献读成对象、按 `locale` 分组、按 `namespace:key` 做 key 级 union，产出 i18next 的 `I18nResource` 形态 `{ locale: { namespace: 嵌套 key 树 } }`。
- **分发**：合并结果连同 `collectNamespaces` / `collectSupportedLngs` / `collectLocaleList` 的产物一起塞进 `MainContext.i18n`，由 `src/server/controllers/appearance.ts` 注册成 `IPC.i18n.resources / list / detect` 三个网关方法，renderer 经 `window.kernel.i18n` 拿。
- **查询**：renderer 的 `src/web/app/i18n-init.ts` 用拿到的资源初始化一个 i18next + react-i18next 实例，之后所有插件经 `useTranslation()` 或 `ctx.i18n.t()` 查文案；语言切换只改 `ui-store.currentLocale`，订阅器触发 `i18next.changeLanguage`，所有持 `useTranslation()` 的组件自动重渲染。

这五段里，"合并"是机制的核心，也是唯一真正做"决策"的地方（谁覆盖谁、namespace 怎么定）；"贡献"和"查询"是内容层的两头；"注册"和"分发"是两根不掺业务逻辑的管道。下面逐段拆。

## 3 languages 槽契约：`LanguageContribution`

### 3.1 类型形状（圆心定义）

`LanguageContribution` 定义在 `packages/shared/src/domain/contributions.ts:130`，是纯类型、零依赖，圆心持有唯一源。它只有三个字段：

```ts
export interface LanguageContribution {
  id: string;                                   // 贡献项标识，通常 {pluginId} 或 {pluginId}.{namespace}
  locale: string;                               // zh-CN / zh-TW / en / de
  resources: Record<string, string> | string;   // key→文案扁平映射，或外部 JSON 相对路径
}
```

它挂在 `PluginManifest` 的 `contributes.languages?: LanguageContribution[]` 上（`contributions.ts:418`）。三个字段的语义逐条钉死：

- **`id` 是声明层的唯一性标识，不是 namespace 来源**。这是这套机制里最容易误读的一点。注释写"通常 `{pluginId}` 或 `{pluginId}.{namespace}`"、`(插件, locale) 维度唯一`——它的作用只是让 manifest 里同一插件的多条语言贡献可区分、可定位，合并器**根本不读 `id`**（`mergeLanguageContributions` 的循环只解构 `contribution.locale` 和 `contribution.resources`，`id` 从不参与任何决策）。namespace 完全由 key 的首段推导（§5.3），`id` 起名成 `timeline.timeline`、`pi-manager.kernel`、`i18n.common` 只是**约定俗成地把它写成了 `{pluginId}.{namespace}`** 方便人读，机制不依赖这个格式。
- **`locale` 是地理区域码，不是 2 位短码**。`zh-CN`（简）/ `zh-TW`（繁）必须靠区域码区分，这是对旧设计文档"只用 2 位短码"的显式偏离（`contributions.ts:128` 注释已标注）。合并器按 `locale` 字符串字面值分组，不做归一化；归一化发生在 renderer 侧的 `detectLocale`（§6.4）。
- **`resources` 是二选一的联合**：要么是**内联对象**（`Record<string, string>`，把文案直接写在 manifest 里，适合一两条的小文案），要么是**相对路径字符串**（指向插件目录下 `./locales/...` 的 JSON 文件，主流做法）。解析逻辑在 `resolveLanguageResources`（§5.2），它区分这两种形态。

### 3.2 resources 的 key 形态：dot-namespace 扁平映射

无论内联还是文件，`resources` 的语义都是一张**扁平的 key→文案**表，key 用 `.` 把 namespace 和子路径串起来。以 `src/plugins/system/i18n/locales/zh-CN/common.json` 为例：

```json
{
  "common.refresh": "刷新",
  "common.locale.zh-CN": "简体中文"
}
```

- `"common.refresh"`：首段 `common` 是 namespace，剩余 `refresh` 是 namespace 内的 key。
- `"common.locale.zh-CN"`：首段 `common`，剩余 `locale.zh-CN` 是**带点号的嵌套 key**，合并阶段会拆成 `locale → zh-CN` 两层嵌套（§5.4）。

这里已经埋下一个关键约定：**key 的第一个 `.` 前的那一段决定它落进哪个 namespace，没有 `.` 的 key 落进默认 namespace `common`**。所以 `resources` 文件名叫什么（`common.json` 还是 `foo.json`）其实不影响归属——归属只看 key 自身的前缀。文件名的 `common`/`settings`/`plugin`/`shell` 只是**组织约定**，让"这个文件里装的 key 都带同一前缀"这件事在物理上可读（§8.3）。

### 3.3 贡献项的规模事实

当前仓库里 38 个壳插件的 `plugin.json` 都声明了 `languages`（`grep -rl '"languages"' src/plugins --include=plugin.json | wc -l` = 38），合计 318 个 `locales/*/*.json` 文件，覆盖 30 个 namespace、4 个 locale（`zh-CN`/`zh-TW`/`en`/`de`）。这个数字不是写死在任何地方的——它由合并器动态收集（§5.5），加一个新 locale 或新 namespace 不需要动壳一行代码。

## 4 注册：languages 槽在 `PluginRegistry` 里怎么存

### 4.1 一条"特殊留数组"的槽

`PluginRegistry`（`src/server/application/loader/registry.ts`）对每种槽位的存储策略不同，这是理解 languages 槽合并语义的前提：

- **themes** 槽用 `Map<string, ThemeContribution>` 按 `id` 去重（`registry.ts:79`，后注册者直接覆盖同 id）。
- **settings / sidePanel / sidebar 等数组类槽**用通用 `ArraySlot<T>`，`push` 前先 `removeById(id)` 清同 id 旧项（`registry.ts:66`），实现"高优先级目录的同 id 贡献覆盖低优先级"。
- **languages** 槽**两者都不是**——它是 `registry.ts:104` 声明的一个**纯数组**，`registerOne` 里直接 `push`，既不去重、也不 `removeById`：

```ts
private languages: { contribution: LanguageContribution; pluginId: string; source: DiscoveredPlugin["source"]; pluginPath: string }[] = [];

// registerOne 内（registry.ts:160-162）：
for (const l of p.manifest.contributes?.languages ?? []) {
  this.languages.push({ contribution: l, pluginId: p.manifest.id, source: p.source, pluginPath: p.path });
}
```

每个元素额外记了 `pluginId`、`source`（`"project" | "user" | "installed" | "builtin"`）、`pluginPath`（插件目录绝对路径，用于把相对 `resources` 路径解析成绝对路径）。`unregister` 时按 `pluginId` 整体过滤（`registry.ts:177`），热加载 deactivate 一个插件就把它的所有语言贡献一起摘掉。

### 4.2 为什么 languages 不按 id 去重

注释说得明白（`registry.ts:103`）："合并器按 source priority 仲裁，特殊留数组"。语言槽的语义是**字典 union**，不是"同名贡献二选一"：

- themes 槽里两个插件贡献同一个 `themeId` 是冲突，必须选一个（后注册覆盖）。
- languages 槽里两个插件贡献**不同的 key** 是常态——timeline 贡献 `timeline.*`，pi-manager 贡献 `kernel.*`，两者不冲突、都该保留。所以注册阶段不能按 id 去重，只能把每条原样堆进数组，把"冲突 key 选谁"这个决策**推迟到合并阶段**按 source priority 做 key 级仲裁。

这一点直接决定了合并器为什么长得和通用 `resolveByPriority`（贡献项级二选一）不一样（§5.1）。

### 4.3 注册序与 source 的绑定

`source` 不是插件自己声明的，而是**由发现目录归属判定**（`src/server/application/loader/discover.ts:7` 注释）：`<cwd>/.my-harness-desktop/plugins/` → `project`、`~/.my-harness-desktop/plugins/` → `user`、数据根的 `installed/` → `installed`、内置目录 → `builtin`。`bootstrap` 的 `assemble.ts:206-209` 按固定顺序 `builtin → installed → user → project` 调用 `discoverPlugins` + `registerAll`，所以数组里**先注册的是低优先级，后注册的是高优先级**。这个顺序本身不做仲裁，只是把材料按序铺好；仲裁规则在合并器里用 `SOURCE_PRIORITY` 数值表表达（§5.1）。

## 5 合并机制：`mergeLanguageContributions`

### 5.1 一个和通用解析不同的优先级语义

`src/server/application/i18n/merge.ts` 开篇注释就把这事点破：**"key 级合并不复用通用 resolveByPriority（那是贡献项级二选一）"**。语言槽是字典 union，所以：

- **不冲突的 key 全部保留**——这是语言槽区别于 themes/settings 的本质。timeline 和 pi-manager 的 key 天然不冲突，谁也不会"覆盖"谁。
- **冲突的 key 按 source priority 取高（高值胜）**——数值表钉死在 `merge.ts:21-26`：

```ts
const SOURCE_PRIORITY: Record<string, number> = {
  builtin: 1, installed: 2, user: 3, project: 4,
};
```

- **同优先级先处理者胜**——合并循环里只有 `existing.priority < priority`（严格小于）才覆盖，等于不覆盖（`merge.ts:99`）。因为注册序是 `builtin → installed → user → project`，同优先级（同一 source 目录）里先发现的插件先被处理，所以同 source 内先声明者胜。

这三个语义合并成一句：**高优先级 source 的 key 覆盖低优先级的同名 key；同 source 内谁先来谁赢；不同 key 各回各家**。i18n 插件是 `builtin`（优先级最低），所以任何第三方语言插件（user/project）都能逐 key 覆盖它的文案——这是"无特权差异"在文案层的落地（`docs/plugins/system/i18n.md` §5.1 也强调了这一点）。

### 5.2 `resolveLanguageResources`：字符串路径 → 对象

合并循环的第一步是 `resolveLanguageResources(contribution, pluginPath)`（`merge.ts:46-70`），把联合类型的 `resources` 归一成对象：

- **字符串形态**：`join(pluginPath, r)` 拼绝对路径 → `existsSync` 检查 → `readFileSync` 读 → `JSON.parse`。文件不存在、JSON 解析失败、顶层不是对象（`null`/数组）三种情况都 `console.error` 记日志并返回 `null`，调用方跳过该条贡献（`merge.ts:84-85`），**不炸启动**。
- **对象形态**：原样返回。

这里用 Node 内置 `fs` 读文件而不是 electron API，因为 `application` 层不 import electron（`merge.ts:8` 注释）——node 服务器宿主也能跑同一段合并逻辑。外部 JSON 路径相对**插件目录**解析，`pluginPath` 由注册阶段的 `p.path` 提供。

### 5.3 阶段一：按 locale 分组 + dot 解析出 namespace

`mergeLanguageContributions` 分两个阶段（`merge.ts:77-138`）。阶段一（`merge.ts:80-103`）建一个 `byLocale: Map<locale, Map<nsKey, { value, priority }>>`：

- 外层按 `contribution.locale` 分组。
- 内层对每个 `(key, value)` 做 dot 解析：**第一个 `.` 前是 namespace，无 `.` 走 `common`**（`merge.ts:91-94`）：

```ts
const dotIdx = key.indexOf(".");
const ns = dotIdx === -1 ? "common" : key.slice(0, dotIdx);
const k  = dotIdx === -1 ? key : key.slice(dotIdx + 1);
const nsKey = `${ns}:${k}`;
```

- 内层 Map 的 key 是 `${ns}:${k}`（用 `:` 拼接，和后续 i18next 的 `nsSeparator: "."` 区分开，避免歧义），value 带 `priority`。
- 覆盖判断：无 existing 直接放；有 existing 时 `existing.priority < priority` 才覆盖（§5.1 的高值胜 + 同优先级先处理者胜）。

注意这一阶段**只做扁平去重，还没建嵌套树**。`nsKey` 里的 `k` 仍可能是带点号的（如 `common.locale.zh-CN` 拆出 ns=`common`、k=`locale.zh-CN`），嵌套留到阶段二。

### 5.4 阶段二：聚合成 i18next 的嵌套资源树

阶段二（`merge.ts:105-138`）把 `byLocale` 聚合成 `I18nResource`：

```ts
export type I18nResourceKey = string | { [key: string]: I18nResourceKey };
export type I18nResource = Record<string, Record<string, I18nResourceKey>>;
// 即 { locale: { namespace: 嵌套 key 树 } }
```

对每个 `nsKey`，取出 `ns` 和 `k`，把 `k` 按剩余 `.` 拆成 `parts`，逐段下钻建嵌套对象。**为什么必须嵌套？** 因为 i18next 的 `keySeparator` 配的是 `"."`，查找路径按 `.` 分层解析；如果合并器把 `"locale.zh-CN"` 作为一个扁平 key 原样存（`resources.common["locale.zh-CN"] = "简体中文"`），i18next 查 `common.locale.zh-CN` 时会按 `locale → zh-CN` 两层找，命中不了这个扁平键（`merge.ts:107` 注释）。所以必须把剩余点号也拆成嵌套对象，让叶子落到正确深度。

阶段二还做**叶/枝冲突容错**（`merge.ts:117-135`）：如果出现 `a.b`（叶子）和 `a.b.c`（子树）互斥——即某个中间段已经是字符串、又要继续下钻，或者叶子位置已存在子树——记 `console.error` 并**跳过该 key**，规则是"先建立者胜出"。注释点明动机：**内容层（插件语言文件）笔误不得炸掉应用启动**（薄壳原则）。文案冲突只丢那一条 key，不崩进程。

### 5.5 三个收集器：namespaces / supportedLngs / localeList

`merge.ts` 还导出三个纯收集函数，它们都是**动态收集、不写死内置清单**（注释明确标注这是对早期"硬编码 8 个 namespace + 4 语言兜底"的评估修复）：

- `collectNamespaces(resources)`（`merge.ts:143-149`）：遍历 `resources` 所有 locale 的 ns 集合去重。产物塞进 `MainContext.i18n.namespaces`，最终作为 i18next 的 `ns` 数组。
- `collectSupportedLngs(contributions)`（`merge.ts:153-157`）：遍历所有贡献项的 `locale` 去重。产物是 `supportedLngs`，renderer 的 `detectLocale` 拿它做归约（§6.4）。
- `collectLocaleList(supportedLngs, resources)`（`merge.ts:163-172`）：把每个 supported locale 映射成 `{ id, name }`，展示名从合并后的 `resources[id].common.locale[id]` 查（即"每个语言用自己的语言表达自己/别的语言名"，如 `zh-CN` 下 `common.locale.en = "English"`），查不到回退 locale code 本身。产物是 `localeList`，语言设置页直接渲染它——**任何第三方贡献的新 locale 都会自动进列表**，不需要改壳。

这三个产物在 `assemble.ts:506-511` 一起装进 `MainContext.i18n`：

```ts
i18n: {
  resources: i18nResources,
  namespaces: collectNamespaces(i18nResources),
  supportedLngs: collectSupportedLngs(languageContributions),
  localeList: collectLocaleList(collectSupportedLngs(languageContributions), i18nResources),
},
```

`MainContext.i18n` 的契约形状定义在 `src/server/application/context/main-context.ts:137-142`。

## 6 i18next 双实例：main 合并、renderer 初始化

### 6.1 设计意图 vs 实际接线（一个必须点破的偏差）

任务清单里写"i18next 双实例（main 合并、renderer init）"，代码注释也是这么写的：`translator.ts:4` 说"main 端持单例（init 一次）；renderer 端经 react-i18next 自己 init 一份"；`i18n-init.ts:4` 说"跨堆：main 与 renderer 各持 i18next 实例（查询语义一致，实例独立）"。但**实际接线只有 renderer 一侧是活的**：

- `src/server/application/i18n/translator.ts` 导出了 `initTranslator`、`changeLocale`、`currentLocale`、`t`、以及 re-export 的 `i18next`，但全仓 grep `initTranslator` 的调用点**只有它的定义行**；对 `../application/i18n/translator` 的 import 只有 `src/server/controllers/appearance.ts:6` 的一处——而且只 import 了 `detectLocale` 这一个**纯函数**。
- 也就是说：**main 端从未初始化过 i18next 实例**。main 做的事只有两件——合并资源（`merge.ts`）和把资源经 IPC 分发（`appearance.ts`）。`translator.ts` 里那套 main 单例（`initTranslator`/`changeLocale`/`t`）是**声明了但没接线的预留代码**。

这是一个值得在文档里明说的现状：所谓"双实例"是设计上的对称布局（两端各持一份、查询语义一致），但当前实现里 main 侧是"只合并、不分发之外不翻译"，**唯一活着的 i18next 实例在 renderer**。main 侧什么时候需要 `t()`？只有当壳后端的 controller 要拼一段用户可见文案（比如系统通知默认标题）时才会用到——目前没有这种需求，所以那套单例一直空着。这不是 bug（renderer 路径完整可用），是"没需求所以没接线"的预留，读代码时别被注释误导以为 main 也 init 了一份。

### 6.2 renderer 实例：`initI18n`

`src/web/app/i18n-init.ts` 的 `initI18n`（`i18n-init.ts:14-45`）是唯一真正初始化 i18next 的地方：

- 幂等：模块级 `inited` 标志，重复调用直接返回。
- 取数：`window.kernel.i18n.resources()` 拿 main 合并好的 `{ resources, ns, supportedLngs }`（IPC 通道 `i18n:resources`，`channel-contract.ts:88`）。
- 定语言：先看 `useUiStore` 里有没有已 hydrate 的 `currentLocale`；没有就用 `window.kernel.i18n.detect(navigator.language)` 检测（`detect` 是 IPC 通道 `i18n:detect`，`channel-contract.ts:86`），检测结果写回 `store.setCurrentLocale`。
- init：`i18next.use(initReactI18next).init({...})`，配置和 main 的 `initTranslator` 保持一致（§6.3）。
- 同步 `document.documentElement.lang = lng`。
- 失败兜底：整段包在 `try/catch`，失败只 `console.error`，i18next 未 init 时 `t` 返回完整 key，不阻塞 render（`i18n-init.ts:5-6` 注释）。

init 时机在 `src/web/app-main.tsx:212`——`initI18n()` 和 `hydrate`、`pluginsReady` 一起 `Promise.all` 进 5s race，`createRoot` 前 await，保证 `useTranslation` 首帧可用；超时也不阻塞。

### 6.3 两份 init 配置的一致契约

main 的 `initTranslator`（`translator.ts:56-70`）和 renderer 的 `initI18n`（`i18n-init.ts:26-40`）配的是**同一套 i18next 参数**，这是"跨堆查询语义一致"的保证：

- `fallbackLng: "en"`（`FALLBACK_LOCALE`，`translator.ts:15`）——fallback 链末端。
- `defaultNS: "common"`——无 dot 的 key 查 `common`（和合并器的 no-dot→common 对齐）。
- `ns: opts.ns` / `supportedLngs`——动态收集的产物。
- `nsSeparator: "."`、`keySeparator: "."`——与合并阶段二的嵌套树对齐。
- `interpolation: { escapeValue: false, prefix: "{{", suffix: "}}" }`——`escapeValue: false` 因为 React 自带转义；插值语法 `{{var}}`（如 `plugin.json` 里的 `"plugin.error.dependents": "以下插件依赖此插件: {{deps}}"`）。
- `returnEmptyString: false`、`returnNull: false`——空串当缺失。
- 不配 `parseMissingKeyHandler`——缺 key 时优先调用方传的 `defaultValue`（manifest 字面值兜底），无 defaultValue 时 i18next 默认返回完整 key（可读，不拼乱码）。

fallback 链因此是：**当前 locale → en →（调用方传的 defaultValue，即 manifest 字面值）→ key 本身**。这一条链是"文案外挂但不崩"的兜底：哪怕某语言包缺一句，界面顶多显示英文或 key，绝不白屏。

### 6.4 `detectLocale`：BCP 47 → 支持 locale 的归约

`detectLocale`（`translator.ts:21-37`）是**纯函数**，两端共用，把 `navigator.language`（或任意 BCP 47）归约到支持的 locale 之一：

- 先精确匹配（大小写不敏感）。
- 主语言/区域归约：`zh-TW`/`zh-HK`/`zh-MO`/`zh-Hant` 或 `zh-tw*`/`zh-hk*`/`zh-mo*` → `zh-TW`；其余 `zh-*` → `zh-CN`；`en-*` → `en`；`de-*` → `de`。
- 都匹配不到 → `FALLBACK_LOCALE`（`en`）。
- 每次命中目标 locale 前都 `supported.includes(...)` 检查——若某 locale 没被任何插件贡献，自动降级到 `en`，不返回一个没有资源的 locale。

这是对旧设计文档"只用 2 位短码"偏离的配套：因为 locale 用了区域码，检测层才需要把 `zh-HK`、`zh-TW`、`zh-CN` 这些**同一主语言的不同区域码**归约到仓库实际支持的 `zh-TW`/`zh-CN` 两档。

## 7 语言切换链路：`setCurrentLocale` → 全局生效

### 7.1 状态真相源：`ui-store.currentLocale`

`currentLocale` 是 `UiState` 的一个字段（`src/web/stores/ui-store.ts:131`），默认值 `"zh-CN"`（`ui-store.ts:217`，与 main 侧 `DEFAULT_PREFS.currentLocale` 一致，`main-context.ts:68`）。它由 `setCurrentLocale` 写入（`ui-store.ts:286-289`）：

```ts
setCurrentLocale: (locale) => {
  set({ currentLocale: locale });
  void window.kernel.prefs.set(PREF_KEYS.currentLocale, locale);
},
```

两件事一起做：**内存态即时更新**（zustand `set`，驱动所有订阅者）+ **prefs 落盘**（`window.kernel.prefs.set`，electron-store，持久化到下回启动）。启动时 `hydrateFromPrefs` 从 `prefs.get(PREF_KEYS.currentLocale)` 读回（`ui-store.ts:441`），保证上次选的语言重启后还在。

### 7.2 两条触发路径，最终都走 `subscribeLocaleChange`

语言切换有两条入口，但底层收敛到同一个订阅器：

- **设置页 UI 路径**：i18n 插件的 `LanguageSettings` 组件（`src/plugins/system/i18n/renderer/index.tsx:20`）只调 `setCurrentLocale(l.id)`——**它不碰 i18next**（`renderer/index.tsx:4-5` 注释：插件守插件式边界，不依赖 shell 实现细节）。
- **程序化路径**：`i18n-init.ts` 导出的 `changeLocale(locale)`（`i18n-init.ts:48-52`）同时做 `setCurrentLocale` + `i18next.changeLanguage` + `document.documentElement.lang`。

**真正让全局生效的是 `subscribeLocaleChange`**（`i18n-init.ts:57-69`），它在 `app-main.tsx:218` 挂一次：

```ts
return useUiStore.subscribe((state) => {
  if (state.currentLocale !== prev) {
    prev = state.currentLocale;
    if (i18next.isInitialized && i18next.language !== locale) {
      void i18next.changeLanguage(locale);
    }
    document.documentElement.lang = locale;
  }
});
```

订阅 `currentLocale` 变化 → 调 `i18next.changeLanguage` → i18next 换当前语言的资源包 → **所有持 `useTranslation()` 的 React 组件自动重渲染**。这一订阅是"设置页只改状态、框架负责传播"的机制落地——插件改一个共享状态，框架把它翻译成 i18next 的语言切换，几十个插件被动响应，插件之间不需要任何直接通信。

### 7.3 多端同步的边界：currentLocale 不在同步白名单里

`app-main.tsx:223-228` 有一个偏好多端同步的白名单 `SYNCED_PREF_KEYS`，只收外观类字段（`currentThemeId`、`fontScale` 等），**`currentLocale` 不在其中**。含义是：**语言是各端独立的选择**，A 端切英文不广播到 B 端（各端独立导航/显示，只同步主题字体这类"想保持一致"的外观）。这是有意的边界，不是遗漏——语言偏好在"状态同步"和"操作独立"的取舍里归入后者。

### 7.4 main 侧的 `changeLocale` 现状

`translator.ts:76-79` 也导出一个 `changeLocale`（`i18next.changeLanguage`），但如前所述 main 从未 init，所以它是预留空转。renderer 的完整链路是：`setCurrentLocale`（ui-store）→ `subscribeLocaleChange` → `i18next.changeLanguage` + `document.lang`。**语言切换全程发生在 renderer 一个堆里**，main 不参与。

## 8 插件怎么写语言包

### 8.1 四件套里的一件：`locales/`

按仓库的"插件四件套"约定（`CLAUDE.md` §7.7），一个功能的 i18n 文案收在插件目录的 `locales/` 子目录：

```
src/plugins/{domain}/{feature}/
  locales/          # i18n 文案（desktop UI 文案）
  renderer/         # desktop 壳插件（UI + 槽位贡献 + 事件）
  pi-extension/     # pi 内核插件（给 pi 补能力，可选）
  dsh-extension/    # dsh 内核插件（给 dsh 补能力，可选）
```

`locales/` 的结构是 `locales/{locale}/{namespace}.json`——**locale 一层、namespace 一层**，每个文件是扁平 `key→文案` JSON。以 `pi-manager` 为例，它的 `locales/` 有 8 个 namespace 文件 × 4 locale：`kernel.json`、`models.json`、`models-settings.json`、`settings.json`、`shell.json`、`ext.json`、`ext-settings.json`、`plugin.json`（`find src/plugins/manager/pi-manager/locales` 可见）。

### 8.2 plugin.json 里的 `contributes.languages` 声明

每个 locale × namespace 文件都要在 `plugin.json` 里声明一条 `LanguageContribution`。以 timeline 插件为例（`src/plugins/sessions/timeline/plugin.json:68-149`）：

```json
"languages": [
  { "id": "timeline.timeline", "locale": "zh-CN", "resources": "./locales/zh-CN/timeline.json" },
  { "id": "timeline.timeline", "locale": "zh-TW", "resources": "./locales/zh-TW/timeline.json" },
  { "id": "timeline.timeline", "locale": "en",     "resources": "./locales/en/timeline.json" },
  { "id": "timeline.timeline", "locale": "de",     "resources": "./locales/de/timeline.json" },
  { "id": "timeline.shell",    "locale": "zh-CN", "resources": "./locales/zh-CN/shell.json" }
  // ... shell / settings / plugin 三个 namespace × 4 locale 同理
]
```

要点：

- **id 惯例是 `{pluginId}.{namespace}`**（`timeline.timeline`、`timeline.shell`、`pi-manager.kernel`），但它只用于 manifest 可读性和 `(插件, locale)` 唯一性，合并器不读（§3.1）。
- **resources 用相对路径**指向插件目录内的文件，合并器用 `join(pluginPath, r)` 解析（§5.2）。
- **namespace 归属看 key 不看 id 也不看文件名**（§5.3）——`timeline.shell` 这条贡献的 `resources` 是 `shell.json`，文件里的 key 都带 `shell.` 前缀，所以实际落进 `shell` namespace；`id` 的第二段和文件名只是"顺势写成一致"。

### 8.3 namespace 约定：共享桶 + 插件私有桶

从 30 个 namespace 的分布看，约定分两类：

- **共享跨插件桶**（多个插件都往里贡献 key，靠前缀不冲突共存）：
  - `common`——高频通用词（`common.refresh`/`common.confirm`/`common.locale.*`），主要 i18n 插件贡献。
  - `settings`——设置页通用文案（`settings.language` 等）。
  - `shell`——壳骨架 UI 文案（`shell.settings`/`shell.savePrompt`/`shell.levelHigh` 等），i18n 插件 + timeline + pi-manager 都往 `shell.*` 贡献（timeline 贡献 `shell.levelOff`…`shell.levelXhigh` 这些思考档位文案）。
  - `plugin`——插件显示名/描述翻译（`plugin.{pluginId}.displayName`、`plugin.error.*`），几乎所有插件都贡献自己的 `plugin.json` 到 `plugin` namespace。
- **插件私有桶**（一个插件的专属域）：`kernel`（pi-manager）、`models`、`timeline`、`sessions`、`projects`、`review`、`stats`、`fonts`、`toolManager`、`dsh`、`voice`、`sub-agent`、`bookmarks`、`pinColors`、`stickers` 等——每个是某插件的领域文案，靠 key 首段天然隔离。

**共享桶为什么能安全 union？** 因为合并是 key 级、不是文件级（§5.1）。两个插件都往 `shell` namespace 放 key，只要 key 前缀不撞（timeline 放 `shell.level*`，pi-manager 放 `shell.*` 自己的词），就各自保留；撞了才按 source priority 仲裁。这就是"跨插件 union 命名空间"的机制含义——**namespace 是弱隔离的命名空间，真正的唯一性单位是完整 key**。

### 8.4 消费方怎么写：`t("key")` 的三条等价路径

贡献了文案之后，消费方查文案有三条等价路径，选哪条取决于在什么层：

- **React 组件里**：`const { t } = useTranslation(); t("timeline.toolExecuting")`——react-i18next 的标准用法，i18n 插件自己的 `LanguageSettings` 就这么用（`renderer/index.tsx:17,29`）。语言切换时自动重渲染。
- **插件代码里经 `usePluginContext()`**：`ctx.i18n.t(key, vars)`——`I18nApi`（`packages/shared/src/domain/context.ts:209-213`）的 `t`，实现里就是包了 `useTranslation()` 的 `t`（`packages/react/src/plugin-context.ts:33-37`）：

```ts
const i18nApi: I18nApi = useMemo(() => ({
  t: (key, vars) => t(key, vars as Record<string, unknown>) as string,
  locale: i18n.language,
  list: () => window.kernel.i18n.list(),
}), [t, i18n.language]);
```

`I18nApi` 三成员：`t(key, vars?)` 同步查字典、`locale` 当前语言、`list()` 异步拿 `{ id, name }[]` 语言列表（走 `i18n:list` 通道）。
- **manifest 声明层**：槽位贡献项里的 `titleKey`/`labelKey`/`descKey` 字段（如 `settingsGroups` 的 `titleKey: "settings.groupSessionFlow"`、`fileActions` 的 `labelKey`），消费方渲染时 `t(labelKey)` 解——**菜单文案不进 manifest 字面值，只进 key**（`contributions.ts:156` 注释）。

无论哪条路径，最终都落到**同一个 renderer i18next 实例**的 `t()`，查的是同一棵合并资源树。

## 9 与其他插件交互：38 个插件共享一份资源

### 9.1 "共享一份资源"的精确含义

i18n 机制不是"i18n 插件把文案翻译好发给别的插件"，而是**壳在启动时把 38 个插件各自贡献的语言包合并成一份 `I18nResource`，所有插件的 `t()` 查这同一份**。三个层面：

- **贡献侧**：每个插件（包括 i18n 插件自己）都是 `contributes.languages` 的一个平等贡献者。i18n 插件贡献的是"壳骨架 + 通用 + 设置 + 插件显示名"这批 key，别的插件贡献各自领域的 key，合起来才是完整资源。
- **合并侧**：合并器不区分"哪个是 i18n 插件"，只认 `locale`、`key`、`source priority`。i18n 插件没有任何特权，它只是 38 个贡献者之一，且因为 `builtin` 优先级最低、可被任何第三方覆盖。
- **消费侧**：别的插件不知道也不关心 `timeline.toolExecuting` 这句文案是谁贡献的，只知道这个 key。文案归属是 i18n 插件的还是 timeline 插件的，对 `t()` 调用方透明。

### 9.2 跨插件 union 命名空间的现实例子

`shell` namespace 是最好的样本：i18n 插件贡献 `shell.settings`/`shell.savePrompt` 等骨架词，timeline 插件贡献 `shell.levelOff`…`shell.levelXhigh` 等思考档位词，pi-manager 贡献 `shell.*` 的内核相关词。它们**各自往 `shell` 这个 namespace 里塞 key**，合并后 `resources["zh-CN"].shell` 是三者 key 的并集。这就是"跨插件 union 命名空间"——namespace 不是某个插件的私有领地，是**按语义域共享的桶**，插件用 key 前缀在桶内划出自己的子空间。

### 9.3 覆盖语义：第三方覆盖内置文案

因为合并是 key 级 + source priority 仲裁（§5.1），第三方语言插件（`user`/`project`）可以**逐 key 覆盖** i18n 插件的 `builtin` 文案——比如第三方贡献 `t("settings.theme")` 的不同翻译，用户看到的是第三方的词。这不是漏洞，是"无特权差异"的正面能力：内置语言包是**最低优先级的默认值**，不是不可动摇的权威。`docs/plugins/system/i18n.md` §6 把这个场景讲透了：删掉内置 i18n 插件后装一个带 `zh-CN` 资源的第三方插件，界面就从"全 key 模式"恢复中文——内核不区分内置/第三方语言插件，谁贡献了资源就用谁的。

### 9.4 依赖方向：i18n 只向内，不产生反向依赖

这套交互里没有"插件 A 调插件 B"的直接通信。别的插件消费 i18n 的输出，靠的是**共享状态（i18next 实例 + currentLocale）的被动响应**，不是事件总线、不是 IPC 直调（`docs/plugins/system/i18n.md` §3.2-3.3 讲了这个间接性）。插件之间唯一需要"知道"的是 key 字符串——这是稳定的查询契约（§10.1），不是对某个插件的运行时依赖。所以 i18n 机制不会在插件之间织出一张反向依赖网。

## 10 i18n 纪律：key 合规，值违规，文案外挂

### 10.1 一条总纪律：key 是契约，值是内容

这套机制的纪律根子，是 `CLAUDE.md` §1.2 的"机制与内容分离"在文案上的特化：

- **key 合规**：壳的代码里必然出现 `t("timeline.toolExecuting")`、`titleKey: "settings.groupSessionFlow"` 这类查询标识。它们是**稳定不变的查询契约**，不是"写死文案"。key 进壳（进渲染代码、进 manifest 声明），是允许且必要的——没有 key，内容就无从挂载。
- **值违规**：`"工具执行中"`、`"设置"` 这些**文案原文**是内容，是会变的。把值写死在壳的 `.tsx`/`.ts` 里就是违规——它该由语言插件经 `languages` 槽贡献，不该焊在机制层。

一句可执行的判据：**打开壳任何一个文件，找到写死的用户可见中文/英文文案原文（不是 key 字符串），就是违规**。`theme["color.primary"]` 是 key 合规，`"#89b4fa"` 是值违规，i18n 与 theme 共用这一条判据，只是值的载体不同（一个是文案、一个是颜色）。

### 10.2 已知偏离（演进待收，标注不藏）

`CLAUDE.md` §7.1 显式标注了两处圆心内容泄漏的历史残留，它们不守"值违规"这条线，属于"标注演进"而非"立即修"：

- `packages/shared/src/domain/slots/theme-tokens.ts` 的 `THEME_TOKEN_DEFAULTS` 兜底色值——圆心里写了写死颜色，违反主题的"值违规"。
- `packages/shared/src/domain/sessions.ts` 的 `roleToPrompt` 中文提示——圆心里写了写死文案，违反 i18n 的"值违规"。

这两处都在**圆心**（`packages/shared/src/domain/`），比壳后端的违规更严重（圆心应零内容）。它们的存在说明"文案外挂"这条纪律还没有 100% 落地，但机制上已经具备收敛它们的条件（语言槽 + key 级合并），只是迁移动作还没做。写新代码时不得新增同类偏离。

### 10.3 文案外挂的完整形态

把纪律正面化，就是"文案外挂"的四段落地，每一段都对应本文前面某节：

- **写文案**：文案原文只出现在 `locales/{locale}/{namespace}.json`（§8.1），不进 `.tsx`/`.ts`/`plugin.json` 的 `title` 字面值（manifest 里的 `title`/`titleKey` 用 key，§8.4）。
- **挂文案**：在 `plugin.json` 的 `contributes.languages` 声明资源（§8.2）。
- **查文案**：消费方只写 `t("key")`，不写原文（§8.4）。
- **换文案**：改 JSON 文件，不碰壳、不发版、不全量回归（改内容只动对应插件）。

### 10.4 机制对纪律的物理保障

i18n 机制本身为这条纪律提供了三道物理防线：

- **壳物理上放不下文案**：`packages/shared/src/domain/` 和 `src/server/application/` 里没有语言文件，文案只能在 `src/plugins/**/locales/` 下（内容层），目录结构就是第一道墙。
- **缺 key 不崩、不白屏**：fallback 链（locale → en → defaultValue → key）保证哪怕某语言包漏一句，界面顶多显示 key 或英文，不会因为文案缺失而炸掉（§6.3）。
- **冲突不炸启动**：合并器的叶/枝冲突容错 + 资源解析失败跳过，让**内容层的笔误**（写错 key、JSON 坏掉）只丢那一条/那一文件，不拖垮整个应用（§5.2、§5.4）——机制对内容容错，是"内容外挂"能成立的底气：外挂的内容可能错，机制必须兜住。

## 11 QA

**Q：`id` 字段到底有没有用？为什么 merge 里不读它？**

`id` 是 `LanguageContribution` 的声明层唯一性标识，用于 `(插件, locale)` 维度区分一条贡献项、manifest 里人可读。合并器不读它，因为**namespace 由 key 首段推导、覆盖由 source priority 仲裁、locale 由 `locale` 字段分组**——三者都不需要 `id` 参与。`id` 写成 `{pluginId}.{namespace}` 是约定不是机制，你把它写成任意唯一字符串，合并结果不变。它唯一的"潜在用途"是将来做热加载时按贡献项精准摘除/替换（当前 `unregister` 按 pluginId 整体过滤，粒度到插件不到贡献项）。

**Q：为什么 main 的 i18next 单例（`initTranslator`）从来没被调用，算不算 bug？**

不算 bug，是"没需求所以没接线"的预留。main 端当前职责是"合并 + 分发"，没有任何一处需要在壳后端拼用户可见文案（系统通知文案由调用方经 i18n 传，见 `context.ts:345` 注释），所以 `translator.ts` 的 `initTranslator`/`changeLocale`/`t` 一直没接线。它和 renderer 的 `initI18n` 配同一套参数，是为了将来 main 需要 `t()` 时语义一致。读代码时别被 `translator.ts:4` 的"main 端持单例"注释误导——那是设计意图，实际 main 没 init。

**Q：两个插件贡献了同名 key 且同 source（比如都是 builtin），谁赢？**

先被处理者赢。合并循环里 `existing.priority < priority` 才覆盖，同 priority 不覆盖（`merge.ts:99`），而注册序里同 source 的插件按发现顺序先注册先处理。所以同一内置目录下，先声明的插件（文件系统枚举序靠前）的 key 生效。确定性、不随机，但**依赖发现序**——如果你在两个内置插件里放了同名 key，想改谁赢，得靠调整插件声明顺序或把想赢的那个升到更高 source 目录。

**Q：`collectNamespaces` 收集的 namespace 和 key 首段推导的 namespace 会不一致吗？**

不会，因为两者同源。`collectNamespaces` 遍历的是**合并后的** `resources`（`{ locale: { namespace: ... } }`）的 ns 键（`merge.ts:144-147`），而这些 ns 正是阶段一从 key 首段推导、阶段二建树时用作第一层的那个字符串。所以 ns 清单 = 实际出现在 key 首段的所有字符串的并集，天然一致。早期实现硬编码 8 个 namespace 兜底时才有不一致风险（漏了动态 ns），现在纯动态收集，加新 namespace 自动进 `ns` 数组。

**Q：语言切换为什么不走事件总线，而走 `ui-store` 订阅？**

因为语言是**跨全部插件共享的框架状态**，不是"插件 A 通知插件 B"的一次性事件。用 `useUiStore.subscribe` 订阅 `currentLocale`，框架把状态变化翻译成 `i18next.changeLanguage`，所有持 `useTranslation()` 的组件被动响应——这是"组件只读 store、零拉取、状态变化推给订阅者"的事件驱动范式的 store 版本。走事件总线会让"切语言"变成需要每个插件 `ctx.events.on` 订阅的一条 channel，反而引入每个插件都要声明 `dependsOn` 的样板。用共享 store 是框架管通用、插件免样板（§9.1 的"框架管语言"）。

**Q：加了新 locale（比如法语 fr），要改壳吗？**

不用。三步全在内容层：① 在插件 `locales/` 下建 `fr/` 目录放 namespace JSON；② 在 `plugin.json` 的 `contributes.languages` 加 `locale: "fr"` 的声明；③ 若想让法语能被自动检测到，在某个语言包的 `common.locale.fr` 补一条展示名（`collectLocaleList` 用它渲染语言列表，缺失回退 code 本身，`merge.ts:170`）。`collectSupportedLngs` 自动收录 `fr`，语言设置页自动多一项。唯一要注意：`detectLocale` 的主语言归约只写了 zh/en/de 三族（`translator.ts:28-35`），`navigator.language = "fr"` 会归约到 `en` 而不是 `fr`——要让法语被浏览器语言自动命中，得给 `detectLocale` 加一条 `fr` 分支（这是壳机制里唯一为新增语言可能要动的地方，其余全是内容层）。

**Q：一条贡献项的 `resources` 指向的文件不存在，会发生什么？**

该条贡献项被跳过，其余照常。`resolveLanguageResources` 里 `existsSync` 失败 → `console.error` → 返回 `null`（`merge.ts:53-55`），合并循环 `if (!resolved) continue`（`merge.ts:84`）。结果：这一条贡献的 key 全都不进资源树，但其它插件、其它文件的 key 正常合并。最终表现是那几句文案回退英文/key，应用照常启动。这是"内容层错误不得炸启动"的兜底之一（§10.4）。

**Q：为什么 `resources` 既可以是对象又可以是路径，两种形态怎么选？**

对象形态适合**一两条内联小文案**——不想为一个 key 建一个文件时直接写 manifest；路径形态适合**成规模的文案表**——主流插件全走路径（318 个 JSON 文件都是路径形态）。联合类型让契约覆盖两种场景，代价是合并器要 `typeof r === "string"` 分叉（`merge.ts:50-68`）。实际约定：**新插件一律用路径形态**，把文案集中在 `locales/` 目录统一管理，内联对象只在极小的场景（第三方插件的个别覆盖词）用。

**Q：删除内置 i18n 插件后，系统的 i18n 机制还在吗？**

机制全在，只剩内容没了。合并器照样跑（只是 `languageContributions` 少了 i18n 那 16 条），`window.kernel.i18n.resources()` 照样返回（其它 37 个插件还在贡献），`initI18n` 照样 init i18next。区别是：`common`/`shell`/`settings`/`plugin` 这四个"壳骨架 + 通用" namespace 的 key 没人贡献了，界面上所有骨架文案（`shell.settings`、`common.confirm` 等）回退 key 本身——用户看到的是"全 key 开发模式界面"。这正是"壳只有机制、内容外挂"的反向证明：机制不依赖任何具体语言插件，内容少了只会让界面难看，不会让系统坏掉（`docs/plugins/system/i18n.md` §6 的完整分析）。
