# i18n

## 1 这个插件解决什么问题

my-harness-desktop 需要支持多语言——今天中文明天英文，今天这个词明天那个词。没有 i18n 插件，文案硬编码在内核里，改文案要动内核、要发版。i18n 插件把所有用户可见文案贡献成外挂资源——改文案只改插件的 JSON 文件，内核一行不动。同时提供语言切换 UI。

## 2 设计决策

### 2.1 为什么是插件而不是内核

文案是内容——会变、会加语言、会调措辞。按 DESIGN.md §2 判据，"一年后会不会换"——会换，推出去。内核只管"有 i18n 初始化和语言切换"这个机制（在 shell 层的 `i18n-init.ts`），文案资源和语言切换 UI 是内容，推给 i18n 插件。

### 2.2 选了什么机制

同时贡献两个槽位：`languages`（48 个 JSON 资源文件，4 语言 × 12 命名空间）和 `settings`（语言切换页，`order: 999` 置底）。零权限——`i18n` 和 `config` 都是核心默认能力。零 `configFile`——语言切换走 `useUiStore` 的 `currentLocale`，不存插件配置文件。

### 2.3 和框架的分工

框架管：i18n 初始化（`i18n-init.ts` 调 `window.pi.i18n.resources()` 拿合并后的资源初始化 i18next 实例）、语言切换（`setCurrentLocale` 触发 i18next `changeLanguage`）、`SettingsSection` / `ListItem` 样式组件。插件管：贡献 48 个 JSON 资源文件 + 渲染语言切换网格。

### 2.4 是否修改了内核

没有。i18n 插件只从 `@my-harness-desktop/react` 导入受控 API——`useUiStore`、`registerSettingsComponent`、`SettingsSection`、`ListItem`、`SettingsComponentProps`，外加 `react-i18next` 的 `useTranslation`。不 import `@my-harness-desktop/core`，不 import `src/domain/`、`src/gateway/`、`src/application/`、`src/shell/` 的任何文件。插件的 `renderer/index.tsx` 总共 52 行，全部是 React 组件代码，零内核代码侵入。

删掉 `src/plugins/i18n/` 目录，内核一行不动。48 个语言资源声明（4 语言 × 12 命名空间）在 `plugin.json` 的 `contributes.languages` 里——内核的插件发现机制读到这个插件不存在，自然跳过；`i18n-init.ts` 里的 `window.pi.i18n.resources()` 返回空对象，i18next 初始化为空资源集，`t("key")` 全部回退 key 本身。语言切换网格在 `contributes.settings` 里声明——插件不在注册表中，设置页自然没有这个 tab。内核的加载器、槽位契约、i18n 初始化机制全都不受影响。
### 2.5 使用了内核的什么功能

i18n 插件使用内核提供的以下能力，每一项底层走什么、内核提供什么保障逐条列出：

- **`contributes.languages` 槽位**：插件在 `plugin.json` 中声明 48 个资源文件，内核的 `mergeLanguageContributions`（application 层）在启动时扫描所有插件的 `languages` 贡献、读 JSON 文件、按 namespace + locale 做 key 级合并。内核保障：冲突 key 按优先级（project > user > installed > builtin）取高，i18n 插件是 builtin 优先级最低。
- **`contributes.settings` 槽位**：`order: 999` 置底，`component: "LanguageSettings"` 指向 renderer 导出的组件。内核的插件加载器在注册组件后，设置页渲染时按 order 排序挂载。
- **`useUiStore`（经 `@my-harness-desktop/react`）**：读 `currentLocale` 和调 `setCurrentLocale`。底层走 electron-store（`~/.my-harness-desktop/config/config.json`），内核在 shell 层的 `i18n-init.ts` 订阅 `currentLocale` 变化 → 调 i18next `changeLanguage`。内核保障：写 electron-store 带原子性（文件级读写锁），读走 zustand subscribe 即时响应。
- **`window.pi.i18n.list()`（经 `window.pi` 直接调用）**：拿可用语言列表。底层走 main 进程 IPC → 查 `mergeLanguageContributions` 合并后的资源 → 收集所有 locale → 返回 `{ id, name }[]`。内核保障：IPC 有权限校验（i18n 是核心默认能力，零声明），返回值格式稳定。
- **框架组件**：`SettingsSection`（只边框无填色）、`ListItem`（列表项样式，`active` prop 控制选中态）。这些组件在 `@my-harness-desktop/react` 发布面，内核提供统一的样式契约——所有设置页用同一套视觉语言。
- **`useTranslation`（react-i18next）**：i18n 插件自己的设置页文案也走 `t("key")`，和其他插件一样经 i18next 消费自己贡献的资源。i18next 实例由内核的 `i18n-init.ts` 初始化——插件不持有也不创建 i18next 实例。
## 3 怎么通信

### 3.1 和内核通信

语言切换不走 `usePluginContext`——直接调 `window.pi.i18n.list()` 拿可用语言列表（因为这是 i18n 插件自己管的列表，不是按 pluginId 绑定的能力）。语言切换走 `useUiStore.setCurrentLocale(locale)`——全局状态，`i18n-init.ts` 订阅它触发 i18next `changeLanguage`，React 组件自动重渲染。

### 3.2 和其他插件通信

间接通信。i18n 插件贡献的文案资源被所有插件通过 `t("key")` 消费——其他插件不需要知道文案是谁贡献的，只需要知道 key。语言切换时所有插件的 `useTranslation()` 自动响应——i18next 实例换资源，React 组件重渲染。这是"插件之间不直接通信，通过共享状态间接通信"的落地。

### 3.3 其他插件怎么使用自己

i18n 插件不和其他插件直接通信——没有插件 A 调插件 B 的接口。其他插件通过 i18next 间接消费 i18n 插件的输出，分两层：

**所有插件的文案渲染**：每个插件的 renderer 组件调 `useTranslation()`（来自 react-i18next），用 `t("key")` 拿文案。这些 key 背后的值由 i18n 插件贡献的 48 个 JSON 文件提供——其他插件不关心文案是谁贡献的，只关心 key 是什么。内核在启动时把 i18n 插件（和其他语言插件）的资源合并到一个 i18next 实例里，所有插件的 `t()` 调用共用这个实例。

受影响的插件列表（枚举当前所有需要 i18n 文案的插件）：`pi-manager`（`kernel.title`、`kernel.desc`、字段描述等）、`pi-model-manager`（`models.addProvider`、`models.deleteProvider` 等）、`theme-manager`（`settings.font`、`settings.theme`、`settings.currentTheme` 等）、sessions-list、projects、git-review、token-stats——凡是调 `useTranslation()` 的插件都受 i18n 插件影响。i18n 插件贡献了 12 个命名空间覆盖所有这些插件的 key。

**语言切换的全局效应**：i18n 插件在设置页提供语言切换 UI——用户点击某个语言后调 `setCurrentLocale(locale)`，这个变化经 `useUiStore` 广播。shell 层的 `i18n-init.ts` 订阅 `currentLocale` → 调 i18next `changeLanguage` → i18next 换资源包 → 所有持有 `useTranslation()` 的 React 组件自动重渲染。整个过程 i18n 插件没有通知任何其他插件——它只是改了共享状态（`currentLocale`），所有订阅者被动响应。

**插件显示名翻译**：i18n 插件的 `plugin` 命名空间（`locales/{locale}/plugin.json`）存放插件显示名的翻译。内核的 `mergeLanguageContributions` 合并后，设置页的 tab 标题、插件列表的名称等走 `t("plugin.{pluginId}")` 查翻译。这些 key 的值由 i18n 插件贡献。

**第三方插件的覆盖**：第三方插件可以通过 `contributes.languages` 贡献同名 key 的文案。由于 i18n 插件是 builtin（优先级最低），第三方插件可以覆盖任何 key——比如第三方插件提供 `t("settings.theme")` 的不同翻译，用户看到的是第三方的文案。这就是"无特权差异"——内核不"识别 i18n 插件的 key 不让覆盖"。
## 4 怎么处理

### 4.1 资源组织

48 个 JSON 文件分布在 `locales/{locale}/{namespace}.json`。12 个命名空间：`common`、`sessions`、`projects`、`settings`、`system`、`kernel`、`models`、`stats`、`plugin`（插件显示名翻译）、`theme`（主题名翻译）、`review`、`shell`。每个文件是 key-value 的扁平 JSON。

内核的 `mergeLanguageContributions` 做 key 级合并：不冲突的 key 全保留，冲突的按来源插件优先级取高。key 的 namespace 解析在合并器里——第一个 dot 前是 namespace，无 dot 走 `common`。

### 4.2 语言切换

`LanguageSettings` 组件渲染四语言卡片网格，点击切换。选中态用 radio-style 圆点表示。切换不重载——i18next 实例换资源，React 组件自动重渲染。`refreshSignal` 变化时重拉语言列表（框架刷新按钮触发）。

## 5 怎么保证

### 5.1 插件不碰 i18next

`LanguageSettings` 组件只调 `useUiStore.setCurrentLocale`——不直接调 i18next 的 `changeLanguage`。i18next 初始化和语言切换在 shell 层的 `i18n-init.ts` 里。插件碰不到 i18next 实例——守插件边界：插件是内容层，不依赖 shell 实现细节。

### 5.2 空态处理

`locales` 列表为空时（`window.pi.i18n.list()` 还没返回），网格为空。不报错——等数据来了再渲染。`refreshSignal` 变化时重拉。

## 6 如果没有这个插件，整个系统会有什么影响

删掉 `src/plugins/i18n/` 目录后，系统仍然能正常启动——内核的加载器发现不到这个插件，跳过加载，其他一切照常。内核不崩溃，机制全在。但用户失去了以下东西：

**失去的 UI 入口**：设置页底部的语言切换网格消失——设置页 tab 列表少一个"语言" tab。用户无法通过 UI 切换语言。

**失去的文案内容**：4 种语言的 48 个 JSON 资源文件全没了。内核的 `mergeLanguageContributions` 只合并其他插件（如果有）的 `languages` 贡献——如果没有任何语言插件，合并结果是空对象。i18next 初始化为空资源集，所有 `t("key")` 调用全部回退 key 本身。用户看到的不是"设置"而是 "settings.theme"，不是"确定"而是 "common.confirm"——整个界面变成 key 的原始字符串。

**对其他插件的影响**：所有插件仍然正常加载、渲染、交互——逻辑没坏。但界面上所有用户可读文字都变成技术性的 key 名，对最终用户没有可用性。这等于一个"开发模式"界面——开发者可能还能用（看到 key 就知道对应什么功能），普通用户完全不能使用。

**语言切换能力**：`useUiStore.currentLocale` 仍然可读写，`i18n-init.ts` 也仍然会订阅并调 `changeLanguage`。但因为没有资源文件，`changeLanguage` 实际上不改变任何东西——所有 key 始终回退 key 本身。用户改 `currentLocale` 的值不影响 UI。

**第三方能否替代**：完全可以。第三方语言插件贡献 `contributes.languages`（带 JSON 资源文件）和 `contributes.settings`（带语言切换 UI）即可完全替代 i18n 插件。由于 i18n 插件是 builtin（优先级最低），第三方插件的文案会覆盖任何同名 key。实际上，用户只要装一个带 `zh-CN` 资源的第三方插件，界面就从"全 key 模式"恢复到正常中文。内核不区分内置语言插件和第三方语言插件——谁贡献了资源就用谁的。

## 7 QA

**Q：怎么加一个新语言？**

在 `locales/` 下加一个新目录（如 `fr/`），放 12 个 namespace JSON 文件。在 `plugin.json` 的 `contributes.languages` 里加资源声明。`collectSupportedLngs` 会自动收录。当前硬编码的兜底语言列表（zh-CN/zh-TW/en/de）不包含新语言——标注"演进"，应该改成纯动态收集。

**Q：第三方插件怎么贡献自己的文案？**

在第三方插件的 `plugin.json` 的 `contributes.languages` 里声明 JSON 资源文件。文件格式和 i18n 插件一致——namespace + key-value。内核的 `mergeLanguageContributions` 会自动合并，冲突时按优先级取高。

**Q：key 冲突时谁赢？**

按来源插件优先级：project > user > installed > builtin。同优先级先处理者胜。i18n 插件是 builtin，优先级最低——第三方插件可以覆盖它的任何 key。
