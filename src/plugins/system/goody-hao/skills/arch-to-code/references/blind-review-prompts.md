# arch-to-code 盲审提示模板

零上下文 subagent 提示模板。每次盲审都**起全新 subagent**，只喂草稿/文件 + 单个问题，不给对话历史、不给源材料、不给背景。复用会让盲测失效（agent 会 rubber-stamp，呼应 SKILL.md §1.14）。

## §4.2 逐节盲审

**何时用**：§4 扩写时，对复杂/机制节做逐节盲审（不盲审每节，借负载控制）。

**起 subagent**（用 Agent 工具，subagent_type 随项目选 general-purpose 或 Explore）：

```
你是一个全新读者，没有任何背景。下面是某架构文档的一节草稿。

<把该节草稿原文贴这里>

只回答这一个问题：

<把预测的读者问题贴这里，例如"这一节说的 conversation_key 两级回退，thread_id 缺失时回退到什么？文中哪一段给依据？">

回答三件事：
1. 这个问题的答案是什么，文中哪段能给依据（引用原文）。
2. 如果文中找不到依据、或让你卡住、或有歧义，明确说"找不到依据/卡住"并指出卡在哪。
3. 这节假设了读者已经知道哪些东西（列出未解释的概念/符号）。

只基于上面给的那节草稿判断，不要假设任何这节之外的上下文。
```

**判据**：能从该节定位到依据且没卡住 → 这节过；找不到依据或卡住 → 回 §4 修这节，修完重盲审（起全新 subagent）。

## §5 整文档盲测（同模板，喂全文）

**何时用**：§5 审全文。零上下文 subagent 拿全文（从盘读回 `docs/{doc}.md`）+ 一个问题。一次一个问题，每个问题一个新 subagent。

提示同上，但"该节草稿"换成"整篇文档"，问题针对整文档级检查：

```
你是一个全新读者，没有任何背景。下面是一份架构文档的全文。

<贴全文，或让 subagent Read 文件路径 docs/{doc}.md —— 若文件大就让它 Read>

只回答这一个问题：

<例如：
- "文中提到'前面那条规则'，指的是第几节哪条？能定位到吗？"
- "通篇用到的'统一抽象'叫什么名字？前后一致吗？"
- "第 3 节的设计决策，和第 5 节的落地是一致的吗？有没有矛盾？"
- "这份文档假设了读者知道哪些前置知识？哪些没解释？">

回答三件事：1 答案+文中依据；2 找不到依据/卡住/歧义就说；3 假设读者已知什么。
```

整文档收敛：横扫缺口空 + 每问文中可定位（SKILL.md §5）。

## §8 spec-vs-impl 盲审（spec 是真相）

**何时用**：§8 第1层。文档已冻结为 spec，对比实现代码。

**关键**：用全新零上下文 subagent，**不用 Workflow 自己的 verify agent**（那些有上下文会 rubber-stamp）。用 code-review 的并行 + 0-100 置信度 + <80 过滤模式。

```
你是一个全新读者，没有任何背景。下面是一份已冻结的架构文档（spec）和据此实现的代码。

spec：<让 subagent Read docs/{doc}.md>
实现代码：<让 subagent Read 相关文件，或 git diff baseline..HEAD>

对每个 impl 单元（见 docs/{doc}.impl-tasks.md），判定：
- implemented：代码按 spec 实现了，行为符合 desired_behavior
- partial：实现了但有缺口（漏了边界、和 spec 部分不符）
- missing：根本没实现

每个判定给：
- 置信度 0-100（<80 的判定要标"存疑"）
- 证据（file:line + spec 锚 §）
- 若实现做了 spec 没说的（基线漂移），单独标出来：drift

只基于 spec 和实际代码判断，不要假设任何对话上下文。spec 是真相，实现要匹配 spec，不是反过来。
```

**收敛**：分类结果汇成结构化残余清单（partial / missing / drift 三类），交用户逐条定：改文档（req-amend 式）还是补实现（回 §7 定向一轮）。

## §8 复盘提示（元审查，第2层）

```
你是一个全新读者。下面是一份 spec 和据此跑的 Workflow 实现产物。

spec：<Read docs/{doc}.md>
任务清单：<Read docs/{doc}.impl-tasks.md>
实现：<git diff baseline..HEAD 或 Read 改动文件>

只审查元层面，不逐行找 bug（那是 code-review 的事）：
1. Workflow 跳了任务清单里哪些单元？为什么？
2. 实现有没有偏离冻结基线（做了 spec 没说的东西）？列出 drift。
3. 有没有引入 kind-switch / 声明式类型标签（违反 SKILL.md 1.4）？
4. 有没有过度工程（实现了 spec 之外的复杂度）？
5. 架构有没有违反洋葱/开闭（哪层该内层却 import 外层）？

每条给证据（file:line + spec 锚）。这是复盘，不是验收——找的是 Workflow 的系统性遗漏，不是个别 bug。
```
